# GradeBookAI — сервер (FastAPI)

Сервер-посредник между данными и клиентами: десктоп-программа, сайт и мобильное
приложение. Клиенты НЕ ходят в БД напрямую — только через этот API по HTTPS.

> **Обновлено 04.09.2026.** Прежняя редакция описывала «Фазу 1»: PostgreSQL, nginx и
> «Фазу 2», в которой десктоп ещё только предстояло отвязать от прямого подключения к
> базе. Всё это давно неправда — десктоп ходит через API с 2.5, PostgreSQL убран
> целиком 04.09.2026. Устаревший README хуже отсутствующего: по нему разворачивают не то.

## Зачем так

- **Offline-first сохраняется:** десктоп работает на локальном SQLite без сети, а когда
  видит сервер — синхронизируется через `/sync`. Это киллер-фича: продукт не ложится от
  отсутствия интернета.
- **На клиентах нет пароля БД.** Доступ — по JWT, роли admin/teacher/student/parent.
  Пароли только хешами (формат общий с десктопом: PBKDF2-SHA512 + Стрибог).
- **Один API на все три платформы** — он же раздаёт собранную Vue-SPA.

## База

**SQLite, и только он.** На бою тот же SQLite под **SQLCipher**: файл шифруется целиком
(AES-256), ключ — `GRADEBOOK_DB_KEY` в `server/.env`.

⚠️ PostgreSQL из проекта убран 04.09.2026 (решение Ярослава). Причина не в идеологии:
двух баз у нас никогда и не было по-настоящему — на бою всё время работал SQLite, а
ветка PostgreSQL не покрывалась ни одним тестом. Непроверенная ветка не даёт
возможности, она даёт ложную уверенность. Подробно — в шапке `app/db.py`.

⚠️ Узкое место SQLite — одновременная ЗАПИСЬ, и закрыто оно режимом WAL плюс ожиданием
блокировки (`db._sqlite_pragmas`), а не сменой СУБД. Масштабы колледжа — тысячи строк.

## Запуск для разработки

```bash
pip install -r server/requirements.txt
cd server
uvicorn app.main:app --reload --port 8000
```

Документация API: <http://localhost:8000/docs>

## Боевое развёртывание

Одной командой на новой машине:

```bash
sudo bash deploy/install.sh --domain esstu-gradebook.ru
```

Всё остальное — обновление, копии, проверка после выкладки, перенос на другую машину,
тяжёлые функции (распознавание речи, перевод, озвучка) — в **`server/DEPLOY.md`**.

## Тесты

```bash
cd server && pytest
```

Прогон занимает около 18 минут: сотни тестов заводят пользователей через гибридный
ГОСТ-хеш на 200 000 итераций. Это ожидаемо медленно, а не зависание.

⚠️ Два одновременных прогона портят общую тестовую базу и дают сотню ЛОЖНЫХ падений.
Прогон должен быть один.

## Модель синхронизации

Каждая сущность несёт `updated_at` (ISO) и `deleted` (надгробие). Метку времени ставит
**сервер**, не клиент. Десктоп хранит метку последней синхронизации, тянет дельту и
отправляет накопленные офлайн-изменения. Конфликты оценок десктоп разрешает локально; на
сервере — LWW по содержимому.

⚠️ `POST /sync/push` решает «применять или нет» СРАВНЕНИЕМ СОДЕРЖИМОГО и на `updated_at`
не смотрит вовсе. Следствие: у кого содержимое иное, тот и прав. Поэтому таблицы, которые
десктоп шлёт без реальной локальной истории изменений (`config`, `subjects`), из
`PUSH_SCOPE` убраны — иначе они откатывали бы сервер.
