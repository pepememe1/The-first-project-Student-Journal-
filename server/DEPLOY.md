# GradeBookAI — развёртывание сервера

> **Переписано 04.09.2026 целиком.** Прежняя редакция описывала продукт годовой
> давности: PostgreSQL, nginx, туннели Serveo/ngrok и «сервер прямо из админ-панели».
> Ничего из этого в продукте нет. Часть была снесена вместе с Qt (13.08.2026), часть
> никогда не работала на бою.
>
> ⚠️ Это не косметика. Устаревшая инструкция ХУЖЕ отсутствующей: по ней уверенно делают
> неверные вещи. Администратор ВСГУТУ, разворачивая по прежней редакции, поставил бы
> PostgreSQL, которого продукт больше не поддерживает, и nginx вместо Caddy — то есть
> потерял бы сжатие, заголовки безопасности и авто-HTTPS.

---

## 0. Коротко: что это за сервер

| | |
|---|---|
| Приложение | FastAPI (`server/app`), **один** процесс uvicorn |
| База | **SQLite**, на бою под **SQLCipher** (файл шифруется целиком, AES-256) |
| Фронт | Vue-SPA, раздаётся тем же приложением + статика через Caddy |
| HTTPS | **Caddy** (сертификат Let's Encrypt получает сам) |
| Автозапуск | systemd, юнит `gradebook` |

⚠️ **PostgreSQL в продукте НЕТ** (решение 04.09.2026). База одна — SQLite. Подробное
объяснение почему — в шапке `server/app/db.py`. Коротко: второй СУБД у нас никогда и не
было по-настоящему (на бою всё время работал SQLite), а непроверенная ветка кода даёт не
возможность, а ложную уверенность.

⚠️ **Воркер ОДИН и таким останется.** Реестр веб-сокетов и ход активностей живут в
памяти процесса: `--workers 2` расколол бы их пополам, и половина участников попала бы в
процесс, который про активность не знает. Переход на несколько процессов — это общий
брокер (Redis pub/sub), отдельная работа, и на нормальной машине она не нужна.

## 1. Развёртывание на новую машину — ОДНА команда

Весь каталог проекта (флешка, архив, `git clone` — неважно) кладём на машину и:

```bash
sudo bash deploy/install.sh --domain esstu-gradebook.ru
```

Скрипт делает всё: пакеты ОС, Caddy, копирование приложения и статики, venv и
зависимости, определение железа, тяжёлый набор (если машина его тянет), ГОСТ-движок,
`.env` с генерацией секретов, systemd-юнит, боевой Caddyfile, проверку.

Полезные ключи:

```bash
--restore-db /путь/к/gradebook_server.db   # развернуть с готовой базой
--no-ai                                    # без распознавания речи и перевода
--with-ai                                  # поставить их даже на слабой машине
--dir /opt/gradebook                       # другой каталог (по умолчанию /root/gb-deploy)
```

### 🔥 Главное правило переноса: `.env` едет ВМЕСТЕ с базой

Файл базы зашифрован ключом из `server/.env`. Привезти базу и дать установщику
сгенерировать **новый** ключ — значит потерять данные навсегда: SQLCipher ответит
«file is not a database», и выглядеть это будет как испорченная копия, а не как неверный
ключ.

Установщик это знает и **останавливается** (код выхода 3), если видит базу без `.env`.
Правильный порядок:

```bash
# на СТАРОМ сервере
scp gb:/root/gb-deploy/server/.env  ./server/.env
scp gb:/root/gb-deploy/server/gradebook_server.db  ./gradebook_server.db
# на НОВОМ
sudo bash deploy/install.sh --domain esstu-gradebook.ru --restore-db ./gradebook_server.db
```

⚠️ **Снимите копию `.env` и храните её ВНЕ сервера.** Без него база не открывается
никем и никогда — это не «неудобно», это потеря данных.

### Чего установщик не умеет, и это принципиально

Домен переключает **A-запись у регистратора**, а не скрипт. Чтобы
`https://esstu-gradebook.ru` открывался с новой машины, нужны две вещи вне её:

1. A-запись домена указывает на IP новой машины;
2. машина доступна снаружи по портам **80** и **443**.

Второе — записанный блокер проекта, и он **не наш**: публичный адрес и порты выдаёт сеть
вуза. Пока их нет, сервер поднимется и будет работать по IP, а Caddy не получит
сертификат (Let's Encrypt проверяет владение доменом через тот самый 80-й порт).
Скрипт честно говорит об этом в конце.

⚠️ **Старый сервер после установки НЕ трогается.** Выключать его можно только после
того, как домен заработает с новой машины.

## 2. Обновление уже работающего сервера

```bash
bash deploy/deploy-server.sh          # server/app + корневые общие модули
cd web && npm run build               # только если менялся фронтенд
bash deploy/deploy-web.sh             # web/dist на бой
```

⚠️ `deploy-server.sh` везёт `server/app/` и корневые модули (список **выводится из
импортов**, а не написан руками — рукописный дважды ронял прод). Файлы уровнем выше,
вроде `server/verify_audit.py`, доставляются отдельно:

```bash
scp server/verify_audit.py gb:/root/gb-deploy/server/
```

⚠️ **`/health: 000` в конце скрипта — не авария.** uvicorn поднимается около пяти
секунд, `curl` не успевает соединиться. Проверять повторно:

```bash
curl -sS -o /dev/null -w '%{http_code}\n' https://esstu-gradebook.ru/health
ssh gb 'journalctl -u gradebook -n 15 --no-pager'
```

⚠️ **Откат есть**: на машине остаются `webdist.old` и `app.old`, возврат — перемещением
обратно. Не удаляйте их «для места»: это и есть механизм отката.

## 3. Что проверять ПОСЛЕ выкладки

«Служба active» — не проверка. Проверка это:

```bash
curl -sS -o /dev/null -w 'главная %{http_code}\n'          https://esstu-gradebook.ru/
curl -sS -o /dev/null -w 'закрытая ручка %{http_code}\n'   https://esstu-gradebook.ru/web/admin/audit/integrity   # ждём 401
curl -sS -o /dev/null -w 'выдуманная ручка %{http_code}\n' https://esstu-gradebook.ru/web/admin/net-takoy         # ждём 404
curl -sS https://esstu-gradebook.ru/app/updates | head -c 120                                                     # версия OTA
```

Все три кода значимы: **200** — сайт жив; **401** — ручка доехала и закрыта ролью;
**404** — заглушка SPA не глотает несуществующие адреса API. Последнее важнее, чем
кажется: пока она их глотала, тест, стучащийся в опечатанный адрес, зеленел не дойдя до
кода.

Новая колонка доезжает миграцией на старте службы. Убедиться, что она реально появилась,
а не «должна была»:

```bash
ssh gb 'cd /root/gb-deploy/server && ../venv/bin/python -c "
from sqlalchemy import inspect; from app.db import engine
print(sorted(c[\"name\"] for c in inspect(engine).get_columns(\"audit_events\")))"'
```

## 4. Резервные копии

| что | где |
|---|---|
| скрипт | `/root/gb-deploy/tools/gb_backup.sh` |
| копии | **`/root/gb-backups/auto/`** ⚠️ |
| журнал | `/var/log/gb-backup.log` |
| таймер | `gb-backup.timer`, полночь по Бурятии (`Asia/Irkutsk`) |
| глубина | 14 снимков |

🔥 **Копии лежат в подкаталоге `auto/`.** В корне `/root/gb-backups/` валяются старые
ручные снимки, и, посмотрев туда, легко решить, что автобэкап сломался месяц назад. Так
уже поднимали тревогу на пустом месте. Смотреть `ls -lt /root/gb-backups/auto/ | head`.

⚠️ **Скрипт ПРОПУСКАЕТ снимок при нехватке места** (нужно ~1.5× размера базы) и пишет
`FAIL` в лог. Это правильный размен — лучше без одной копии, чем добить почти полный
диск. Но значит: **молчание лога не доказательство**, читать надо его хвост.

### Проверка копии восстановлением

Копия, из которой ни разу не восстанавливались, — это надежда, а не копия.

🔥 **Ключ подаётся как RAW-HEX**: `PRAGMA key = "x'<hex>'"`. Подашь как обычную строку —
SQLCipher выведет из неё ключ функцией формирования, и файл «не откроется». **Выглядит
это ровно как испорченная копия**, и на этом уже чуть не объявили копии битыми.
⚠️ Сам `PRAGMA key` ничего не проверяет: ошибка всплывает на первом чтении. «Соединение
открылось» не значит «ключ верный» — проверять надо `integrity_check` и живым `SELECT`.

⚠️ **Все копии лежат на ТОЙ ЖЕ машине.** Получивший root получает и данные, и копии.
Неизменяемого (WORM) хранилища вне сервера нет — это открытый пункт.

## 5. Доступ к машине

В `~/.ssh/config` есть алиас — писать длинную форму не нужно:

```
Host gb
    HostName 194.226.120.74
    User root
    IdentityFile ~/.ssh/gb_vps_ed25519
    IdentitiesOnly yes
```

Значит `ssh gb`, `scp файл gb:/путь`. ⚠️ `IdentitiesOnly yes` не для красоты: без него
агент предлагает серверу все свои ключи подряд, и тот рвёт связь по «too many
authentication failures» ещё до нашего.

## 6. Тяжёлые функции (распознавание речи, перевод, озвучка)

Ставятся отдельным набором и **только на машине, которая их тянет**:

```bash
python tools/provision_ai_host.py            # холостой прогон: железо и что встанет
python tools/provision_ai_host.py --apply    # поставить
```

Включать после установки **ничего не нужно**: продукт спрашивает «умеет ли эта машина» в
рантайме, а не читает тумблер. Проверить, что он это увидел:

```bash
curl -sS https://esstu-gradebook.ru/web/messenger/translate/status
curl -sS https://esstu-gradebook.ru/web/vector/stt/status
```

⚠️ **На арендованный VPS этот набор не влезает, и это измерено, а не прикинуто**: Argos
требует +343 МБ сверх уже живого torch при 342 МБ свободных. Он уйдёт в своп и утащит за
собой журнал на единственном ядре.

⚠️ **Качество перевода на предметной лексике плохое** («две пары по математике» → «two
math couples»). Обещать перевод покупателю как рабочую функцию нельзя.

## 7. Безопасность и 152-ФЗ — что должно быть на бою

- **сервер и данные — в РФ**; для ВСГУТУ ещё и на ИХ железе (п. 5.2.4.1 их политики:
  «не поручает обработку персональных данных другому лицу»). Пока сервер на арендованном
  нами VPS, вуз не соответствует собственной политике — закрывается переездом, а не
  документом;
- **`GRADEBOOK_DB_KEY` задан** — иначе файл базы не шифруется, и ПДн лежат открытым
  текстом. Установщик генерирует его сам; проверить: `grep -c GRADEBOOK_DB_KEY server/.env`;
- **`GRADEBOOK_JWT_SECRET`** — длинный случайный, не дефолт;
- **ГОСТ-движок** (OpenSSL GOST-engine / ViPNet) — установщик находит его сам и включает
  сертифицированный режим; без него хеш считает `gostcrypto` (медленнее, не сертифицирован);
- **секреты — в учётных данных службы systemd**, а не в окружении: переменные процесса
  видны в `/proc/<pid>/environ` и в `systemctl show`, то есть ключ от базы с ПДн читает
  любой, кто получил root. Готовый юнит печатает `deploy/deploy-release.sh --print-unit`;
- **приманки**: `GRADEBOOK_TRUST_IPS` обязателен. Колледж сидит за одним NAT — без белого
  списка один студент со сканером забанит всё здание.

## 8. Caddy: боевой конфиг РОВНО ОДИН

Живой конфиг — `server/Caddyfile` в репозитории. Установщик кладёт его копию, подменяя
одну строку (домен), и проверяет `caddy validate` перед перезапуском.

🔴 **Не пишите свой Caddyfile.** В репозитории лежат ещё два ОБРАЗЦА (`web/deploy/`), и
оба помечены шапкой «⛔ НЕ БОЕВОЙ КОНФИГ». В них нет заголовков безопасности, лимитов,
таймаутов, а пересылка сделана **белым списком путей** — то есть развернувший по такому
получит живой вход, зелёный сайт и 404 там, где у людей обновления телефонов, обновление
десктопа и расписание.

Сверить боевой файл с git (нормализует переводы строк — сырое сравнение хешей даёт
ложное расхождение):

```bash
bash tools/check_prod_caddyfile.sh
```

Код выхода значим: 1 — расхождение, 2 — проверить не удалось. «Нет связи» это НЕ «всё
хорошо».

⚠️ **Две грабли Caddy, обе оплачены упавшим сайтом:**
1. Caddy работает под пользователем `caddy`, а `/root` имеет права `drwx------`. Пропишешь
   `root * /root/gb-deploy/webdist` — сайт отдаст **403 на каждый ассет**. Статика лежит
   копией в `/var/www/gradebook`;
2. пересылать на приложение надо **всё, кроме статики**, а не белый список путей.
   Забытый путь в списке — это 404 на входе в журнал.
