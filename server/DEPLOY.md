# GradeBookAI — Подробный гайд: сервер, запуск, доступ из любой сети

Здесь по-честному и подробно: как это работает, как запустить, почему бывают
ошибки, бесплатные способы открыть сервер наружу, как подключается чужой ПК на
другом интернете и какой именно адрес вводит админ.

---

## 0. Частые вопросы (коротко)

**Почему `server/app/__init__.py` пустой?**
Это нормально. Файл `__init__.py` нужен Python, чтобы считать папку `app`
**пакетом** — тогда работают импорты вида `from app.main import app` и
`from .db import init_db`. Содержимого ему не требуется (у нас там только строка-
докстринг). Пустой `__init__.py` — стандартная практика, это не ошибка.

**Почему ошибка при запуске `main.py` напрямую?**
Если запустить `python server/app/main.py` (или кнопкой «Run» по файлу), будет:
```
ImportError: attempted relative import with no known parent package
```
Причина: `main.py` использует **относительные импорты** (`from .db import ...`,
`from .routers import auth`). Они работают, только когда модуль запущен как часть
пакета `app`, а не как одиночный скрипт. Запуск файла напрямую делает его
`__main__` без пакета → импорты ломаются.

**Как правильно запускать** (из папки `server`):
```bash
cd server
python run.py
# или то же самое:
uvicorn app.main:app --host 0.0.0.0 --port 8000
```
Ключевое: команду давать ИЗ папки `server`, тогда `app` виден как пакет.

## 1. Как это работает

```
        PostgreSQL (приватно, на сервере; в интернет НЕ выставляется)
              ▲  только локально
        Бэкенд-API (FastAPI) ── наружу по HTTPS ──┐
              ▲                                    │
        HTTPS + JWT                          HTTPS + JWT
        Десктоп-прога (offline-first)        Сайт (в будущем)
```

- Прога работает **офлайн** на локальном SQLite. Появилась сеть и задан адрес
  сервера — фоновый поток синхронизируется через API (push свои изменения, pull
  чужие). Нет сети — спокойно ждёт. Это и есть offline-first (киллер-фича).
- Клиенты знают только **адрес API**, не пароль БД. Доступ — по логину/паролю
  (JWT), роли admin/teacher/student.
- Наружу торчит **только API**. PostgreSQL слушает localhost на сервере.

## 2. Запуск для разработки (на своём ПК, без настройки БД)

По умолчанию БД — файл SQLite (ничего ставить не надо):
```bash
pip install -r server/requirements.txt
cd server
python run.py
```
Проверка в браузере:
- http://localhost:8000/health → `{"status":"ok"}`
- http://localhost:8000/docs → интерактивная документация всех эндпоинтов.

## 2.5. Сервер прямо из админ-панели (модель «сервер на ПК админа»)

Если один ПК колледжа будет и рабочим местом администратора, и сервером —
поднимать `uvicorn` руками не обязательно. В программе: **админ-панель → вкладка
«Сервер» → карточка «Этот ПК как сервер»**.

Что делает админ (на ПК-сервере):
1. **Движок БД сервера:** «SQLite» (по умолчанию, ничего ставить не надо) или
   «PostgreSQL». Для PostgreSQL вписать хост/порт/базу/пользователя/пароль и нажать
   **«Проверить подключение»** (нужен установленный `psycopg2`, он в
   `server/requirements.txt`).
2. **«Сохранить настройки БД»** — выбор записывается в `server/.env`
   (`GRADEBOOK_DB_URL`). Секрет JWT генерируется автоматически, если его не было.
3. **«▶ Запустить сервер»** — поднимает FastAPI/uvicorn **ФОНОВЫМ процессом** (порт по
   умолчанию 8000). С версии 2.6.1 сервер и ssh-туннель — ОТДЕЛЬНЫЕ процессы, которые
   **продолжают работать, даже когда программа закрыта** и при смене аккаунта на хосте
   (PID — в `server/server.pid`/`tunnel.pid`, логи — в `server.log`/`tunnel.log`). При
   следующем запуске программа ПОДХВАТЫВАЕТ уже работающий сервер (по `/health` и живому
   PID), не плодя второй. Состояние видно по индикатору. **«■ Остановить»** — единственное,
   что гасит фоновые процессы (закрытие программы их больше НЕ останавливает). Для Serveo
   ссылка теперь **постоянная** (`https://gradebook-xxxx.serveo.net`, имя хранится в
   `.env`) — её не нужно обновлять клиентам между запусками.
4. Узнать IP этого ПК в сети (`ipconfig` / `ip a`) и сообщить клиентам адрес
   `http://<IP-этого-ПК>:8000`.

Что делают клиенты (остальные ПК):
- Получают `.exe`. При запуске, если адрес сервера не задан, появляется окно
  «введите API сервера для синхронизации» — вводят туда `http://<IP-хоста>:8000`
  (сменить адрес можно и на странице входа кнопкой «⚙ Сервер»). Либо адрес зашит в
  сборку (`app_settings.DEFAULT_API_URL`) — тогда вводить ничего не нужно. Дальше:
  вошёл логином/паролем — данные подтянулись. **К PostgreSQL клиенты не
  подключаются** — только к API.

Важные оговорки:
- Сменили движок БД (SQLite ⇄ PostgreSQL) — **перезапустите программу**, затем
  снова «Запустить сервер» (строка подключения читается при старте сервера один раз).
- Хост-ПК должен быть **включён и доступен** по сети (порт 8000 открыт в брандмауэре,
  адрес — локальный IP, не `localhost`). Для доступа из другого интернета — туннель
  или публичный адрес (разделы 6–7).
- Сервер с 2.6.1 — **фоновый процесс**: переживает закрытие программы и смену аккаунта,
  гасится только кнопкой «Остановить» (или `taskkill`/диспетчером задач по PID из
  `server/*.pid`). Это удобно для «сервера на ПК админа», но для по-настоящему
  круглосуточного сервера (с автозапуском при загрузке ОС, рестартом при сбое) —
  боевое развёртывание через systemd (раздел 7).
- Зависимости сервера (`fastapi`/`uvicorn`/`sqlalchemy`, для PostgreSQL ещё
  `psycopg2`) должны быть доступны программе: в сборке `.exe` — включены в неё, при
  запуске из исходников — `pip install -r server/requirements.txt` (один раз).
- Для **боевых** ПДн студентов — сервер в РФ и HTTPS (раздел 7), а не временные
  туннели.

## 3. Как стать администратором

Админ создаётся ОДИН раз. Способы:

**А. Через прогу (штатно).** Запусти прогу → войди логином `admin` → задай пароль
(первый запуск, локально). Затем в админке вкладка «Сервер» → «Запустить сервер»:
поднимется сервер, и его адрес (`http://127.0.0.1:8000`) **сам сохранится в
программе**. При первой синхронизации прога создаст админа на сервере теми же кредами.

**Б. Вручную (проверить сервер).** Через http://localhost:8000/docs → эндпоинт
`POST /auth/bootstrap-admin`, или командой:
```bash
curl -X POST http://localhost:8000/auth/bootstrap-admin ^
  -H "Content-Type: application/json" ^
  -d "{\"login\":\"admin\",\"password\":\"ПарольМин8\",\"full_name\":\"Администратор\"}"
```
Повторный вызов вернёт 409 (админ уже есть) — это нормально и безопасно.

Дальше админ в проге заводит преподавателей/студентов (каждому — логин и пароль).
Они синхронизируются на сервер; эти люди входят со своих ПК своими кредами.

## 4. Какой адрес вводит админ (важно!)

«Адрес сервера» = **базовый URL API**, по которому сервер виден тому ПК.
- **В одной локальной сети:** `http://192.168.1.50:8000` (IP сервера в сети).
  Снаружи, из другого интернета, такой адрес НЕ работает.
- **Из любого интернета:** нужен ПУБЛИЧНЫЙ адрес —
  `https://ваш-домен` или `https://xxxx.trycloudflare.com` (бесплатный туннель,
  раздел 6) или `http://ПУБЛИЧНЫЙ_IP:8000`.

Куда вводить адрес:
1. окно при запуске «введите API сервера для синхронизации» (появляется, если адрес
   не задан);
2. страница входа → кнопка «⚙ Сервер» (сменить адрес может любой клиент, не заходя
   в админку — удобно для Serveo, где адрес меняется каждый запуск);
3. админ-панель → вкладка «Сервер» → «Адрес сервера»;
4. зашить в сборку: `app_settings.DEFAULT_API_URL = "https://адрес"` (тогда клиентам
   вообще ничего вводить не надо). Для разработки — переменная `GRADEBOOK_API_URL`.

Адрес хранится в локальной БД самой программы (отдельного `api_config.json` больше
нет). Пустой адрес = офлайн-режим без сервера (прога работает только локально).

## 5. Как данные подтягиваются на ЧУЖОМ ПК (на другом интернете)

Пошагово, что происходит у друга в другом городе:
1. У друга стоит прога; **публичный** адрес сервера он вводит в окне при запуске
   (или на странице входа кнопкой «⚙ Сервер»).
2. Админ заранее создал другу учётку (преподаватель/студент) — она ушла на
   сервер при синхронизации админского ПК.
3. Друг запускает прогу, вводит свои логин/пароль. Прога:
   - проверяет вход локально (offline-first), а в фоне логинится к API (получает
     JWT);
   - фоновый поток делает `pull` → забирает с сервера студентов, преподавателей,
     группы, занятия, оценки → пишет в свой локальный SQLite;
   - свои изменения отправляет `push`.
4. Друг видит данные. Дальше работает даже без интернета; появится сеть —
   до-синхронизируется.

То есть «другой интернет» не важен — важно, чтобы адрес сервера был **публично
доступен** (раздел 6 — как сделать бесплатно).

## 6. Бесплатные способы открыть сервер наружу

> ⚠️ Важно про 152-ФЗ: бесплатные туннели (Cloudflare/ngrok) идут через
> зарубежные серверы. Это ОК для **теста с другом на учебных/выдуманных данных**,
> но НЕ для боевых персональных данных студентов. Для боевой эксплуатации —
> только сервер в РФ (раздел 7).

### 6.1. Cloudflare Tunnel (рекомендую, бесплатно, без «белого IP»)
Туннель сам соединяется наружу от твоей машины — не нужны проброс портов и
публичный IP (работает даже за роутером/CGNAT). Даёт адрес `https://...`.

1. Скачать `cloudflared` (Windows: с офсайта Cloudflare, один .exe).
2. Запустить бэкенд: `cd server && python run.py` (слушает :8000).
3. В другом окне:
   ```bash
   cloudflared tunnel --url http://localhost:8000
   ```
   Он напечатает адрес вида `https://random-words.trycloudflare.com`.
4. Этот адрес и есть `api_url`. Дай его другу — он введёт адрес в окне при запуске.
   - Быстрый режим выше даёт ВРЕМЕННЫЙ адрес (меняется при перезапуске).
   - Постоянный адрес (свой домен) — бесплатно через аккаунт Cloudflare +
     `cloudflared tunnel create` + DNS-запись (named tunnel).

### 6.2. ngrok (просто, бесплатно)
1. Зарегистрироваться на ngrok, поставить, прописать authtoken.
2. `ngrok http 8000` → выдаст `https://xxxx.ngrok-free.app`.
3. Это `api_url`. На бесплатном тарифе адрес меняется при каждом запуске.

### 6.3. localhost.run / serveo (без установки, по SSH)
```bash
ssh -R 80:localhost:8000 localhost.run
```
Выдаст временный публичный URL. Удобно для разовой проверки, бывает нестабильно.

### 6.4. Дом/колледж: «белый IP» + бесплатный домен (если есть публичный IP)
Если у ПК есть публичный IP и доступ к роутеру:
- проброс порта 8000 (или 443) на этот ПК;
- бесплатный домен через DuckDNS (`*.duckduckgo`-подобный поддомен бесплатно);
- бесплатный сертификат Let's Encrypt (certbot) для HTTPS.
⚠️ У многих провайдеров в РФ «серый» IP (CGNAT) — проброс не сработает, тогда
только туннель (6.1/6.2).

### 6.5. Бесплатные облачные ВМ
Есть бесплатные/триальные ВМ (например, Always Free у некоторых облаков), но они
обычно вне РФ и требуют привязку карты — для боевых ПДн не подходят (152-ФЗ).
Для теста — на твой выбор.

## 7. Боевой режим: сервер в РФ + HTTPS (для реальных данных)

VPS в РФ (Timeweb / Selectel / Yandex Cloud / VK Cloud / Reg.ru), публичный
адрес, HTTPS. PostgreSQL — на той же ВМ, слушает localhost.

### 7.1. БД
```bash
sudo apt update && sudo apt install -y python3-venv postgresql nginx
sudo -u postgres psql -c "CREATE DATABASE vsgutu_grades;"
sudo -u postgres psql -c "CREATE USER vsgutu_user WITH PASSWORD 'СИЛЬНЫЙ_ПАРОЛЬ';"
sudo -u postgres psql -c "GRANT ALL PRIVILEGES ON DATABASE vsgutu_grades TO vsgutu_user;"
```

### 7.2. Приложение
```bash
cd /opt && git clone <репозиторий> gradebook && cd gradebook/server
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env   # отредактировать:
#   GRADEBOOK_DB_URL=postgresql://vsgutu_user:СИЛЬНЫЙ_ПАРОЛЬ@localhost:5432/vsgutu_grades
#   GRADEBOOK_JWT_SECRET=<openssl rand -hex 32>
#   GRADEBOOK_ALLOWED_ORIGINS=https://ваш-домен   (когда появится сайт)
```

### 7.3. Автозапуск (systemd) — `/etc/systemd/system/gradebook.service`
```ini
[Unit]
Description=GradeBookAI API
After=network.target postgresql.service

[Service]
WorkingDirectory=/opt/gradebook/server
EnvironmentFile=/opt/gradebook/server/.env
ExecStart=/opt/gradebook/server/.venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 8000 --workers 4
Restart=always

[Install]
WantedBy=multi-user.target
```
```bash
sudo systemctl enable --now gradebook
```

#### Барьер подтверждения устройств в systemd-проде (важно)
С версии 2.6.1 сервер не пускает неодобренные ПК (см. барьер `app/connect.py`). В
модели «сервер из админки» хост опознаётся автоматически по `GRADEBOOK_HOST_DEVICE_ID`,
который проставляет десктоп. Но при запуске СЛУЖБОЙ (systemd) сервер поднимается без
десктопа, и админ работает с УДАЛЁННОГО ПК — его устройство тоже неодобрено, а одобрить
его некому (вкладка «Запросы» сама требует одобренного устройства). Замкнутый круг
разрывается разово одним из способов:
- прописать device_id админского ПК в `EnvironmentFile` как `GRADEBOOK_HOST_DEVICE_ID`
  (узнать id: на его ПК — локальный ключ `device_id` в БД программы), затем
  `systemctl restart gradebook`; после первого входа можно убрать;
- либо добавить строку в таблицу `approved_devices` напрямую в БД (одна запись с
  `device_id` админского ПК).
После этого админ входит, видит и одобряет остальные ПК как обычно.

⚠️ Многоворкерный нюанс: ОЖИДАЮЩИЕ запросы и коды живут в памяти процесса (как
`events.py`/`throttle.py`), поэтому при `--workers N` запрос/принятие/ввод кода могут
попасть в РАЗНЫЕ воркеры и «не увидеть» друг друга. Одобренные устройства лежат в БД и
общие для всех воркеров — на уже подключённых ПК это не влияет. Если одобрение новых ПК
по службе «капризничает», временно поднимите процесс одобрения на одном воркере (или
вынесите pending-состояние в общий слой — Redis/БД, как и для `events`/`throttle`).

#### Сколько воркеров и зачем (масштаб на сотни-тысячи пользователей)
Один процесс uvicorn использует по сути одно ядро CPU. Вход проверяет пароль через
PBKDF2 (200 000 итераций — это требование защиты ПДн, ослаблять нельзя), поэтому при
ОДНОВРЕМЕННОМ входе тысяч пользователей один процесс становится узким местом (входы
выстраиваются в очередь). Нагрузочный тест это подтвердил: на 1 воркере дельта-
синхронизация тянет тысячи (5000 пользователей: pull p50 ~2.5 c, >99% успеха), а вот
герд из 5000 ОДНОВРЕМЕННЫХ входов на одном процессе занимает ~2.5 минуты.

Решение — несколько воркеров: `--workers N` (ориентир: N = число ядер CPU сервера,
обычно 4–8). Тогда входы распараллеливаются по процессам.

⚠️ **Несколько воркеров требуют PostgreSQL, а не SQLite.** Разные процессы не могут
безопасно делить один SQLite-файл на запись (блокировки/порча). Поэтому связка для
нагрузки: **PostgreSQL (общая БД) + `--workers N`**. SQLite — для одного процесса
(небольшой колледж, режим «сервер из админки»).

> Встроенный «сервер из админки» (вкладка «Сервер») запускает ОДИН процесс внутри
> программы — это удобно для небольшого развёртывания. Для нагрузки в тысячи
> одновременных входов разворачивайте сервер этим способом (systemd + несколько
> воркеров + PostgreSQL), а не кнопкой в админке.

### 7.4. nginx + HTTPS (Let's Encrypt) — `/etc/nginx/sites-available/gradebook`
```nginx
server {
    server_name ваш-домен;
    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```
```bash
sudo ln -s /etc/nginx/sites-available/gradebook /etc/nginx/sites-enabled/
sudo apt install -y certbot python3-certbot-nginx
sudo certbot --nginx -d ваш-домен
sudo ufw allow 80,443/tcp && sudo ufw enable
```
Теперь API на `https://ваш-домен`. В прогах `api_url = https://ваш-домен`.

### 7.5. Чек-лист безопасности (152-ФЗ)
- Сервер и БД — в РФ. Наружу только 80/443; PostgreSQL — localhost.
- `GRADEBOOK_JWT_SECRET` — длинный случайный (не дефолт).
- HTTPS обязателен. `.env` не коммитить. Пароль БД сильный.
- Бэкапы PostgreSQL по расписанию (`pg_dump`).
- Анти-брутфорс входа включён на сервере (`/auth/login`: после серии неверных
  попыток — `429 Too Many Requests`). За обратным прокси проследи, чтобы реальный
  IP клиента доходил до приложения (заголовок `X-Forwarded-For`) — иначе все
  клиенты выглядят как один адрес. Caddy и nginx-конфиги ниже это уже передают.

### 7.6. Caddy — HTTPS в одну строку под СВОИМ доменом (рекомендуемая замена serveo)

Это рекомендованный боевой способ, когда сервером служит обычный ПК (в т.ч. на
Windows) с «белым» (публичным) IP — например, ПК администратора в колледже.
В отличие от serveo/ngrok, **TLS терминируется на вашем же ПК**, и данные не
проходят через чужого иностранного посредника — это и нужно для 152-ФЗ.

Почему Caddy, а не nginx+certbot: Caddy сам получает и продлевает сертификат
Let's Encrypt для вашего домена, конфиг — одна строка. Certbot не нужен.

**Что нужно один раз:**
1. **Домен.** Купить домен (RU-домен — недорого). `GradeBookAI` — это имя продукта,
   нужен реальный домен, например `gradebookai.ru` (или поддомен колледжа
   `journal.vsgutu.ru`).
2. **DNS A-запись** домена → ваш публичный IP. Если IP **динамический** — поднимите
   DDNS (DuckDNS и т.п.), чтобы запись следовала за IP.
3. **Проброс порта** на роутере: внешние 80 и 443 → этот ПК. (80 нужен Caddy для
   проверки домена при выпуске сертификата.)
4. **Поставить Caddy** (Windows: один .exe с caddyserver.com; Linux: пакет).

**Caddyfile** (рядом с caddy.exe), весь конфиг:
```caddy
gradebookai.ru {
    reverse_proxy 127.0.0.1:8000
}
```
Caddy сам выпустит сертификат, поднимет HTTPS и будет проксировать на ваш uvicorn
(`127.0.0.1:8000`). Реальный IP клиента он передаёт в `X-Forwarded-For` —
серверный анти-брутфорс это учитывает.

**Запуск:**
```bash
caddy run            # на переднем плане (проверить, что всё ок)
# боевой режим — службой, чтобы работала без открытого окна:
#   Windows:  caddy start   (или зарегистрировать как службу)
#   Linux:    systemctl enable --now caddy
```
После этого и десктоп, и будущий сайт указывают ОДИН адрес: `https://gradebookai.ru`.
Адрес сервера остаётся настройкой (вводится в самой программе либо зашивается в
`DEFAULT_API_URL`) — заказчик подставляет свой домен, в коде ничего не зашито.

**Только внутренняя ЛВС, без публичного домена?** Если сервер виден лишь внутри сети
колледжа, публичный сертификат не выпустить. Тогда сделайте **внутренний** сертификат
(Caddy умеет свой локальный CA, либо самоподписанный) и раздайте клиентам файл CA,
указав путь в переменной окружения `GRADEBOOK_CA_BUNDLE` рядом с прогой. Так https в
ЛВС заработает с включённой проверкой сертификата (без небезопасного отключения
проверки). При http к удалённому адресу прога честно предупреждает, что ПДн пойдут
открытым текстом.

### 7.7. Канал ГОСТ-TLS через ViPNet (для аттестации по УЗ-3)

Когда нужно. Для УЗ-3 передача ПДн по сети должна идти по защищённому каналу; если
внутренние регламенты (Минобрнауки/служба ИБ ВСГУТУ) требуют ОТЕЧЕСТВЕННОЙ криптографии
канала — это **ГОСТ-TLS на сертифицированном СКЗИ** (ViPNet / КриптоПро / Континент),
а не Let's Encrypt из 7.6. Это инфраструктурная задача; приложение к ней уже готово.

⚠️ Важное про архитектуру. **Обычный Python (`requests`/OpenSSL) НЕ умеет ГОСТ-TLS.**
Поэтому ГОСТ-TLS НЕ встраивается в код приложения — его терминирует СКЗИ снаружи, а
прога продолжает говорить по обычному TLS/localhost. Два рабочих варианта:

**А. Сетевой уровень (рекомендую, проще для десктопа).** ViPNet на обоих концах
(ViPNet Coordinator на шлюзе сервера + ViPNet Client на ПК пользователей) поднимает
защищённый ГОСТ-туннель на уровне сети. Внутри туннеля прога ходит как обычно
(`http(s)://внутренний-адрес`), а наружу всё идёт по ГОСТ. Приложение менять не надо.

**Б. ГОСТ-TLS терминатор перед сервером.** Сертифицированный шлюз (ViPNet TLS Gateway /
КриптоПро NGate) принимает ГОСТ-TLS снаружи и проксирует на `127.0.0.1:8000` (uvicorn).
Сервер слушает только localhost. Реальный IP клиента шлюз передаёт в `X-Forwarded-For`
(серверный анти-брутфорс это учитывает). На клиенте при этом тоже нужен ГОСТ-TLS
(ViPNet TLS Client / браузер с ГОСТ) — иначе соединение не установится.

Что уже сделано в коде для готовности к ГОСТ-TLS:
- TLS-проверка на клиенте всегда включена; свой (в т.ч. ГОСТ) корневой сертификат —
  через `GRADEBOOK_CA_BUNDLE`;
- сервер дружит с reverse-proxy (`X-Forwarded-For`), слушает один порт, легко уходит
  на localhost за терминатором.

> ГОСТ-TLS (канал) и ГОСТ-хеш (пароль) — РАЗНЫЕ вещи и решаются разными средствами.
> Канал — ViPNet/КриптоПро снаружи (этот раздел). Хеш — OpenSSL gost-engine на сервере
> (пакет `gost-engine` + строки `engine` в `openssl.cnf`); тогда `hashlib` увидит
> `streebog512` и наш ГОСТ-этап станет C-быстрым. ⚠️ Установка ViPNet CSP сама по себе
> hashlib НЕ ускоряет (он в Windows CryptoAPI, а не в OpenSSL Python'а). Проверить
> активный бэкенд хеша: `python diag_gost.py`.

## 8. Как «подключиться к этой штуке» (сводка точек доступа)

После запуска (локально или по публичному адресу `BASE`):
- `GET  BASE/health` — жив ли сервер.
- `GET  BASE/docs` — вся документация и ручная проверка из браузера.
- `POST BASE/auth/bootstrap-admin` — создать первого админа.
- `POST BASE/auth/login` — вход, отдаёт JWT.
- `GET  BASE/sync/pull?since=` — забрать изменения.
- `POST BASE/sync/push` — отправить изменения (нужен заголовок
  `Authorization: Bearer <токен>`).

Десктоп всё это делает сам: ты только задаёшь `api_url` и входишь логином/паролем.
