# 2. Текущее состояние GradeBookAI

## 2.1. Серверная часть

### Что сделано хорошо

### 1. SQLite настроен не в «голом» режиме

В `server/app/db.py` уже есть:

- WAL;
- `busy_timeout=5000`;
- `synchronous=NORMAL`;
- `temp_store=MEMORY`;
- адаптивный размер SQLite-кэша;
- SQLAlchemy-пул;
- `pool_pre_ping`;
- SQLCipher для боевой БД;
- запуск `PRAGMA optimize`/ANALYZE;
- индексы для горячих путей.

Это хорошая конфигурация для сервера с одной SQLite-базой и умеренной нагрузкой. SQLite в WAL-режиме позволяет читателям не блокировать друг друга и не блокировать запись на обычных операциях, но принципиальное ограничение остаётся: одновременно пишет только один writer. Это прямо описывает официальная документация [SQLite WAL](https://www.sqlite.org/wal.html).

То есть WAL не превращает SQLite в многописательную распределённую СУБД. Он улучшает конкуренцию чтения и записи, но не устраняет конфликт нескольких тяжёлых операций записи.

### 2. Синхронные тяжёлые маршруты не блокируют event loop напрямую

Многие messenger-endpoints объявлены обычным `def`, а не `async def`. FastAPI уводит синхронный обработчик в thread pool. Это спасает event loop от прямой блокировки.

Это особенно важно для:

- записи сообщения;
- проверки прав;
- работы с SQLite;
- формирования большого ответа;
- операций с вложениями.

Но здесь есть важная граница:

> Thread pool — не бесплатная параллельность.

Если одновременно придёт много запросов, они начнут занимать рабочие потоки и конкурировать за единственный SQLite writer. Поэтому переход на `def` решает проблему остановки event loop, но не решает:

- очередь потоков;
- блокировки SQLite;
- медленные запросы;
- чрезмерное количество запросов;
- большой объём сериализации.

### 3. Есть идемпотентность отправки

Использование `client_nonce` и проверки пары:

- conversation;
- sender;
- client nonce

защищает от дублей при:

- повторной отправке;
- сетевом retry;
- потере ответа POST;
- гонке WebSocket-события и HTTP-ответа.

На клиенте временное сообщение рисуется оптимистично, а затем подменяется настоящим по `client_nonce`. Это правильная модель для мессенджера.

### 4. WebSocket не пересылает полный текст сообщения каждому участнику

Сервер в основном рассылает сигнал вроде:

```json
{
  "type": "changed",
  "conversation_id": "..."
}
```

После этого клиент повторно забирает разрешённые данные через REST.

Это лучше, чем отправлять полное сообщение всем участникам напрямую:

- меньше риск нарушения ACL;
- меньше персональных данных в realtime-слое;
- проще контролировать видимость;
- WebSocket не становится вторым независимым API;
- сервер не должен держать сложное состояние сообщения в двух каналах.

Для GradeBookAI это особенно полезно из-за ролевого доступа и требований к ПДн.

### 5. История загружается курсорами

Есть:

- `before`;
- `after`;
- пагинация;
- догрузка старых сообщений;
- ограничение размера страницы;
- пропуск временных отрицательных id.

Это правильнее, чем каждый раз загружать всю историю беседы.

### 6. Поиск и AI-поиск не отправляют историю переписки целиком во внешнюю модель

Обычный поиск работает по локальным данным. AI-поиск использует модель только для расширения поискового запроса, а содержимое переписки не отправляет ей целиком.

Это хорошее решение с точки зрения приватности. Однако технически текущая реализация всё ещё может загрузить до 2000 текстовых сообщений и обрабатывать их в Python. Это означает, что при росте истории стоимость поиска будет зависеть не только от базы, но и от Python-фильтрации.

### 7. Отдельный online-only контур мессенджера

Мессенджер не входит в `SYNC_MODELS`. Это архитектурно правильно:

- оценки и учебные данные работают offline-first;
- переписка требует онлайн-семантики;
- не нужно пытаться синхронизировать сообщения через общий LWW-механизм;
- не появляется конфликт между «сообщение было удалено модератором» и локальной офлайн-копией.

Это одно из ключевых архитектурных решений проекта. Перенос messenger в Go не должен случайно смешать его с offline-first-частью.

## 2.2. Что ограничивает сервер сейчас

### 1. Процессное состояние остаётся главным ограничением

В `_common.py` WebSocket-реестр хранится примерно как:

```python
_by_user: dict[str, set]
```

Это состояние конкретного процесса.

Отсюда следствие:

- один процесс знает только о своих WebSocket;
- второй worker не знает о соединениях первого;
- broadcast между workers не работает автоматически;
- состояние presence, rate-limit, events и похожих подсистем нельзя оставлять только в памяти процесса.

Именно это, а не сам Python, сейчас определяет потолок горизонтального масштабирования.

FastAPI официально предупреждает: при запуске нескольких workers каждый процесс имеет отдельную память. В документации также показан типичный эффект: если один процесс держит модель размером 1 ГБ, четыре worker-процесса могут потребить около 4 ГБ. См. [FastAPI — Server Workers](https://fastapi.tiangolo.com/deployment/server-workers/) и [FastAPI — Deployment Concepts](https://fastapi.tiangolo.com/deployment/concepts/).

### 2. `_broadcast` — сигнал, но не журнал событий

Сейчас broadcast означает: «что-то изменилось, перечитай данные». Это нормально для небольшого числа клиентов, но это не durable event log.

Если worker или клиент был отключён:

- событие не обязательно можно воспроизвести;
- сервер не хранит подтверждённый cursor доставки;
- часть изменений приходится обнаруживать через polling или повторный запрос;
- reconnect не имеет полноценной гарантии replay.

Для мессенджера желательно разделить два понятия:

| Механизм | Назначение |
|---|---|
| WebSocket/SSE | быстро сообщить о событии |
| HTTP `after`/event cursor | восстановить пропущенные события |
| durable outbox/stream | не потерять событие между процессами и при сбое |

Сейчас первая и вторая части есть частично, а третья ещё не завершена.

### 3. Polling всё ещё нужен как страховка

В `livePolling.js` уже есть хорошая оптимизация:

- при живом WebSocket опрос редкий — около 30 секунд;
- без WebSocket fallback — около 3,5 секунды;
- скрытая вкладка не опрашивается;
- есть переподключение с backoff.

Это большой прогресс по сравнению с прежним поведением.

Но сам факт fallback означает, что при проблемах WebSocket нагрузка быстро увеличивается. Внутренний документ оценивает для 3000 пользователей сценарий примерно так:

- polling каждые 30 секунд — около 0,1 ядра в расчётной модели;
- fallback каждые 3,5 секунды — около 0,9 ядра только на polling-путь.

Это арифметическая оценка, а не live-замер. Но направление очевидно: устойчивый realtime-транспорт важнее, чем механическая замена Python на Go.

### 4. Поиск по переписке пока не является полнотекстовым индексом

Для кириллицы SQLite без ICU не даёт нужного поведения регистронезависимого поиска, поэтому часть поиска выполняется в Python.

Это понятно и корректно с точки зрения результата, но при больших чатах потенциально дорого.

Возможные варианты:

- нормализованный поисковый столбец;
- SQLite FTS5;
- отдельный индекс токенов;
- ограниченный индекс последних сообщений;
- асинхронный поисковый индекс.

Но индекс будет содержать ПДн. Поэтому его нельзя рассматривать только как техническую оптимизацию: он должен входить в тот же контур шифрования, резервного копирования, удаления и сроков хранения.

### 5. Сводка чата потенциально тяжёлая

`chat_summary` может:

- загрузить большое количество сообщений;
- собрать transcript;
- использовать AI;
- сохранить локальный кэш процесса.

Для длинных переписок лучше:

- ограничить размер входного окна;
- использовать предварительное резюме по сегментам;
- делать задачу асинхронной;
- кэшировать по стабильному cursor;
- не пересобирать сводку при каждом небольшом изменении;
- исключить пересылку чужих сообщений без явной политики доступа.

### 6. Thread pool может стать скрытым bottleneck

Если запись сообщения — обычный `def`, это правильно для event loop. Но при burst-нагрузке десятки запросов могут занять пул.

Нужно измерять отдельно:

- время ожидания thread pool;
- время SQL-запросов;
- время блокировки SQLite;
- время сериализации ответа;
- время broadcast;
- время push-уведомления;
- время внешнего AI-вызова;
- время обработки вложений.

Без этого переход на Go будет похож на замену диспетчера в аэропорту, где реальная очередь образуется на единственной взлётной полосе — в данном случае на SQLite write lock.

# 3. Desktop Edition

## 3.1. Что сделано хорошо

Десктопная архитектура сейчас существенно лучше, чем старый вариант с двумя UI:

- Vue SPA используется и в браузере, и внутри программы;
- локальный сервер поднимает тот же `server/app`;
- локальная SQLite/SQLCipher используется для offline-first;
- синхронизация вынесена в отдельный фоновой runner;
- UI не должен ждать завершения синхронизации;
- локальный API имеет persistent HTTP client для удалённых вызовов;
- messenger проксируется на удалённый сервер, но не пытается притворяться offline-first;
- локальные и удалённые данные разделены по смыслу.

Это правильное разделение:

```text
offline-часть:
WebView → local FastAPI → local SQLite → background sync

online messenger:
WebView → local proxy → remote API → remote DB
```

## 3.2. Основной desktop bottleneck

Для мессенджера на десктопе есть дополнительный сетевой hop:

```text
WebView2
   ↓
локальный FastAPI
   ↓
httpx
   ↓
Caddy/HTTPS
   ↓
боевой FastAPI
   ↓
SQLite
```

Этот hop добавляет:

- локальную обработку;
- локальный proxy;
- дополнительную сериализацию;
- дополнительную диагностику;
- потенциальное различие timeout-ов.

На хорошей сети это может быть незаметно. Но для пользователей с плохим каналом он ухудшает диагностику: пользователь видит «мессенджер не отвечает», хотя проблема может быть на любом из пяти звеньев.

Важно: перенос backend мессенджера на Go сам по себе не уберёт этот hop на десктопе. Его можно уменьшить только отдельным решением:

- локальный Go/WebSocket bridge;
- прямой WebSocket из WebView2 на боевой realtime endpoint;
- изменение desktop proxy;
- либо сохранение текущей схемы ради общей политики безопасности.

Пока нет замера, я бы не менял этот путь только ради теоретической экономии.

## 3.3. Почему нельзя переносить весь локальный сервер на Go

Локальный сервер десктопа — это не просто мессенджер. Он обслуживает:

- локальную БД;
- offline-first журнал;
- локальный вход;
- локальные настройки;
- расписание;
- Vector с локальными фактами;
- синхронизацию;
- security headers;
- WebView bridge;
- отдельную политику локальной сессии.

Полный перенос локального контура на Go означал бы:

- второй rewrite;
- вторую реализацию доступа к SQLite/SQLCipher;
- второй формат локальной сессии;
- повторную проверку поведения офлайн;
- повторную проверку шифрования;
- повторный аудит загрузки `.exe`;
- повторную проверку совместимости с WebView2.

Это слишком большой радиус изменения по сравнению с исходной задачей.

# 4. Web Edition

## 4.1. Сильные стороны

### Lazy loading

45 страниц загружаются лениво, а в initial bundle остаются только критичные компоненты:

- оболочка;
- вход;
- 404.

Это уже дало большой результат: внутренняя оценка показывает снижение первой загрузки примерно с 1,47 МБ до 347 КБ.

### WebSocket плюс HTTP reconciliation

Текущая модель разумная:

- WebSocket даёт быстрый сигнал;
- HTTP получает авторизованные данные;
- polling остаётся fallback;
- reconnect работает с backoff;
- скрытые вкладки не создают бессмысленную нагрузку.

### Оптимистическая отправка

Пользователь сразу видит своё сообщение, а серверная версия приходит позже. `client_nonce` предотвращает появление двух одинаковых сообщений.

### Параллельная загрузка чата

Начальная загрузка беседы больше не идёт длинной лестницей из семи последовательных `await`. Это важнее, чем декоративная анимация.

## 4.2. Что нужно проверить дополнительно

### Виртуализация ленты

В текущем просмотре я не увидел доказательства полноценной виртуализации длинной ленты сообщений. Это не означает, что её точно нет в нужной форме, но утверждать обратное нельзя.

Для чата с сотнями или тысячами сообщений нужно проверить:

- сколько DOM-узлов остаётся при открытии большой истории;
- как работает прокрутка;
- сколько времени занимает layout;
- сколько памяти занимает одна беседа;
- как ведёт себя лента после 10 000 сообщений;
- не пересоздаются ли все компоненты при каждом polling/reconnect;
- сохраняется ли позиция при догрузке старых сообщений.

Если виртуализации нет, это может стать более важным bottleneck, чем backend language.

### Payload списка чатов

Список чатов содержит достаточно много метаданных:

- unread;
- mention;
- last message;
- participants;
- avatars;
- permissions;
- status;
- pin/archive;
- системные признаки.

Нужно измерять:

- размер ответа списка;
- время JSON parse;
- время реактивного обновления Pinia;
- количество компонентов, перерисованных после одного изменения;
- размер ответа на 3000 пользователей;
- размер ответа на одного пользователя с 100–200 беседами.

### Reconnect storm

При падении realtime-транспорта одновременно могут переподключаться тысячи клиентов. Нужен отдельный тест:

- 1000 клиентов отключились одновременно;
- через 1–5 секунд сервер снова доступен;
- клиенты применяют backoff;
- сервер не создаёт лавину reconnect;
- polling не включается в полном объёме одновременно;
- Redis/stream не теряет события;
- старые подключения корректно закрыты.

Именно такие аварийные режимы регулярно оказываются дороже обычного steady state.

# 5. Внутренние реальные замеры проекта

Основной документ проекта — [PERF-SCALE-2026.md](<C:/Users/yaros/Desktop/WORK/GB_2_7/The-first-project-Student-Journal-/docs/PERF-SCALE-2026.md>).

## 5.1. Самый сильный результат: индекс, а не язык

На наборе примерно из 922 500 сообщений открытие чата дало:

| Сценарий | До | После | Эффект |
|---|---:|---:|---:|
| Открытие чата | 151,4 мс | 3,3 мс | примерно 46× |
| Запрос списка бесед преподавателя | 36,9 мс | 23,6 мс | примерно −36 % |
| Запрос списка бесед студента | 6,0 мс | 5,1 мс | небольшой эффект |
| Количество SQL-запросов в одном сценарии | 59 | 39 | примерно −34 % |

Причина главного ускорения — индекс по `messages.reply_to_id`. Один запрос раньше сканировал почти миллион строк.

Это очень важный результат для решения о Go:

> Если Python-обработчик за 3,3 мс получает тот же результат, который раньше строился за 151 мс из-за отсутствующего индекса, смена языка дала бы намного меньший эффект, чем изменение схемы БД.

Именно поэтому перед rewrite нужно профилировать не только язык и runtime, но и SQL-план.

## 5.2. Поведение списка бесед

Внутренний замер показывает, что оптимизация batch/point-запросов принесла заметный эффект для преподавателя:

- было около 36,9 мс;
- стало около 23,6 мс;
- число SQL-запросов уменьшилось с 59 до 39.

Это ещё один аргумент против немедленного полного rewrite: часть проблемы решается изменением формы доступа к данным.

## 5.3. Mention scan

В худшем сценарии сканирование упоминаний занимало около 30 % времени списка чатов. При коротком хвосте это было около 5–7 мс.

Это потенциальная область оптимизации, но текущий документ разумно не предлагает автоматически заводить новый индекс или сложную денормализацию. Сначала нужно подтвердить:

- частоту такого сценария;
- количество пользователей;
- реальную долю запросов;
- изменение при 3000–10 000 пользователях;
- влияние на запись;
- стоимость обслуживания счётчиков.

## 5.4. mmap и `PRAGMA optimize`

На шифрованной базе mmap дал небольшой эффект:

- примерно 4–7 %;
- около 1–3 мс в отдельных сценариях;
- только на более сильной машине.

Это полезная микрооптимизация, но не причина переписывать messenger.

## 5.5. Что пока не измерено

Наиболее важное ограничение текущего исследования:

не было полноценного теста:

- через Caddy;
- через HTTPS/TLS;
- с реальными HTTP-клиентами;
- с конкурентными WebSocket;
- с 1000–3000 одновременных соединений;
- с burst-отправкой;
- с reconnect storm;
- с двумя и более worker;
- с реальным Redis;
- с реальной задержкой сети;
- с измерением RSS каждого процесса.

Поэтому сейчас нельзя честно заявить:

- сколько RPS выдержит сервер;
- сколько одновременно живых соединений он держит;
- где production p95/p99;
- сколько пользователей безопасно обслужит один worker;
- даст ли Go существенную экономию.

# 6. Интервью

## 6.1. LinkedIn: realtime messaging и SSE

Ключевой источник — интервью InfoQ с Akhilesh Gupta, техническим лидером LinkedIn по realtime delivery и messaging:

[LinkedIn’s Real-Time Messaging Architecture — InfoQ Podcast](https://www.infoq.com/podcasts/linkedin-realtime-messaging-architecture/)

В интервью описана архитектура, где отдельно существуют:

- основная messaging-система;
- платформа realtime-доставки;
- подписки на topics;
- распределённое хранилище соответствий подписок;
- dispatcher;
- отдельный actor/объект на постоянное соединение;
- HTTP POST для действий клиента;
- EventSource/SSE для server-to-client доставки.

LinkedIn выбирал SSE, потому что в их сценарии поток в основном идёт от сервера к клиенту:

- новые сообщения;
- typing;
- seen receipts;
- presence;
- realtime-подсказки.

### Что это значит для GradeBookAI

У нас уже есть похожая модель:

```text
клиентское действие → HTTP
изменение на сервере → broadcast signal
клиент → повторный авторизованный GET
```

Теоретически можно заменить downstream WebSocket на SSE, если:

- клиент почти ничего не отправляет по realtime-каналу;
- typing можно отправлять отдельным HTTP/WS-путём;
- серверу нужен в основном односторонний downlink;
- есть reconnect cursor;
- есть безопасная аутентификация.

Но это не означает, что SSE автоматически лучше.

### Проблема SSE-аутентификации

Стандартный `EventSource` исторически неудобен для произвольного `Authorization` header. Нельзя просто бездумно перенести текущий JWT из WebSocket subprotocol в SSE.

Потребуется один из вариантов:

- короткоживущий одноразовый realtime-ticket;
- secure cookie;
- отдельная сессия realtime;
- URL-токен с очень коротким сроком и аккуратной защитой логов;
- специальный fetch-based SSE-клиент вместо обычного `EventSource`.

У нас уже есть важное решение: токен WebSocket уходит через `Sec-WebSocket-Protocol`, а не в query string, чтобы не попадать в access logs. Переход на SSE нельзя делать ценой возврата токена в URL.

### Вывод из интервью

Интервью LinkedIn поддерживает идею:

> Разделять REST/business API и realtime delivery полезнее, чем переписывать весь messaging domain.

Это хорошо совпадает с предлагаемой архитектурой Go-шлюза.

# 7. Реальные случаи

Здесь я разделяю реальные проблемы самого проекта и внешние production-кейсы.

## 7.1. Реальные случаи в GradeBookAI

### Случай 1: почти миллион строк из-за одного отсутствующего индекса

Открытие чата было около 151 мс, после индекса — 3,3 мс.

Это реальный показатель того, что:

- SQL-план был важнее языка;
- схема данных важнее framework overhead;
- query profiling необходимо делать до rewrite.

### Случай 2: polling создавал лишнюю нагрузку

При спокойном открытом чате прежняя модель давала около 9 запросов за 10 секунд на пользователя.

Затем были добавлены:

- редкий polling при живом WS;
- fallback только при отсутствии WS;
- hidden-tab suppression;
- reconnect;
- cursor-based updates.

Это классический пример, где архитектурная оптимизация транспорта сильнее, чем замена Python на Go.

### Случай 3: семь последовательных запросов при открытии чата

Это давало «лесенку»:

- сначала отображался ник;
- потом лента;
- потом закреплённые;
- потом участники;
- затем остальная информация.

На быстром стенде это выглядело терпимо, на боевом канале давало около 700 мс до полной картины.

Исправление было не в анимации, а в параллелизации. Это также не задача для смены языка.

### Случай 4: сообщение появлялось дважды

Причина:

- сообщение приходило по WebSocket раньше HTTP-ответа;
- клиент не мог сопоставить его с optimistic draft.

Решение:

- `client_nonce`;
- подмена временного объекта настоящим;
- автор получает nonce, чужим участникам он не нужен.

Это пример, когда корректность протокола важнее raw performance.

### Случай 5: процессное состояние не даёт сразу включить workers

В памяти процесса находятся:

- WebSocket registry;
- части live state;
- некоторые throttle/presence/event-механизмы;
- состояние, связанное с realtime.

Запуск нескольких workers без общей координации приведёт к частично работающему мессенджеру: пользователь подключён к одному процессу, событие пришло в другой.

Поэтому текущий незакоммиченный [PLAN-MULTIWORKER.md](<C:/Users/yaros/Desktop/WORK/GB_2_7/The-first-project-Student-Journal-/docs/PLAN-MULTIWORKER.md>) идёт в правильном направлении: сначала вынести process-local state, потом разрешать workers.

## 7.2. Discord: массовое хранение сообщений

Официальный инженерный разбор Discord:

[How Discord Stores Trillions of Messages](https://discord.com/blog/how-discord-stores-trillions-of-messages)

Discord описывает переход:

- от MongoDB;
- к Cassandra;
- затем к большим распределённым кластерам;
- с partitioning по каналу и временным bucket;
- с проблемами hotspot partition;
- с огромной operational cost;
- с необходимостью менять модель хранения по мере роста.

В статье приводятся исторические масштабы: от десятков узлов до сотен узлов и триллионов сообщений.

### Что переносимо к нам

Переносимая идея не в Cassandra. У нас нет масштаба Discord и нет основания добавлять такую систему.

Переносима другая мысль:

> Хранилище сообщений должно проектироваться вокруг реальных шаблонов чтения, а не вокруг моды на конкретную СУБД.

Для GradeBookAI это означает:

- открыть последние сообщения;
- догрузить историю назад;
- найти сообщения в беседе;
- получить thread;
- определить unread;
- выдать signal после записи.

Пока для этих сценариев текущая SQLite-схема уже показывает хорошие результаты после индексации.

## 7.3. Discord: WebSocket-трафик −40 %

Официальный инженерный кейс:

[How Discord Reduced WebSocket Traffic by 40 Percent](https://discord.com/blog/how-discord-reduced-websocket-traffic-by-40-percent)

Discord обнаружил, что для маленьких realtime-сообщений более тяжёлое сжатие не всегда выгоднее. В конкретном сценарии zlib давал меньший payload, чем zstd, из-за особенностей streaming compression и истории словаря.

### Урок для GradeBookAI

Нельзя говорить:

- «zstd современнее, значит обязательно лучше»;
- «Go WebSocket-библиотека быстрее, значит трафик уменьшится»;
- «включим compression и получим бесплатный выигрыш».

Нужно измерять:

- средний размер события;
- распределение размеров;
- CPU compression;
- долю маленьких сообщений;
- влияние на мобильные устройства;
- расход батареи;
- длительность соединения.

Наши realtime-сигналы маленькие. Возможно, сжатие для них вообще невыгодно.

## 7.4. Discord: миллион пользователей в одном сервере

Инженерный разбор:

[Maxjourney: Pushing Discord’s Limits with a Million-plus Online Users](https://discord.com/blog/maxjourney-pushing-discords-limits-with-a-million-plus-online-users-in-a-single-server)

Discord описывает модель:

- процесс на guild;
- отдельные session на подключённых пользователей;
- fanout через процесс guild;
- условную доставку с учётом прав.

### Что это показывает

Масштаб realtime определяется не только числом TCP/WebSocket-соединений. Важны:

- ownership состояния;
- маршрутизация;
- ACL;
- fanout;
- backpressure;
- graceful shutdown;
- межпроцессная передача.

Для GradeBookAI это аргумент в пользу отдельного realtime-слоя, но не в пользу копирования Discord.

## 7.5. Discord: авария Stateful Realtime

Инженерный разбор аварии:

[Behind the Scenes of the 3/25/26 Voice Outage](https://discord.com/blog/behind-the-scenes-of-the-3-25-26-voice-outage)

В аварии каскад возник из-за сочетания:

- потери части сессий;
- stateful-модели;
- изменения количества pod;
- недостаточно безопасного handoff;
- проблем с termination grace;
- неудачного поведения при deployment.

### Урок для Go

Go не устраняет проблемы:

- state handoff;
- reconnect storms;
- graceful shutdown;
- drain;
- потерянных подписок;
- повторной регистрации;
- backpressure;
- рассинхронизации workers.

Если мы вынесем realtime в Go, необходимо сразу проектировать:

- `/health/ready`;
- `/health/live`;
- graceful drain;
- отказ от новых соединений во время остановки;
- закрытие старых соединений с корректным retry;
- сохранение cursor;
- replay после reconnect;
- измерение dropped events.

- блокировкой SQLite;
- reconnect storm;
- внешним AI;
- Caddy;
- сетью;
- запросом без индекса,

то переписывание runtime не устранит хвост.

## 8.4. SQLite как серверная база

Официальная документация отдельно отмечает, что SQLite может быть быстрой server-side БД, если доступ к ней корректно сериализован.

### Что это значит для нас

- сообщения не синхронизируются между десктопами;
- большая часть операций — чтение последних данных и короткие записи.

Переход на Go, но с той же SQLite, не уберёт ограничение одного writer.

# 11. Авторитетные источники и официальная документация

В этой категории я использовал первичные или максимально близкие к первичным материалы.

## 11.1. SQLite

- [SQLite WAL](https://www.sqlite.org/wal.html)
- [Appropriate Uses For SQLite](https://www.sqlite.org/whentouse.html)

Факты:

- WAL улучшает одновременное чтение и запись;
- reader не блокирует reader;
- writer всё равно один;
- WAL рассчитан на процессы на одной машине;
- нельзя бездумно использовать WAL через network filesystem;
- SQLite может быть server-side базой при корректной сериализации записи.

## 11.2. Go

- [Go pprof](https://go.dev/blog/pprof)
- [Go Execution Traces](https://go.dev/blog/execution-traces-2024)
- [Go Performance Wiki](https://go.dev/wiki/Performance)
- [Managing Connections — Go database/sql](https://go.dev/doc/database/manage-connections)
- [Accessing relational databases — Go](https://go.dev/doc/database/)

Официальная документация Go отдельно предупреждает:

- `sql.DB` — это пул соединений, а не одно соединение;
- `MaxOpenConns` нужно ограничивать;
- неправильный pool может привести к блокировкам или deadlock;
- база может стать узким местом независимо от эффективности Go;
- профилирование нужно проводить на workload, близком к реальному.

Это очень важно для возможного Go-сервиса поверх SQLite: нельзя открыть неограниченный пул и считать, что goroutines автоматически ускорят запись. Это может даже увеличить конкуренцию за SQLite writer.

## 11.3. FastAPI и workers

- [FastAPI Server Workers](https://fastapi.tiangolo.com/deployment/server-workers/)
- [FastAPI Deployment Concepts](https://fastapi.tiangolo.com/deployment/concepts/)
- [FastAPI Benchmarks](https://fastapi.tiangolo.com/benchmarks/)

Факты:

- один процесс может одновременно обслуживать множество клиентов;
- workers позволяют использовать несколько CPU;
- память процесса не разделяется;
- глобальные объекты не синхронизируются автоматически;
- benchmark framework не равен benchmark бизнес-приложения.

## 11.4. Redis Pub/Sub и Streams

- [Redis Pub/Sub](https://redis.io/docs/latest/develop/interact/pubsub/)
- [Redis Streams](https://redis.io/docs/latest/develop/data-types/streams/)
- [Redis Streaming Use Case](https://redis.io/docs/latest/develop/use-cases/streaming/)

Redis Pub/Sub использует at-most-once semantics. Если подписчик отключился, сообщение может быть потеряно.

Redis Streams дают:

- ordered append-only entries;
- cursor;
- replay;
- consumer groups;
- ACK;
- возможность удерживать ограниченное окно истории.

### Что это значит для нас

Для мессенджера нельзя использовать Redis Pub/Sub как единственную гарантию доставки.

Правильнее:

```text
SQLite transaction:
  message insert
  outbox event insert

background publisher:
  outbox → Redis Stream

realtime gateway:
  Stream → connected clients

client:
  event cursor
  HTTP backfill after reconnect
```

В Redis лучше отправлять не тело сообщения, а минимальный сигнал:

```json
{
  "event_id": "evt-...",
  "conversation_id": "...",
  "kind": "message_changed"
}
```

Тело сообщения клиент получает через уже существующий авторизованный REST API. Это снижает риск утечки ПДн в realtime-инфраструктуре.

## 11.5. SSE

Стандарт:

[WHATWG Server-Sent Events](https://html.spec.whatwg.org/multipage/server-sent-events.html)

SSE поддерживает:

- `EventSource`;
- `text/event-stream`;
- reconnect;
- `Last-Event-ID`;
- server-to-client push.

Для GradeBookAI SSE может быть удобен для:

- новых сообщений;
- unread;
- mention;
- presence;
- системных событий;
- обновления списка чатов.

Но отдельный клиентский канал для typing может остаться на WebSocket или HTTP.

Главная техническая проблема — безопасная аутентификация SSE без возврата к JWT в URL.

## 11.6. OpenTelemetry

- [OpenTelemetry General Semantic Conventions](https://opentelemetry.io/docs/specs/semconv/general/)
- [OpenTelemetry Trace Semantic Conventions](https://opentelemetry.io/docs/specs/semconv/general/trace/)

OpenTelemetry особенно полезен при переходе к нескольким языкам. Он позволит связать в одну трассу:

```text
browser
  → local desktop proxy
  → Caddy
  → Python REST
  → SQLite
  → Redis Stream

```

При этом нельзя включать в span attributes:

- ФИО;
- текст сообщения;
- полный JWT;
- email;
- содержимое переписки;
- необезличенный IP, если он не нужен для конкретной цели.

Нужно использовать:

- request id;
- event id;
- технический endpoint;
- role class;
- status code;
- duration;
- message kind;
- размеры payload;
- hashed/low-cardinality identifiers.

# 12. Сравнение Python и Go именно для этого проекта

| Область | Текущий Python | Потенциальный Go | Реальный вывод |
|---|---|---|---|
| HTTP REST | Уже работает, бизнес-логика в одном месте | Может быть быстрее на простых ручках | Для наших сложных ручек benchmark важнее языка |
| WebSocket | Работает в одном процессе | Удобен для большого числа соединений | Нужно измерять memory/connection и delivery p99 |
| SSE | Можно добавить | Удобен для большого server-to-client потока | Сначала решить auth и replay |
| CPU serialization | Может быть заметной | Обычно ниже overhead | Проверять pprof/py-spy, а не предполагать |
| SQLite | Один writer | Один writer останется | Go не устранит DB lock |
| SQLAlchemy | Даёт удобство, но overhead | `database/sql` проще и быстрее в некоторых сценариях | Не поможет, если bottleneck — плохой SQL-план |
| Память соединений | Нужно измерять | Часто может быть выгоднее | Нужен одинаковый concurrent benchmark |
| Process state | Нельзя сразу workers | В Go тоже будет process-local state | Язык не решает shared state |
| Security/ACL | Уже реализованы и протестированы | Нужно реализовать заново | Главный риск полного rewrite |
| Deploy | Один Python application | Новый процесс и новый artifact | Увеличение операционной сложности |
| Observability | Нужно усилить | Можно сразу pprof + OTel | Полезно только при единой трассировке |
| Rollback | Текущий путь уже известен | Новый gateway можно откатить отдельно | Частичный rollout значительно безопаснее |

## Что Go, вероятно, даст

Потенциальные преимущества:

- меньше памяти на большое число лёгких соединений;
- удобная модель goroutine;
- быстрый сетевой IO;
- простой profiling;
- хорошая модель graceful shutdown;
- удобный отдельный realtime service;
- меньше зависимости от Python thread pool для connection management.

## Чего Go не даст автоматически

Go сам по себе не исправит:

- отсутствующий индекс;
- плохой SQL;
- единственный SQLite writer;
- слишком частый polling;
- отсутствие durable outbox;
- потерю событий при reconnect;
- неправильный ACL;
- длинную AI-операцию;
- сетевую задержку;
- размер payload;
- отсутствие виртуализации DOM;
- плохой desktop proxy;
- неправильную семантику удаления сообщений.

# 14. Как именно сделать межпроцессное состояние

## 14.1. Не использовать Redis Pub/Sub как единственную доставку

Для критичных событий:

- публикация сообщения;
- edit;
- delete;
- mention;
- system event;
- channel update

нужен outbox/stream.

Пример:

```text
BEGIN
  INSERT INTO messages (...)
  INSERT INTO messenger_outbox (
      event_id,
      conversation_id,
      kind,
      message_id,
      created_at
  )
COMMIT
```

Только после commit outbox publisher отправляет event в Redis Stream.

Так сообщение и событие не расходятся:

- сообщение записано, но event не потерян;
- event не указывает на несуществующее сообщение;
- publisher может повторить отправку;
- gateway может использовать idempotent обработку.

## 14.2. Не передавать текст сообщения в Redis без необходимости

Для первого этапа Redis event должен содержать:

- `event_id`;
- `conversation_id`;
- `message_id`;
- `kind`;
- технический timestamp.

Не нужно передавать:

- body;
- ФИО;
- email;
- attachment URL;
- полный список участников.

Клиент получает данные через авторизованный REST endpoint. Это сохраняет существующую ролевую модель.

## 14.3. Нужен event cursor

Сейчас `after=<message_id>` используется как cursor для сообщений. Для полноценного realtime лучше иметь отдельный monotonically increasing `event_id` или sequence.

Причина: события могут относиться к старому сообщению:

- edit старого сообщения;
- delete старого сообщения;
- reaction;
- report;
- moderation event.

Если cursor основан только на последнем message id, старое изменённое сообщение не всегда удобно обнаружить через обычный `after`.

Возможные решения:

- отдельная таблица `messenger_events`;
- sequence в outbox;
- event id, монотонный в рамках conversation;
- глобальный stream cursor;
- HTTP `after_event`.

# 16. Когда полный перенос messenger на Go будет оправдан

Я бы разрешил полный rewrite только при одновременном выполнении условий.

## Условие 1: есть настоящий benchmark

Нужно сравнить текущий Python и Go-кандидат на одинаковом workload:

- 1000/3000/10 000 открытых соединений;
- 10/100/500 отправок в секунду;
- 200-участниковая беседа;
- личные чаты;
- группы;
- каналы;
- reconnect storm;
- edit/delete/reaction;
- mention;
- unread;
- поиск;
- список чатов;
- TLS через Caddy;
- desktop proxy;
- Redis;
- SQLite;
- synthetic data без реальных ПДн.

## Условие 2: измерены p95 и p99

Не только average.

Минимальный набор:

| Метрика | Что сравнивать |
|---|---|
| Send p50/p95/p99 | от HTTP POST до ответа |
| Delivery p50/p95/p99 | от commit до сигнала клиенту |
| Open chat p50/p95/p99 | от запроса до полной ленты |
| RSS | на 1000/3000/10 000 соединений |
| CPU | idle, steady state, burst |
| SQLite lock wait | среднее и p99 |
| Thread/goroutine wait | очередь обработки |
| reconnect time | после падения gateway |
| dropped events | абсолютное число |
| duplicate events | абсолютное число |
| Redis lag | consumer lag |
| payload bytes | downstream traffic |

## Условие 3: доказано, что bottleneck — именно Python

Например:

- CPU Python serialization занимает больше 50 % времени;
- DB time занимает менее 20 %;
- Redis и Caddy не доминируют;
- HTTP overhead значителен;
- memory per connection существенно хуже;
- Go-кандидат сохраняет тот же SQL и показывает устойчивый выигрыш на p99.

Если же 60–80 % времени занимает:

- SQLite;
- SQLAlchemy query;
- lock wait;
- внешний service;
- сеть,

то полный rewrite будет дорогим обходом проблемы.

## Условие 4: есть контрактные тесты паритета

Нужно проверять обе реализации:

- одинаковая авторизация;
- одинаковый ACL;
- одинаковый список видимых сообщений;
- одинаковое поведение mute;
- одинаковые edit/delete semantics;
- одинаковые `client_nonce`;
- одинаковые timestamps;
- одинаковая обработка forbidden;
- одинаковое поведение reconnect;
- одинаковый формат event;
- одинаковая идемпотентность.

Не включать в telemetry:

- тело сообщения;
- ФИО;
- email;
- JWT;
- полный URL с токеном;
- необезличенный текст запроса.

## Приоритет P1 — закончить durable events

Сначала:

- transactional outbox;
- event id;
- retry publisher;
- Redis Streams;
- replay;
- bounded retention;
- HTTP backfill;
- idempotent consumer.

Это даст больше архитектурной пользы, чем немедленный rewrite.

## Приоритет P1 — закончить shared state

Доделать:

- rate-limit;
- presence;
- canary state;
- connect state;
- events;
- WebSocket cross-process broadcast;
- graceful degraded behavior.

После этого включать второй worker только на staging.

## Приоритет P2 — оптимизировать данные

Проверить:

- SQL `EXPLAIN QUERY PLAN`;
- большие списки;
- поиск;
- summary;
- unread;
- mention;
- reactions;
- replies;
- cursor updates;
- размер JSON;
- виртуализацию Vue-ленты.

## Приоритет P2 — прототип Go gateway

Сделать минимальный Go-сервис только для:

- `/realtime`;
- WebSocket или SSE;
- health;
- pprof;
- OTel;
- Redis Stream consumer;
- graceful drain.

Не переносить сразу:

- регистрацию;
- login;
- MFA;
- message writes;
- moderation;
- attachments;
- admin;
- roles.

## Приоритет P3 — A/B и canary

Схема rollout:

```text
Caddy:
  /realtime-go → Go gateway
  /web/messenger → Python REST

feature flag:
  1 % клиентов → Go
  10 %
  25 %
  50 %
  100 %
```

На каждом этапе:

- сравнить p95/p99;
- проверить duplicate events;
- проверить lost events;
- проверить reconnect;
- проверить desktop;
- проверить mobile;
- проверить privacy logs;
- проверить graceful shutdown.

Откат должен быть простым: вернуть realtime route на Python или отключить Go endpoint.

# 18. Что я не рекомендую

## Не рекомендую полный rewrite «потому что Go быстрее»

Это слабое основание. Наши собственные замеры уже показали:

- 46× выигрыш от индекса;
- заметный выигрыш от уменьшения числа SQL-запросов;
- большая часть текущей проблемы связана с архитектурой состояния и transport fallback.

## Не рекомендую сразу переносить БД сообщений в Redis

Redis не должен быть canonical message storage:

- сообщения должны переживать рестарт;
- нужна модерация;
- нужна история;
- нужны backup;
- нужна SQL-выборка;
- нужны retention/deletion semantics;
- нужны audit guarantees.

Redis подходит как event/state layer, не как автоматическая замена БД.

## Не рекомендую сразу возвращать PostgreSQL только ради Go

Проект сознательно удалил непроверенную PostgreSQL-ветку. Возвращать её нужно только при доказанной необходимости:

- SQLite write contention;
- многопроцессная запись;
- распределённый deployment;
- реальная потребность в concurrent writers.

Если это понадобится, решение должно быть отдельным архитектурным проектом, а не побочным эффектом Go rewrite.

## Не рекомендую включать workers до shared state

Несколько процессов с process-local WebSocket registry дадут частично рабочий, трудно диагностируемый мессенджер.

## Не рекомендую SSE без новой модели authentication

Нельзя ради простоты перейти от WebSocket subprotocol к JWT в URL. Нужно заранее спроектировать ticket/cookie/session.

## Не рекомендую ориентироваться на BigTech как на прямой blueprint

Discord и LinkedIn решают задачи:

- миллионы соединений;
- сотни тысяч RPS;
- многорегиональные кластеры;
- десятки инженеров эксплуатации;
- отдельные команды хранения и realtime.

У GradeBookAI другой масштаб, один сервер, SQLite, юридические ограничения и требования к простоте переезда.

# 19. Итоговое решение

Мой итоговый рейтинг вариантов:

| Вариант | Оценка |
|---|---|
| Полностью переписать messenger на Go сейчас | Не рекомендую |
| Оставить всё как есть | Тоже не рекомендую |
| Сначала индексы, payload, outbox, shared state, benchmark | Обязательно |
| Вынести realtime gateway на Go | Перспективно |
| Оставить Python REST и БД | Рекомендую на первом этапе |
| Перенести в Go только после доказанного bottleneck | Да |
| Сразу переносить сообщения в новую БД | Только после отдельного capacity/legal проекта |
| Kubernetes ради масштабирования | Пока не нужен |
| Redis Pub/Sub как единственный event transport | Нельзя |
| Redis Streams + outbox + HTTP backfill | Рекомендую |

Формула решения:

```text
Сначала:
  измеряем → устраняем SQL/polling/state bottleneck
  → делаем durable events
  → разрешаем multi-worker
  → строим Go gateway
  → сравниваем A/B

Только если:
  Python CPU/память/serialization остаются главным bottleneck
  → переносим больше домена на Go
```

То есть Go в проекте имеет смысл, но его правильная роль сейчас — не «новый весь messenger», а:

> отдельный быстрый и наблюдаемый realtime-транспорт поверх уже проверенной Python-бизнес-логики.

Это даст нам возможность получить преимущества Go, не переписывая заново наиболее чувствительную часть продукта: роли, ПДн, модерацию, историю сообщений, вложения, удаление, уведомления и аудит.
