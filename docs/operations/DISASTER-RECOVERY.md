# Восстановление после аварии (DR)

> Сверено с кодом 27.09.2026 (Release 4.1). Для администратора сервера. Пути даны для
> текущего VPS (`/root/gb-deploy`); на машине, поставленной `deploy/install.sh`, код в
> `/opt/gradebook`, база в `/var/lib/gradebook`.

## 1. Что у нас есть и сколько можно потерять

| что | как | где |
|---|---|---|
| снимок базы | `deploy/backup/gb_backup.sh`, раз в сутки в 00:00 по Улан-Удэ, 14 штук, сам себя проверяет (`integrity_check` + счёт пользователей) | `/root/gb-backups/auto/`, журнал `/var/log/gb-backup.log` |
| ключ базы | `GRADEBOOK_DB_KEY` в `server/.env` (или учётных данных systemd) | **копия обязана лежать вне машины**: без ключа снимок бесполезен |
| код и сайт | неизменяемый архив `tools/build_release.py` | собирается заново из репозитория |
| файлы обновлений | `server/ota_bundles/`, `downloads/` | в снимок базы **не входят**; выкладываются заново из сборок |

**Точка восстановления — до суток.** Правки, принятые сервером после последнего снимка,
пропадают и с сервера, и из копий программ (они пересоберутся по восстановленной базе).
Правки, которые на момент аварии ещё ждали отправки (очередь программы и телефона),
досылаются сами — с проверкой версии клетки, конфликт решает человек.

⚠️ **`deploy/install.sh` таймер копий НЕ ставит** (проверено 22.09.2026). Новая машина
без ручного шага из `deploy/backup/README.md` работает без резервных копий молча.
Первым делом после установки — поставить таймер и посмотреть его журнал.

⚠️ Все копии — на той же машине, что и база. Потеря диска = потеря копий. Единственный
воздушный зазор сейчас — ручная копия у ответственного; снимать её регулярно.

## 2. Проверить копию, не трогая боевую базу

Копия, из которой ни разу не восстанавливались, — надежда, а не копия. Проверка идёт на
временном файле:

```bash
TMP=$(mktemp -d); cp "$(ls -1t /root/gb-backups/auto/gradebook_*.db | head -1)" "$TMP/r.db"
export GB_KEY=$(grep -E '^GRADEBOOK_DB_KEY=' /root/gb-deploy/server/.env | cut -d= -f2- | tr -d "\"'\r")
/root/gb-deploy/venv/bin/python - "$TMP/r.db" <<'PY'
import os, sys, sqlcipher3
c = sqlcipher3.connect(sys.argv[1])
c.execute("PRAGMA key = \"x'%s'\"" % os.environ["GB_KEY"])
print("integrity:", c.execute("PRAGMA integrity_check").fetchone()[0])
print("users:", c.execute("SELECT COUNT(*) FROM users").fetchone()[0])
PY
rm -rf "$TMP"
```

🔥 Ключ подаётся как raw-hex (`x'…'`), а не паролем. Поданный строкой, он «не откроет»
файл, и это выглядит ровно как испорченная копия. `PRAGMA key` сам ничего не проверяет —
ошибка всплывает на первом чтении.

## 3. Восстановление на той же машине

```bash
systemctl stop gradebook
cd /root/gb-deploy/server
mkdir -p /root/gb-backups/broken-$(date +%F-%H%M)
mv gradebook_server.db* /root/gb-backups/broken-$(date +%F-%H%M)/    # не удалять: разбор
cp /root/gb-backups/auto/gradebook_<ДАТА>.db gradebook_server.db
chmod 600 gradebook_server.db
../venv/bin/python -m app.sync_clock --new-epoch     # ОБЯЗАТЕЛЬНО, см. ниже
systemctl start gradebook
curl -sS -o /dev/null -w '%{http_code}\n' https://<домен>/health   # ждём 200
../venv/bin/python verify_audit.py                                 # цепочка журнала
```

🔑 **`--new-epoch` обязателен.** Программы и сайт качают изменения по номеру изменения
(`change_seq`). После отката номера выдаются заново, и курсор, сохранённый у программы до
аварии, указывал бы на чужие правки. Новая метка базы заставляет каждую копию программы
пересобраться целиком (`server/app/sync_clock.py::new_epoch`). Забыть этот шаг — получить
копии, которые молча расходятся с сервером.

После восстановления журнал безопасности короче, чем контрольная точка, снятая до аварии
(`verify_audit.py --checkpoint`, хранится вне машины): это ожидаемо — записи после снимка
пропали вместе с базой. Подделкой это не является; зафиксировать в акте, сколько записей
потеряно.

## 4. Восстановление на новой машине

```bash
sudo bash deploy/install.sh --domain <домен> --restore-db /путь/gradebook_<ДАТА>.db
```

Установщик требует `server/.env` рядом с базой: новый ключ поверх привезённой базы — это
потеря данных навсегда, поэтому без `.env` он отказывает (код 3). Дальше — шаги
`--new-epoch`, проверка `/health`, `verify_audit.py` из §3, таймер копий из §1 и
переключение A-записи домена (скрипт этого не делает). Старую машину не выключать, пока
домен не заработал с новой.

## 5. Что происходит у людей

| где | что увидят |
|---|---|
| программа на ПК | при следующей синхронизации копия пересоберётся с сервера целиком; неотправленные правки досылаются по одной; если клетку за это время изменили — в «Что не ушло» появится выбор «своё / серверное» |
| телефон и сайт | то же для очереди оценок: конфликт — в «не принято» с выбором |
| все | правки последних часов до аварии (после снимка) придётся внести заново; предупредить преподавателей, какой период проверить |

## 6. Учения

Раз в семестр: §2 на свежей копии и §4 на отдельной машине с выдуманными данными
(`tools/smoke_release.py --stay`). Копию боевой базы на машину разработчика не
переносить — это запрещено п. 5.2.4.1 политики ВСГУТУ, а не просто неудобно.
