# Передача сопровождения

> Сверено с кодом 27.09.2026 (Release 4.1), раздел 3 — 14.10.2026. Для администратора ВСГУТУ, который принимает
> сервер, и для команды, которая его передаёт. Поля `<…>` заполняются при передаче.

## 1. Кто за что отвечает

| зона | ответственный | контакт |
|---|---|---|
| сервер, копии, ключи базы | `<администратор ВСГУТУ>` | `<…>` |
| выпуск обновлений (программа, телефон, сайт) | `<…>` | `<…>` |
| оператор ПДн, уведомления в РКН | ответственный за ПДн ВСГУТУ | `<…>` |
| разработчик (по договору) | команда Synapse | `<…>` |

Доступ разработчика к боевой машине — только по договору поручения (п. 5.2.4.1 политики
ВСГУТУ). Без договора разработчик консультирует, а команды выполняет администратор.

## 2. Что передаётся

- [ ] исходный код и архив выпуска (`tools/build_release.py`, хеши в манифесте);
- [ ] `server/.env` или учётные данные systemd — **лично, не почтой**; копия ключа базы
      запечатанной вне машины;
- [ ] закрытые ключи подписи обновлений (`release_signing_key.hex`, `ota_signing_key.pem`)
      и `release.keystore` — если выпуск обновлений переходит к вузу;
- [ ] доступ к аккаунту RuStore (приложение `ru.esstu.gradebook`);
- [ ] список внешних сервисов и их ключей — [SUBPROCESSORS.md](../security/SUBPROCESSORS.md);
- [ ] эти документы: [KEY-ROTATION.md](KEY-ROTATION.md),
      [DISASTER-RECOVERY.md](DISASTER-RECOVERY.md),
      [INCIDENT-RESPONSE.md](../security/INCIDENT-RESPONSE.md),
      [PDN-MODEL.md](../security/PDN-MODEL.md).

В день передачи: SSH-ключи прежней команды убираются из `authorized_keys`, пароли
административных учётных записей меняются (см. [KEY-ROTATION.md](KEY-ROTATION.md) §9).

## 3. Ежедневно и еженедельно

```bash
systemctl status gradebook caddy --no-pager            # обе active
curl -sS -o /dev/null -w '%{http_code}\n' https://<домен>/health     # 200
tail -3 /var/log/gb-backup.log                          # последняя строка — OK за сегодня
ls -lt /root/gb-backups/auto/ | head -3                 # копии в auto/, а НЕ в корне
df -h /                                                 # при нехватке места копия пропускается
journalctl -u gradebook -n 50 --no-pager                # предупреждения старта
```

Раз в неделю: `python server/verify_audit.py` (цепочка журнала безопасности), контрольную
точку `--checkpoint` — записать вне машины. Раз в семестр — учения из
[DISASTER-RECOVERY.md](DISASTER-RECOVERY.md) §6.

### Что сервер делает сам (ночь по Улан-Удэ, проверено 14.10.2026)

| когда | что | где настроено |
|---|---|---|
| каждую ночь, 00:00 | зашифрованный снимок базы с проверкой, хранится 14 | `deploy/backup/` |
| каждую ночь, 02:00 | исправления безопасности ОС; перезагрузка, если её требует ядро или libc | `deploy/maintenance/52gradebook-unattended`, drop-in таймера `apt-daily-upgrade` |
| ночь на воскресенье, 03:30 | уборка кэшей: скачанные пакеты, кэш pip, OTA-бандлы кроме текущего и трёх прежних | `deploy/maintenance/gb_cleanup.sh` + `gb-cleanup.timer` |
| раз в месяц | ротация журналов наших скриптов (`gb-backup.log`, `gb-cleanup.log`), год истории | `deploy/maintenance/logrotate-gradebook` |
| каждый час | уязвимости пакетов Python, ОС и Caddy по OSV и CISA KEV, исправление сразу с откатом | `deploy/vulnwatch/` |
| постоянно | письмо сразу: чужой вход на сервер, упавшая служба, правка ключей и учёток, приманка; журнал или сайт молчат 3 минуты — перезапуск и письмо | `deploy/alarm/` (служба `gb-alarm`) |
| при падении | Caddy поднимается сам через 3 секунды (у пакетного юнита `Restart=no`) | `deploy/maintenance/caddy-restart.conf` |
| ночь на воскресенье, 04:00 | все обновления ОС, не только безопасности; перезагрузка, если нужна | `deploy/maintenance/gb_os_update.sh` + `gb-os-update.timer` |
| воскресенье, 05:00 | учения: свежая копия базы поднимается рядом с боем на :8091 и проверяется | `deploy/backup/gb_restore_drill.sh` + `gb-drill.timer` |
| при входе в Windows и каждые 6 ч | ПК администратора забирает ночную копию (и секреты под DPAPI) в `D:\GradeBookAI-backups` | `tools/server-buttons/offsite_pull.ps1`, `deploy/backup/gb_offsite.sh` |
| первый запрос к `.php`, `wp-admin`, `.env` | бан на сутки (только 80/443); вернулся в течение недели — бан на неделю | `server/deploy/infra/` (fail2ban `caddy-scanner`, `gb-scanner-week`) |
| при нехватке памяти | первыми гибнут разовые задачи, последними — журнал, Caddy, ssh, сторож | `deploy/maintenance/oom/` |
| пуш в `Release-*`, всё зелёное | автодеплой проверенного архива, смоук и откат на сервере, письмо | `deploy/ci/README.md` |
| каждые 15 минут | GitHub проверяет `/health` снаружи | `.github/workflows/uptime.yml` (работает с ветки по умолчанию) |

Руками, когда нужно (их же зовут кнопки на рабочем столе, `tools/server-buttons/install.py`):
`deploy/maintenance/gb_maintenance.sh on|off` — жёсткий рубильник работ,
`deploy/maintenance/gb_restart.sh [all|reboot]` — рестарт с проверкой,
`deploy/backup/gb_restore.sh list | db N | code` — база из копии или прежняя выкладка. На бою
все три лежат в `/root/gb-deploy/maintenance/`.

Прежние OTA-бандлы — только запись того, что стояло на телефонах: откатиться на них
правкой `latest.json` нельзя (он подписан, а телефон не ставит бандл не новее своего).
Откат телефонов — выпуск нового номера из нужного коммита.

Журнал systemd ограничен в `journald.conf` (`SystemMaxUse`), журнал доступа Caddy — в
самом `Caddyfile` (20 МБ × 5, не дольше 14 дней). Уборка копии базы, `.env`, откат деплоя
и раздачу файлов не трогает: путей к ним в скрипте нет.

```bash
systemctl list-timers gb-backup.timer gb-cleanup.timer apt-daily-upgrade.timer
tail -3 /var/log/gb-cleanup.log
apt-cache policy openssh-server | head -8    # среди источников ОБЯЗАН быть noble-security
```

⚠️ **Проверять последнюю строку на новой машине первым делом.** В образе VPS reg.ru раздела
`noble-security` в источниках пакетов не было, и автообновления три с половиной месяца
запускались каждое утро и не ставили ничего: накопилось 180 исправлений безопасности.
Снаружи это не видно никак — таймер зелёный, журнал без ошибок.

## 4. Частые ситуации

| что видно | причина | что делать |
|---|---|---|
| весь колледж получает «слишком много запросов» | кто-то из здания задел приманку, а адрес колледжа не в `GRADEBOOK_TRUST_IPS` | `systemctl restart gradebook` (бан живёт в памяти); вписать публичный адрес колледжа в `GRADEBOOK_TRUST_IPS` |
| «хранилище файлов не настроено» | свободно меньше 20 ГБ и нет ключей S3 — вложения честно выключены | освободить место или задать `GRADEBOOK_FILES_MODE` |
| расписание пустое или «собирается» | портал ВСГУТУ недоступен или меняется | ждать; правки администратора в расписании живут поверх портала и не теряются |
| Вектор отвечает сухо, без живой речи | GigaChat недоступен или ключ отозван | ответы по-прежнему верные (шаблоны); проверить ключ в «Настройках ИИ» |
| программа на ПК «не пускает»: подтверждение устройства | новый ПК | одобрить у администратора: «Запросы на подключение» |
| служба не стартует, в журнале про ключ базы или драйвер `sqlcipher3` | нет ключа или драйвера | это защита, а не сбой: без шифрования сервер с ПДн не поднимается |
| служба не стартует после восстановления | забыт `--new-epoch` или права на файл базы | [DISASTER-RECOVERY.md](DISASTER-RECOVERY.md) §3 |

## 5. Чего не делать никогда

- **не запускать второй процесс** (`--workers 2`) без Redis: число процессов выводит
  `server/serve.py`, и защита от перебора паролей ослабла бы в N раз молча;
- **не подключать раздел управления SSH к серверу**: он живёт только в программе
  (`desktop/server_admin.py`), на бою такого кода нет намеренно;
- **не копировать боевую базу на личные компьютеры**, в том числе «для отладки»;
- **не выключать шифрование базы** ради скорости — разница не видна в замерах, а без
  ключа сервер и не стартует;
- **не менять ключи полей** (`GRADEBOOK_DATA_KEY`, `GRADEBOOK_INDEX_KEY`) без инструмента
  перешифровки — [KEY-ROTATION.md](KEY-ROTATION.md) §4;
- **не удалять `webdist.old` и `app.old`** на сервере — это механизм отката выкладки.

## 6. Выпуск обновлений

| что | команда | проверка |
|---|---|---|
| сервер | `bash deploy/deploy-server.sh` (корневые модули едут сами) | `/health` 200 через ~5 с; `000` сразу после рестарта — ещё не поднялся |
| сайт | `cd web && npm run build && bash deploy/deploy-web.sh` | главная 200, ручка без входа 401 |
| телефон по воздуху | `web/deploy/release-ota.ps1 -Deploy` (подписывает и проверяет подпись) | `/app/updates` отдаёт новую версию и подпись |
| программа ПК | `tools/publish_desktop_update.sh` (подпись обязательна, ворота `--verify`) | `/desktop/updates` отдаёт новую версию с подписью |
| APK | только при смене нативной части; перезалив в RuStore | — |
