# GradeBookAI — аудит безопасности и план соответствия (152-ФЗ + межд. стандарты)

> Аудит на Pre-Release-2.8. Цель: сайт и десктоп на 100% соответствуют 152-ФЗ РФ
> (приказ ФСТЭК России №21) и международным практикам (OWASP Top-10, ISO/IEC 27001,
> OWASP ASVS). Ниже: что уже хорошо, найденные слабые места (по критичности) и
> пошаговый план устранения. Секреты в этот файл НЕ выносятся.

## 0. Модель данных и угроз
- **ПДн**: ФИО, группа, оценки, посещаемость, e-mail, телефон студентов/преподавателей.
- **Секреты**: JWT-секрет, пароль SMTP, учётка GigaChat, хеши паролей.
- **Границы**: десктоп (offline-first, локальный шифр) ↔ REST API (FastAPI) ↔ SQLite на VPS
  ↔ браузер (SPA). Внешние: portal.esstu.ru (чтение), smtp.mail.ru (почта), GigaChat (LLM).

## 1. Что уже сделано ХОРОШО (сильные стороны)
- 🔒 **Пароли** — двухэтапный гибрид PBKDF2-SHA512 + Стрибог512 (Р 50.1.111-2016), одинаково
  на десктопе и сервере. Открытый пароль нигде не хранится и не логируется (проверено).
- 🔒 **JWT_SECRET** на бою — 64 симв., не дефолт → токены не подделать. Токены жёсткие ~5 ч,
  есть чёрный список (revoke) и видимость сессий.
- 🔒 **Транспорт** — HTTPS/TLS (Caddy + Let's Encrypt, авто-обновление). Сервер в РФ.
- 🔒 **Анти-брутфорс** — throttle по (IP, логин) на /auth/login и по IP на /auth/register.
- 🔒 **CORS** сужен на `https://esstu-gradebook.ru` (не «*»).
- 🔒 **Доступ к БД** — только через SQLAlchemy ORM (параметризовано) → SQL-инъекций нет.
- 🔒 **Ошибки 500** не выдают стек-трейс наружу (единый обработчик).
- 🔒 **ПДн на десктопе** — Fernet (AES-128) + ключ под Windows DPAPI.
- 🔒 **Раздача файлов** `/downloads/*` — защита от path-traversal (realpath внутри папки).
- 🔒 **Регистрация** — только после ОДОБРЕНИЯ админом (нельзя самому получить доступ к группе).

## 2. НАЙДЕННЫЕ СЛАБЫЕ МЕСТА (по критичности)

### 🔴 Критично / высокий приоритет
1. **ПДн на СЕРВЕРЕ хранятся в открытом виде.** БД — SQLite-файл на VPS, ФИО/оценки/почты/
   телефоны лежат открыто. Кража файла БД = утечка всех ПДн. Десктоп шифрует локаль, сервер — нет.
   *152-ФЗ/ФСТЭК №21 требует защиты ПДн при хранении.*
2. **PII (e-mail=логин, телефон) в БД открыто.** Как отметил заказчик: кража почты → компрометация.
   Нужна защита адресов/телефонов при хранении (шифрование или хеш-индекс для поиска + шифр для показа).
3. **Учётка GigaChat в БД открытым текстом** (`config['gigachat_credentials']`, синкается с
   десктопа). Секрет провайдера LLM в незашифрованной таблице.

### 🟡 Средний приоритет
4. **`/auth/recover` без rate-limit** — можно спамить сбросами пароля по известной почте
   (annoyance/DoS) и энумерировать существующие аккаунты по разнице ответа/времени.
5. **Нет security-заголовков** (HSTS, X-Content-Type-Options, X-Frame-Options/CSP, Referrer-Policy).
   Защита от clickjacking/MIME-sniffing/утечки Referer.
6. **Веб-барьер устройства снят полностью** — валидные креды с ЛЮБОГО устройства дают доступ.
   Осознанное решение заказчика, но это ослабленный контроль vs десктоп. Компенсировать журналом
   входов и (опц.) 2FA для админа.
7. **Нет аудита ВСЕХ значимых действий** на сервере (ввод/правка оценок, CRUD ПДн, экспорт xlsx,
   одобрение регистрации, восстановление пароля). Приказ ФСТЭК №21 требует регистрации событий ИБ.
8. **Резервные копии/логи** — не проверено, где лежат бэкапы серверной БД и не попадают ли ПДн в
   логи systemd/journalctl открыто. Нужен контроль хранения и ротации.

### 🟢 Низкий приоритет / усиление
9. **Нет 2FA** для администратора (не требование 152-ФЗ, но межд. практика для привилегий).
10. **Восстановление пароля шлёт пароль письмом** — стандартно, но лучше одноразовая ссылка со
    сроком жизни, а не сам пароль в теле письма.
11. **Политика паролей** для самих аккаунтов (min длина/сложность) — админ может задать слабый.
12. **Нет автоматической разлогинизации по неактивности** на сайте (есть только 5-часовой TTL).

## 3. ПЛАН УСТРАНЕНИЯ (по фазам, с маппингом на стандарты)

### Фаза S1 — быстрые победы (низкий риск, делаем сразу)
- [ ] Rate-limit `/auth/recover` (как register: 5/3 мин по IP); ответ всегда одинаковый
      («если аккаунт есть — письмо отправлено») → нет энумерации. *(OWASP A07)*
- [ ] Security-заголовки в Caddy: `Strict-Transport-Security`, `X-Content-Type-Options: nosniff`,
      `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, базовый `Content-Security-Policy`.
      *(OWASP A05, ISO A.13)*
- [ ] Убрать/деактивировать демо-аккаунты (`webtest` и пр.) на бою.
- [ ] Восстановление: слать одноразовую ссылку (токен, TTL 30 мин), а не пароль в письме.

### Фаза S2 — защита данных при хранении. ВАЖНО про сертификацию (см. §6)
> Замечание (верное): Fernet(AES)+ключ в `.env` — это **defense-in-depth**, но НЕ
> сертифицированное соответствие 152-ФЗ. Регулятору (ФСБ/ФСТЭК) важен не «факт шифрования»,
> а **сертифицированное СКЗИ + ГОСТ + регламент ключей + документы**. Поэтому S2 делим на два
> контура: (A) техническая защита-в-глубину сейчас; (B) сертифицированный контур для боевого
> внедрения у госоператора.

**(A) Defense-in-depth (делаем в коде, снижает риск утечки файла БД/бэкапа):**
- [ ] **Абстрактный слой крипто** `crypto_backend`: интерфейс encrypt/decrypt/blind_index, чтобы
      бэкендом можно было подставить как Fernet (dev), так и **СКЗИ** (бой) — без переписывания логики.
- [ ] Шифровать **телефон** и (после миграции) e-mail: «слепой индекс» HMAC для поиска по логину +
      шифр для показа. Логин остаётся рабочим, открытой почты в БД нет. ⚠️ Каскад: id `stud:{login}`,
      `sub` в JWT, синк — меняем аккуратно на обслуживании, не на живом проде.
- [ ] Шифрование файла БД (SQLCipher) ИЛИ LUKS-том под БД — защита от кражи файла/диска.
- [ ] `.env`: строгие права (✅ 600), + вынести секреты в защищённое хранилище (не plaintext-файл).

**(B) Сертифицированный контур 152-ФЗ (СКЗИ) — для боевого внедрения:**
- [ ] Определить **уровень защищённости (УЗ)** актом классификации ИСПДн (для колледжа: ПДн «иные»,
      субъектов <100k, угрозы тип 3 → ориентировочно **УЗ-3/УЗ-4**; итог фиксирует оператор).
- [ ] Криптозащиту (при передаче/хранении ПДн) выполнять **сертифицированным СКЗИ**: **КриптоПро CSP**
      или **ViPNet CSP**, алгоритмы **ГОСТ 34.12-2018 (Кузнечик/Магма)**, класс СКЗИ под УЗ (обычно КС1).
      Наш код УЖЕ имеет ГОСТ-путь для хеша пароля (Стрибог через OpenSSL GOST-engine/ViPNet) — крипто-
      бэкенд (A) достраиваем так, чтобы шифрование шло через тот же сертифицированный движок.
- [ ] **Регламент ключей**: хранение в СКЗИ / на токенах (Рутокен/JaCarta) или в защищённом хранилище,
      **журнал учёта ключей и СКЗИ**, разграничение доступа к ключам.
- [ ] Канал: при передаче ПДн по недоверенной сети — TLS через сертифицированное СКЗИ (ГОСТ-TLS,
      напр. Stunnel/КриптоПро на фронте) в дополнение к Let's Encrypt.

### Фаза S3 — аудит и мониторинг ИБ (приказ ФСТЭК №21, ISO A.12.4)
- [ ] Единый **аудит-лог** значимых действий: вход/выход, ввод/правка/удаление оценок, CRUD ПДн,
      экспорт, одобрение регистрации, сброс пароля, отзыв сессии — с кто/когда/IP/что.
- [ ] Хранить аудит отдельно, только на добавление (append-only), с ротацией; ПДн в логах — не в
      открытом виде (id вместо ФИО).
- [ ] Контроль бэкапов: где лежат, шифрование бэкапов, срок хранения, восстановление проверено.

### Фаза S4 — усиление доступа
- [ ] (Опц.) 2FA (TOTP) для администратора.
- [ ] Политика паролей на создание/смену (min 8, буквы+цифры+спецсимвол; блок топ-утёкших).
- [ ] Идл-таймаут сессии на сайте (авто-выход после N минут бездействия).
- [ ] Пересмотр веб-барьера устройства: хотя бы «доверенные устройства» для персонала.

### Фаза S5 — процессы и документы (организационные меры 152-ФЗ)
- [ ] Политика обработки ПДн, согласие субъекта ПДн (галка при регистрации), уведомление РКН.
- [ ] Модель угроз и модель нарушителя (ФСТЭК), акт классификации ИСПДн, назначение
      ответственного за ИБ.
- [ ] Регламент реагирования на инциденты и уведомления об утечке (72 ч — межд. практика/GDPR-подобно).

## 5. Порядок работ
S1 (сразу, безопасно) → S3 (аудит — безопасно, требование ФСТЭК №21) → S2(A) defense-in-depth
→ S2(B) сертифицированный контур + S5 (документы). S2(B) — организационно-лицензионный трек
(закупка СКЗИ, аттестация), идёт параллельно коду.

## 6. Реальность сертификации 152-ФЗ (важно для продажи госоператору)

**Суть замечания (верного):** сертифицированное соответствие 152-ФЗ определяется не самим
фактом шифрования, а применением **сертифицированного СКЗИ**. Наша схема Fernet(AES)+`.env`:
| Критерий | Наша схема (сейчас) | Требование 152-ФЗ (УЗ-1..3) |
|---|---|---|
| Алгоритм | AES (зарубежный) | ГОСТ 34.12-2018 (Кузнечик/Магма), Стрибог |
| Крипто-средство | библиотека `cryptography` | **сертифицированное СКЗИ** (КриптоПро, ViPNet) |
| Хранение ключей | текстовый `.env` (права 600) | регламент: токены/HSM/хранилище СКЗИ + журнал учёта |
| Документы | нет | формуляр СКЗИ, акт установки, журнал учёта ключей |

**Разделение ответственности:**
- **Код (наша зона):** абстрактный крипто-слой с возможностью подключить СКЗИ; ГОСТ-хеш пароля
  уже есть; аудит-лог; анти-НСД; корректная архитектура ключей (не хардкод, не в git).
- **Оператор/поставщик (организационно-лицензионная зона):** закупка и установка СКЗИ (КриптоПро/
  ViPNet), определение УЗ и модель угроз, **аттестация ИСПДн** (для госоператора) или оценка
  соответствия, регламенты и журналы, назначение ответственного за ИБ, уведомление РКН.

**Вывод:** технически мы строим систему «под СКЗИ» (чтобы легально подключить сертифицированный
движок), но САМА сертификация/аттестация — это отдельный проект с лицензиями и документами, не
только код. Fernet+`.env` оставляем как временную defense-in-depth для MVP/демо, с явной пометкой
«не является сертифицированным СКЗИ».
