# GradeBookAI изнутри: экскурс для программиста

Этот документ для того, кто впервые открыл репозиторий и хочет за вечер понять, как устроен
проект: из чего он состоит, как по нему идёт запрос, где живут правила и почему сделано именно
так. Он не заменяет код и не повторяет его построчно: где подробности важны, даны имена файлов
и функций, по которым их легко найти.

Сверено с кодом 22.10.2026, версия 4.1.4. Если текст разошёлся с кодом, прав код, а документ
надо поправить. Собирается в Word командой `python -X utf8 tools/build_tour_docx.py`.

## 1. Что это за продукт

GradeBookAI — электронный журнал успеваемости для Технологического колледжа ВСГУТУ (Улан-Удэ).
Преподаватели ставят оценки и отмечают пропуски, студенты и родители видят успеваемость,
кураторы получают отчёты, администрация ведёт группы, предметы и расписание. Внутри есть
мессенджер с каналами и модерацией и помощник «Вектор», который отвечает на вопросы об
успеваемости и расписании.

Продукт работает на трёх платформах, и на всех трёх это одно и то же веб-приложение:

- **сайт** в браузере;
- **программа для Windows**, которая умеет работать без интернета;
- **приложение для Android** из RuStore, обновляемое по воздуху.

Продукт обрабатывает персональные данные студентов, поэтому многие решения продиктованы
152-ФЗ: шифрование баз, отказ от иностранных сервисов, отдельное согласие студента на доступ
родителя. Оператором персональных данных является ВСГУТУ, мы поставляем программу.

## 2. Большая картина

```text
  Интерфейс у всех трёх один: Vue-SPA из web/

  Сайт (браузер)       Программа для Windows          Android (Capacitor)
        |              окно WebView2                         |
        |                    |                               |
        |              локальный сервер 127.0.0.1            |
        |              тот же server/app,                    |
        |              копия базы под SQLCipher              |
        |                |                  |                |
        |          очередь правок     онлайн-разделы         |
        |          и зеркало          пересылаются           |
        v                v                  v                v
  +------------------------------------------------------------------+
  |  Caddy (HTTPS)  ->  FastAPI server/app  ->  SQLite + SQLCipher    |
  +------------------------------------------------------------------+
```

Главные решения, на которых всё держится (подробно — в `docs/adr/`):

1. **Одна SPA на три платформы** (ADR-0004). Интерфейс пишется один раз в `web/`. Программа
   показывает его в окне на движке Edge, Android — в обёртке Capacitor. Различия платформ
   выражаются узкими проверками возможностей, а не копиями страниц.
2. **Программа работает без сети** (ADR-0001). Внутри программы на 127.0.0.1 поднимается
   тот же самый серверный код `server/app`, но на локальной копии базы. Интерфейс говорит
   с ним, а правки журнала уходят на основной сервер очередью, когда появится связь.
3. **Одна база — SQLite, на сервере зашифрованная SQLCipher** (ADR-0003). Второй СУБД нет.
4. **Время для порядка изменений ставит сервер** (ADR-0005), а позицию в потоке изменений
   задаёт серверный номер изменения `change_seq`, а не время.
5. **Мессенджер только онлайн** (ADR-0002): переписка не копируется на компьютеры.

### Общие корневые модули

Это небольшие модули на чистой стандартной библиотеке Python. Их импортируют и сервер, и
программа, поэтому правило в них существует в одном экземпляре:

| модуль | что решает |
|---|---|
| `grading.py` | средний балл, шкалы преподавателей, «завалено ли», средний по группе |
| `study_hours.py` | учебные часы и ЗЕТ: занятие = пара = 2 часа |
| `estimators.py` | честная статистика по малой выборке (интервал Уилсона, сглаживание, тренд Тейла — Сена) |
| `college_clock.py` | время колледжа: «сегодня» и учебный день по Улан-Удэ |
| `vector_nlu.py` | разбор вопросов к Вектору |
| `voice_command.py` | разбор голосовых команд преподавателя |
| `dropout_risk.py` | риск отчисления: прозрачные факторы и веса |
| `teacher_match.py` | сопоставление ФИО преподавателя из расписания портала |
| `desktop_update.py` | правила автообновления программы и номер версии |

Часть правил нужна и браузеру. Тогда у Python-модуля есть зеркало на JavaScript (например,
`web/src/utils/grading.js`, `web/src/utils/vectorNlu.js`), а совпадение держат общие наборы
данных в `docs/contracts/`: одни и те же случаи проверяют тесты на обоих языках.

## 4. Путь одного запроса: преподаватель ставит оценку на сайте

1. Страница журнала (`web/src/pages/teacher/`) зовёт `teacherApi` из
   `web/src/api/endpoints.js` — весь контракт с сервером собран в этом файле.
2. HTTP-клиент `web/src/api/client.js` подставляет токен, идентификатор устройства и тип
   клиента; на ответ 401 один раз тихо обновляет токен.
3. На сервере запрос попадает в `server/app/main.py`, проходит промежуточные слои (заголовки
   безопасности, метрики, приманки) и доходит до `teacher_set_grade` в
   `server/app/routers/web/write.py`.
4. `deps.get_current_user` проверяет токен и его тип. Обработчик проверяет значение оценки
   (`grading.is_allowed_value`), что занятие входит в назначение этого преподавателя
   (`_teacher_check_assignment`) и его подгруппу, что семестр не архивный, и находит студента
   по `student_id` — по ФИО только если в группе он один (`_resolve_student`).
5. `_lock_for_write` берёт замок записи. Под замком `_ensure_term_open` проверяет, не закрыт
   ли семестр итоговой оценкой, а `_ensure_base_version` — не изменил ли кто-то эту оценку
   после того, как преподаватель её увидел (иначе — конфликт, а не тихая перезапись).
6. Строка оценки ключуется неизменяемым `student_id`: формат ключа считается только в
   `server/app/models.py::grade_id`.
7. При записи триггер SQLite выдаёт строке следующий номер изменения (`change_seq`), по нему
   программы на других компьютерах узнают о правке.
8. В конце обработчик сообщает студенту в системный канал «Мои оценки» (`notify_grade_posted`).
   Сбой уведомления не отменяет записанную оценку.

## 5. Программа для Windows

Нативных экранов у программы нет: окно (`desktop/webview2_app.py`) показывает ту же SPA.
Запуск в `main.py` идёт так: убедиться, что программа не запущена второй раз (иначе поднять
уже открытое окно) → применить скачанное обновление → открыть служебную базу → поднять
локальный сервер → открыть окно. Проверка копии стоит раньше обновления: подменять `.exe`,
пока работает вторая копия, нельзя.

Ключевые части:

| файл | роль |
|---|---|
| `desktop/local_api.py` | поднимает `server/app` на 127.0.0.1 с локальной копией базы; пересылает на основной сервер разделы, которые живут только там (`_PROXY_PREFIXES`: мессенджер, модерация, одобрение устройств) |
| `desktop/route_policy.py` | для каждого запроса записи решает: `replay` (журнал — в копию и в очередь), `local` (только копия, с записанной причиной) или `proxy` (сразу на сервер; без сети — честный отказ). Умолчание — `proxy` |
| `desktop/desk_outbox.py` | очередь правок журнала: досылает строго по порядку, с версией, которую видел человек; конфликт показывает человеку |
| `desktop/local_mirror.py` | зеркало: подтягивает с сервера всё новее последнего увиденного номера изменения; строку с неотправленной правкой не трогает |
| `sync/sync_runner.py` | фоновый цикл: досылка → зеркало → раз в час «Сверщик» (`sync/verifier.py`), который проверяет, что копия совпадает с сервером |
| `data/local_db.py` | обе локальные базы шифруются целиком ключом устройства под DPAPI |

Пример без сети: преподаватель ставит оценку в программе, сети нет. Локальный сервер пишет
оценку в копию, и интерфейс сразу её показывает. Запрос встаёт в очередь. Когда связь
появляется, очередь отправляет его на основной сервер вместе с версией, которую видел
человек. Если за это время оценку изменили на сайте, сервер ответит конфликтом, и программа
покажет обе версии с кнопками «оставить моё» и «взять серверное».

## 6. Синхронизация

- Синхронизируются 11 таблиц — справочники и журнал (`SYNC_MODELS` в `server/app/models.py`).
  Всё остальное (мессенджер, аудит, второй фактор) живёт только на сервере.
- У каждой синхронизируемой таблицы есть колонка `change_seq` и три триггера
  (`server/app/sync_clock.py`). Писатель в SQLite один, поэтому порядок номеров совпадает с
  порядком фиксаций: если клиент видел номер N, он видел всё, что меньше N. Время для этого
  не годится: метку ставят до фиксации, а читатель видит только зафиксированное.
- Удаление пишет запись в журнал удалений `sync_deletes`, иначе копия не узнала бы о нём.
- `/sync/pull?cursor=N` отдаёт изменения после N, `/sync/head` — долгий опрос «появилось ли
  новое», чтобы правка доезжала за секунды.
- Если сервер восстановили из резервной копии, номера «откатываются». Это ловит якорь рядом с
  базой (`sync_clock.check_restore`): поколение базы меняется, и копии программ сверяются с
  чистого листа, а не теряют правки молча.
- Модель синхронизации проверяется тестом-автоматом `tests/test_sync_state_machine.py`:
  случайные истории действий и проверка правил после каждого шага.

## 7. Роли и права

Роли: `student`, `teacher`, `parent`, `admin`, `moderator`. Куратор — это преподаватель, у
которого есть курируемые группы.

- Права проверяются на сервере на каждом запросе. Скрыть кнопку в интерфейсе — не защита:
  тот же запрос может прийти из программы, из очереди или голосовой командой.
- Чтение для кабинетов собрано в `server/app/webdata.py` и разрезано по ролям в
  `server/app/routers/web/` (`student`, `teacher`, `curator`, `admin_read` и другие).
- Родитель видит журнал только после согласия студента: привязка создаётся в ожидании, и
  студент подтверждает её у себя.
- Подтверждение нового устройства обязательно для программы и не требуется для сайта и
  телефона (`deps.device_barrier_applies`).
- Модерация мессенджера — роли `admin` и `moderator`; для студентов модератор виден только
  номером.
- Права, как и прочее, проверяются свойствами по всему коду: `server/tests/test_scope_properties.py`.

## 8. Вектор: помощник, который не выдумывает цифры

```text
вопрос → vector_nlu.classify()          что спрашивают (интент, фамилия, предмет, день)
       → web/vector.py::_vector_facts() факты из базы SQL-запросами, строго по роли
       → vector_llm.voice()             языковая модель только переформулирует
       → ответ
```

- Цифры считает код, а не модель. Модель (GigaChat или локальная Ollama) лишь делает текст
  живым; без неё работают шаблоны.
- Ответы с фамилиями в модель не уходят вовсе: такой ответ отдаётся как есть. Это проверяет
  тест-свойство `server/tests/test_vector_never_voices_names.py` по всем интентам.
- Разбор вопросов одинаков на сервере и в офлайн-режиме телефона: Python и JavaScript
  сверяются по `docs/contracts/vector-intent-cases.json`, а все ответы всех ролей — по снимку
  `docs/contracts/vector-map.json`.
- Голосовые команды преподавателя («Иванову пять») разбираются без модели
  (`voice_command.py`) и записываются только после подтверждения человеком.

## 9. Мессенджер

- Пакет `server/app/routers/messenger/`: `_common.py` (права, реестр сокетов, сборка ответов)
  и модули по темам — чаты, сообщения, каналы, вложения, модерация, трекер задач.
- Доставка — веб-сокет плюс страховочный опрос; при живом сокете опрос редкий, в скрытой
  вкладке молчит.
- Любая запись в беседу — сообщение, правка, пересылка — проходит одну проверку
  `messages._ensure_may_write`.
- Вложения идут мимо нашего сервера: браузер кладёт файл в хранилище по подписанной ссылке
  (`server/app/storage.py`), тип файла проверяется по белому списку.
- Ответ Вектора в общей беседе не записывается в базу и виден только спросившему: так чужие
  данные не попадают к соседям ни в одной из многих выборок сообщений.

## 10. Безопасность и персональные данные

- **Пароли:** гибридный хеш PBKDF2-SHA512 и PBKDF2 на ГОСТ «Стрибог»; один код на сервере и в
  программе. Пароль не хранится нигде, вход сохраняется только токеном.
- **Токены:** без второго фактора сессия живёт 5 часов; со вторым фактором (TOTP, свой код на
  стандартной библиотеке) — дольше.
- **Шифрование:** серверная база — SQLCipher, обе локальные базы программы — тоже, ключ
  устройства защищён DPAPI.
- **Секреты** читаются одной точкой `server/app/secrets_source.py` и никогда не попадают в git.
- **Журнал безопасности** (`server/app/audit.py`) — с цепочкой хешей: правка задним числом
  заметна, проверка — `server/verify_audit.py`.
- **Приманки** (`server/app/canary.py`): пути и учётка, к которым законно не обращается никто;
  обращение фиксируется и блокирует адрес.
- **Иностранные сервисы:** перевод работает офлайн, распознавание речи — на своём сервере.
  Каждый внешний адрес описан в `docs/security/SUBPROCESSORS.md`, и тест не даст добавить новый
  молча.
- Базовый уровень по OWASP ASVS 5.0 ведётся проверяемым файлом `docs/security/asvs-baseline.json`.

## 11. Тесты

Тестов около четырёх с половиной тысяч: клиентские (`tests/`), серверные (`server/tests/`),
веб (`web/tests/`, `node --test`) и Android (Gradle).

```bash
pytest                                   # клиент и общие модули (из корня)
cd server && pytest                      # сервер (около 9 минут)
cd web && npm test && npm run lint       # веб
cd web/android && ./gradlew :app:testDebugUnitTest
```

Как здесь принято писать тесты:

- **Проверять свойство, а не снимок значения.** Не «список равен этим пяти строкам», а «каждый
  элемент списка удовлетворяет правилу»: иначе тест краснеет на каждом законном изменении.
- **Обратный ход.** Новый тест-сторож обязан краснеть, если откатить исправление. Тест,
  зелёный и без исправления, неотличим от исправного кода.
- **Тесты-сторожа по всему коду.** Многие правила проверяются разбором исходников: нет ли
  блокирующего вызова в асинхронном обработчике, не читается ли секрет в обход единой точки,
  не появилось ли состояние, которое сломает работу в несколько процессов.
- **Герметичность.** Тест не ходит в сеть, сам задаёт окружение и не зависит от календаря.
- Pytest запускается по одному: два прогона одновременно портят общую тестовую базу.

## 12. Сборка и выкладка

- **Сервер** собирается в неизменяемый архив (`tools/build_release.py`); две сборки одного
  коммита совпадают побайтно. Выкладка — скрипты в `deploy/`, на машине остаётся копия для
  отката. Перед людьми стоит Caddy с единственным конфигом `server/Caddyfile`.
- **Программа** собирается Nuitka (`build_nuitka.sh`) в один `.exe`; обновление подписывается
  Ed25519, программа проверяет подпись перед заменой файла.
- **Android:** правки интерфейса едут по воздуху подписанным бандлом
  (`web/deploy/release-ota.ps1`), APK пересобирается только при смене нативной части.
- Новый сервер разворачивается одной командой (`deploy/install.sh`); регламенты передачи,
  восстановления после аварии и смены ключей — в `docs/operations/`.

## 13. Как здесь пишут код

- **Одна дверь.** У каждого правила одно место: расчёт оценок — `grading.py`, время —
  `college_clock.py`, секреты — `secrets_source.py`, запись в беседу — `_ensure_may_write`.
  Нашёл вторую копию — убери её.
- **Громкий отказ лучше тихого.** Нет связи — честная ошибка с причиной, а не «сохранено» в
  пустоту. Исключения не глотаются молча.
- **Умолчание — прежнее поведение.** Новая настройка не меняет то, что работало у тех, кто
  просто обновился.
- **Сначала стандартная библиотека.** Свои TOTP, QR-код, подпись запросов к хранилищу и
  парсер расписания написаны, чтобы не тянуть лишних зависимостей и не отправлять данные
  третьим лицам.
- **Имена — по-английски, комментарии — по-русски.** Комментарий объясняет, почему код такой,
  коротко и спокойно; история находки — в сообщении коммита.
- Python — PEP 8 и `ruff`; Vue — `<script setup>`, Composition API, тексты через словарь
  `web/src/i18n/dictionaries.js` (русский, английский, китайский), цвета — токены `--gb-*`.
- Новая колонка в существующей таблице требует миграции в `server/app/db.py`: автоматическое
  создание схемы заводит только новые таблицы.

## 14. С чего начать

1. Установить зависимости: `uv sync --extra desktop --extra server --extra dev`, затем
   `cd web && npm install`.
2. Поднять стенд с выдуманным колледжем: `python -X utf8 tools/qa_stand.py` и открыть
   `http://127.0.0.1:8765`. В нём нет ни одной живой персональной записи — на нём и пробуют.
3. Прочитать по порядку: `README.md` → `docs/adr/` → `server/app/main.py` →
   `server/app/routers/web/write.py` → `desktop/route_policy.py` → `server/app/sync_clock.py`.
4. Первая задача — небольшая правка с тестом: найти место, написать тест, который краснеет
   без правки, сделать правку, прогнать соседние тесты.

## 15. Словарь

| слово | значение |
|---|---|
| бой | основной сервер, которым пользуются люди |
| стенд | локальный сервер с выдуманными данными для проверок |
| копия | локальная база программы, из которой читает интерфейс |
| зеркало | процесс, который подтягивает в копию изменения с сервера |
| очередь досылки | неотправленные правки журнала из программы |
| номер изменения | `change_seq`, позиция строки в потоке изменений |
| надгробие | пометка удаления вместо физического стирания |
| LWW | «последняя запись побеждает»; у нас порядок задаёт сервер |
| OTA | обновление интерфейса телефона без перезалива приложения |
| ЗЕТ | зачётные единицы трудоёмкости |
| интент | тип вопроса к Вектору |
