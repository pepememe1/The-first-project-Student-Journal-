# План: Telegram-бот и мини-приложение управления (кнопки деплой / пуш / OTA)

> Составлен 03.09.2026 по задаче Ярослава. **Реализация — следующим заходом.**
> Решение по размещению принято им же: **бот и мини-приложение живут на VPS отдельным
> портом**; после переезда журнала на железо ВСГУТУ бот остаётся на освободившемся VPS.

---

## 1. Что это решает

Дословная постановка: «когда у тебя заканчиваются токены и ты не успеваешь запушить и
задеплоить и выпустить OTA — чтобы я делал это сам».

То есть цель не «панель управления ради панели», а **довести до конца работу, которую я
не успел сдать**. Плюс сводка состояния сервера с телефона.

Требования:
- сводка: статус, аптайм, память, диск, логи — всё, что уже есть в разделе «Сервер»;
- три кнопки: **деплой на VPS**, **пуш в GitHub с выбором ветки** (есть — в неё, нет —
  создаётся), **выпуск OTA-бандла**;
- **перед каждой кнопкой прогоняются тесты; красные — действие НЕ выполняется.**

## 2. 🔥 Три ограничения, найденные проверкой машины (03.09.2026)

Их надо решить до кода, иначе план развалится на середине.

### 2.1 На VPS НЕТ node и npm — веб и OTA там не собрать

Проверено живой командой:

| инструмент | на VPS |
|---|---|
| git 2.43, python 3.12, rsync, curl, jq | ✅ есть |
| **node, npm** | ❌ **НЕТ** |
| zip / unzip | ❌ нет (не беда: `python -m zipfile` умеет) |

OTA-бандл и `web/dist` собираются `npm run build`. Значит **кнопка «выпуск OTA» на VPS
физически не может собрать бандл.** Варианты:

- **(A) Поставить node на VPS.** Место теперь есть (3.7 ГБ). Но `vite build` пойдёт на
  ЕДИНСТВЕННОМ ядре, которое обслуживает журнал, и с 960 МБ RAM — то есть выкладка будет
  тормозить работающий колледж. Прямо противоречит принципу «одно ядро, один uvicorn».
- **(B) Кнопка ВЫКЛАДЫВАЕТ уже собранный бандл**, а не собирает. Я собираю `web/dist` и
  кладу бандл в очередь (`server/ota_bundles/queue/`) до конца заходa; кнопка проверяет
  контрольную сумму, публикует и сверяет, что сайт отдаёт новую версию. **Дёшево, ничего
  не ломает, и покрывает ровно заявленный сценарий** («не успел выложить готовое»).
- **(C) Сборка в GitHub Actions**, VPS забирает артефакт. Правильный «взрослый» путь,
  но требует настройки Actions и токена с доступом к артефактам.

**Рекомендую B сейчас и C потом.** A — не рекомендую: цена ложится на студентов.

### 2.2 Код лежит на МОЕЙ машине, а бот — на VPS

Это главный подвох сценария. Когда у меня кончаются токены, правки лежат
**незакоммиченными на ПК Ярослава**. Бот на VPS их не видит и запушить не может — ему
нечего пушить.

Решение — **автопуш в служебную ветку по хуку `Stop`**: как только я останавливаюсь
(в том числе по обрыву или лимиту), правки уезжают в ветку `claude-wip/<дата>`. Тогда:

- код всегда на GitHub, даже если я не успел сказать «готово»;
- кнопка «пуш» в боте становится **перекладыванием** `claude-wip` → нужную ветку
  (с прогоном тестов), а не «пушем из ниоткуда»;
- кнопка «деплой» берёт код из GitHub, а не с выключенного ПК.

⚠️ Служебная ветка — НЕ релизная. `claude-wip` никогда не сливается автоматически:
это черновик, который может быть на середине правки.

⚠️ Автопуш обязан молчать при отсутствии изменений и никогда не трогать
`Release-*`/`pre-release-*`.

### 2.3 §16 CLAUDE.md запрещает выполнение команд в боевом приложении

Дословно: *«Граница проходит по НАЛИЧИЮ КОДА, а не по проверке роли… Никогда не
подключать `desktop/server_admin.py` к `server/app/main.py`, даже временно для
отладки»*. Держит `test_prod_server_has_no_command_execution`.

Кнопка «деплой» — это исполнение команд. Поэтому:

> **Бот — ОТДЕЛЬНЫЙ процесс на ОТДЕЛЬНОМ порту и в ОТДЕЛЬНОМ каталоге. Ни одна его
> строка не импортируется в `server/app`, и ни один его роутер не подключается к
> `main.py`.** Инвариант §16 сохраняется буквально: в боевом приложении кода выполнения
> команд по-прежнему нет.

⚠️ Соблазн «подключить роутер к main.py, там же уже есть авторизация» велик и ошибочен:
он снимает единственную настоящую границу и обнуляет существующий тест. В план это
записано, чтобы следующий не сделал «проще».

## 3. Архитектура

```
Telegram ──HTTPS──> Caddy (esstu-gradebook.ru/tg/*)  ──> 127.0.0.1:8010  (gb-botd)
                          │                                    │
                    статика мини-аппа                     отдельный процесс,
                    /var/www/gb-tg/                       отдельный systemd-юнит,
                                                          свой пользователь `gbbot`
                                                                 │
                                          ┌──────────────────────┼──────────────────────┐
                                     сводка (read-only)     ворота+действия        аудит
                                     hostinfo по HTTP       tools/gate_*.sh    audit_events
```

**Почему отдельный порт, а не отдельный домен:** сертификат уже есть, Caddy уже настроен
и под тестом. Новый поддомен = новый сертификат и новая запись DNS, ради ничего.

**Почему свой пользователь `gbbot`:** процессу нужны права на деплой, но не нужен доступ
к базе с ПДн. Отдельный пользователь + `sudoers` на конкретные команды (`systemctl
restart gradebook`, и только) — единственный способ это разделить.

⚠️ **`/tg/*` придётся добавить в Caddyfile**, а он под тестом (52 проверки). Правка
обязана сохранить инвариант «на приложение идёт ВСЁ, кроме статики»: `/tg/*` — новое
исключение, и в тесте появится его проверка.

## 4. Безопасность — обязательная часть, не «потом»

Кнопка «деплой» = удалённое выполнение кода на машине с ПДн студентов. Поэтому:

1. **Проверка подписи `initData`** (HMAC-SHA256 по токену бота, схема Telegram). Без неё
   любой может подделать запрос — миниапп это просто веб-страница. Проверка на СЕРВЕРЕ,
   на каждый запрос, а не один раз при открытии.
2. **Белый список `telegram_user_id`.** Не «роль», не «пароль» — список из одного-двух id
   в конфиге. Всё прочее — 403 без объяснений.
3. **Токен бота через `secrets_source.py`** (уже существующая единственная точка чтения
   секретов: креды systemd → файл → окружение). Переменная окружения видна в
   `/proc/<pid>/environ` любому, кто получил root.
4. **Каждое нажатие — в `audit_events`** с id, действием, ветвью и результатом. Журнал
   с 02.09 несёт цепочку хешей, то есть след правки заметен.
5. **Ограничитель частоты**: не чаще одного действия в N секунд. Иначе кнопка «деплой»
   становится способом положить сервер собственными рестартами.
6. 🔒 **Логи в миниапп идут ФИЛЬТРОВАННЫМИ.** `journalctl` боевого сервера содержит
   логины и пути с ПДн, а Telegram — иностранный сервис (п. 5.6.1 политики ВСГУТУ,
   трансграничная передача не осуществляется). Отдаём только уровни/счётчики/строки,
   прошедшие белый список, а не сырой хвост. **Это не перестраховка: сырой
   `journalctl -n 200` в чат — это утечка.**
7. **Кнопка не выполняет то, что не прошло ворота** — см. ниже.

## 5. Кнопки и ворота

Общий принцип: кнопка не запускает действие напрямую. Она запускает **скрипт-ворота**,
который сначала проверяет, и лишь при нулевом коде выхода выполняет.

Ворота — отдельные файлы в `tools/`, чтобы их можно было позвать и руками, и из бота, и
из CI. Ненулевой код выхода обязан ОСТАНАВЛИВАТЬ действие.

### 5.1 Кнопка «Деплой сервера»

| шаг | чем | почему |
|---|---|---|
| 1 | `git fetch` + проверка, что `HEAD..origin/<чужая ветка>` пуст | девять совпавших SHA однажды дали ложную уверенность и уронили прод на 9 минут — файлы доехали из ДРУГОЙ ветки |
| 2 | серверный `pytest` | 1336 тестов, ~15 мин. Долго, но это единственные настоящие ворота |
| 3 | клиентский `pytest` | 757 |
| 4 | `tools/check_prod_caddyfile.sh` | сверяет боевой конфиг с git (написан 03.09.2026) |
| 5 | проверка состава архива | корневые модули (`grading.py`, `study_hours.py`, …) едут отдельно — частичный деплой ронял прод дважды |
| 6 | `deploy/deploy-release.sh` | неизменяемый артефакт + переключение ссылки |
| 7 | `curl /health`, `/`, выдуманная ручка → 404 | «сервис active» не значит «сайт жив» |
| 8 | не поднялся — **автоматический откат** | уже умеет `deploy-release.sh` |

⚠️ **Пятнадцать минут для кнопки в телефоне — много.** Поэтому два режима:
`--fast` (только затронутые тесты + шаги 1,4,5,7) и `--full`. Полный обязателен, если
тронуты синк, модели, роли, security. Решение о режиме принимает СКРИПТ по diff, а не
человек: «я тут только текст поправил» — самая частая причина падения прода.

### 5.2 Кнопка «Пуш в GitHub» (с выбором ветки)

Поле ввода имени ветки; есть — пуш в неё, нет — создаётся от текущей.

| шаг | чем |
|---|---|
| 1 | линт: `cd web && npm run lint` (если тронут веб) — **на VPS npm нет**, см. §2.1: этот шаг выполним только в варианте C |
| 2 | серверный + клиентский pytest |
| 3 | веб-тесты `npm test` — то же ограничение |
| 4 | запрет пуша в `main`/`pre-release-*` без явного подтверждения второй кнопкой |
| 5 | `git push origin <ветка>` |

⚠️ **Автор коммита — Ярослав или Влад.** Никаких трейлеров с упоминанием ассистента:
историю уже приходилось переписывать (`filter-branch` + force-push по всем ветвям).
Бот подставляет автора из конфига, а не «bot».

⚠️ **Пуш в существующую ветку — только `--ff-only` либо явное подтверждение.** Иначе
кнопка однажды перепишет чужую работу.

### 5.3 Кнопка «Выпуск OTA-бандла»

По варианту **B** (рекомендуемому):

| шаг | чем |
|---|---|
| 1 | в очереди `server/ota_bundles/queue/` есть подготовленный бандл | иначе честный отказ: «нечего выкладывать» |
| 2 | проверка SHA-256 бандла | Capgo сверяет её сама; несовпадение = телефоны молча не обновятся |
| 3 | 🔥 **проверка, что в архиве нет обратных слэшей** | `Compress-Archive` пишет `\`, и Android читает имя буквально — OTA не доезжала МЕСЯЦ при зелёных логах |
| 4 | файлы лежат в КОРНЕ архива, а не в подпапке | та же грабля |
| 5 | версия по схеме `1.<ГГММДД>.<ЧЧММ>` | `1.0.<ГГММДДЧЧММ>` не влезает в 32-битное число — так была сломана КАЖДАЯ выпущенная версия |
| 6 | публикация + `latest.json` |
| 7 | `curl /app/updates` — сайт правда отдаёт новую версию |

## 6. Сводка состояния (read-only часть)

Берётся из **уже существующего** `server/app/hostinfo.py` — того же источника, что раздел
«Сервер». Второй завёлся бы и разошёлся, и Ярослав видел бы разные числа на двух экранах.

Показываем: статус служб, аптайм, load average, память и подкачку, диск, размер базы и
факт её шифрования, свежесть последнего автобэкапа (**читать `/root/gb-backups/auto/`, а
не корень — в корне лежат старые ручные снимки, и по ним легко решить, что бэкап сломан**),
версии на бою (`/desktop/updates`, `/app/updates`), целостность журнала аудита.

⚠️ Сводка ходит на боевой сервер по HTTP как обычный клиент — не импортирует его код.

## 7. Этапы (порядок значим)

1. **Автопуш в `claude-wip` по хуку `Stop`** — без него весь сценарий не работает (§2.2).
   Самостоятельная польза: правки перестают теряться при обрыве.
2. **Ворота отдельными скриптами** `tools/gate_deploy.sh`, `gate_push.sh`, `gate_ota.sh`.
   Проверяемы руками, полезны сразу, до всякого бота.
3. **Демон бота** `botd/` — отдельный каталог, юнит, пользователь, порт 8010. Сначала
   ТОЛЬКО сводка, без единой кнопки.
4. **Подпись initData + белый список + аудит.** До кнопок.
5. **Кнопки по одной**, в порядке возрастания цены ошибки: OTA → пуш → деплой.
6. **Тесты на сам бот**: подпись отвергается при подделке, чужой id получает 403, ворота
   с ненулевым кодом не пропускают действие, логи не содержат ПДн. С обратным ходом.

Реалистичная оценка: пункты 1–2 — один заход; 3–4 — один; 5–6 — один-два.

## 8. Открытые вопросы к Ярославу

1. **OTA: вариант B (выкладывать готовое) или C (сборка в GitHub Actions)?** A (node на
   VPS) не рекомендую — сборка отнимет единственное ядро у работающего колледжа.
2. **Веб-тесты и линт требуют npm.** При B они выполняются у меня до передачи бандла;
   в боте их не будет. Достаточно ли этого, или нужен вариант C ради полных ворот?
3. **Полный прогон 15 минут** — держать кнопку столько, или довериться режиму `--fast`
   с автоматическим выбором по diff?
4. **Токен бота и `telegram_user_id`** — кладу в `secrets_source`; нужен сам токен от
   @BotFather и ваш id.
5. **Каталог на VPS**: предлагаю `/opt/gb-botd` (не `/root`: под ним Caddy не читает, и
   вообще боту там не место).
