# GradeBookAI — Pre-release 2.9 (история изменений)

Кратко: **оценки больше не теряются при смене фамилии студента** (переход на неизменяемый
идентификатор), **синхронизация шлёт только изменения** (а не всю базу каждый цикл),
**редактор расписания в админке**, **умный Вектор на всех платформах**, **живой
анимированный маскот** (арт Арины — один формат на ПК/веб/телефон), **мобильное приложение
Android** с обновлениями «по воздуху», **закрыт план техдолга**. Ранее в 2.9: голосовой ввод
«Вектор слушает» (Whisper, локально), локальный ИИ Ollama, скачок по безопасности/152-ФЗ
(SQLCipher, ГОСТ-хеш на C-скорости, passkey/Face ID, аудит-лог), PWA, CI.
Реальные данные колледжа появятся после покупки журнала вузом.

## 2.9 — Надёжность данных: оценки привязаны к студенту, а не к его фамилии

### Смена фамилии больше не «теряет» оценки
Раньше оценка опознавалась по **написанию ФИО**. Стоило исправить опечатку в фамилии или
внести смену фамилии после замужества — и вся история оценок оставалась привязана к старому
написанию, то есть у студента «пропадала». Теперь оценка привязана к **неизменяемому
идентификатору** студента, а ФИО хранится рядом только для отображения.

- Переименование стало безопасной операцией: меняются два поля, история остаётся на месте.
  Прежде она физически переносилась на новые ключи — при сбое посреди переноса часть оценок
  могла осиротеть.
- Перевод накопленных данных сделан отдельными скриптами с **предварительным отчётом**:
  сколько записей привязано, а какие требуют ручного разбора и почему (нет такого студента
  в справочнике, полные тёзки). На боевой базе привязались **все 47 записей**.
- Полных тёзок система **не угадывает**: если различить некого, связь остаётся прежней и
  попадает в отчёт. Приписать оценку не тому студенту хуже, чем оставить как было.

### Синхронизация: отправляем только изменения
Раньше каждый цикл отправлял на сервер **полный снимок** локальной базы: сервер применял
только изменившееся, но объём трафика рос вместе с числом занятий и оценок. Теперь уезжает
только дельта. Отдельно предусмотрены три страховки от потери правок — на случай гонки
«правка ровно в момент отправки», отхода системных часов назад и разрыва связи; плюс
периодический полный снимок как самоизлечение.

### Безопасность доступа к серверу
- Вход на сервер **по паролю закрыт** — только SSH-ключ. По root-аккаунту шло около
  **5000 попыток подбора в сутки**; пароль был лишь второй, более слабой дверью.
- Автоматическая уборка счётчиков анти-брутфорса (они росли безгранично) и скользящее окно
  подсчёта неудач: редкие опечатки живого пользователя больше не складываются в блокировку.

### Прочее
- Тесты: **235** клиентских и **113** серверных.
- Исправлена изоляция тестов: прогон больше не затирает рабочий список предметов.

## 2.9 — Анимированный маскот, мобильное приложение, техдолг

### Маскот «Вектор» ожил (анимация Арины)
- **Четыре анимированных состояния** вместо статичных картинок: покой (уши/хвост), приветствие
  (машет), обдумывание, речь. Исходники — рисованные ролики Арины с зелёным хромакеем.
- **Один файл на все платформы.** Конвейер `tools/build_mascot_anim.py`: хромакей + деспилл
  (гашение зелёного отлива по контуру) + общий кроп (маскот не «прыгает» при смене состояния)
  → **анимированный WebP с альфа-каналом**. Тот же файл играет и в браузере (сайт + мобильное
  приложение), и в Qt на десктопе (`QMovie`) — отдельных версий под платформу нет.
- **Речь собрана из двух слоёв:** ролик «говорит» нарисован как отдельная голова, поэтому
  говорящая голова монтируется поверх спокойного тела — тело живёт, рот двигается, шва нет.
- **Покой с паузой.** Анимация покоя не крутится без остановки (это «моргало»): движение →
  пауза ~2 c → снова движение.
- **Экран входа (ПК и сайт):** Вектор машет при появлении окна, через 1.6 c уходит в покой,
  при наведении мышки задумывается и показывает облачко с советом.
- **В чате:** на «привет» сначала машет рукой, потом отвечает; думает, пока считает; говорит,
  пока отдаёт ответ. Эмоции по успеваемости (30 спрайтов «морда+жест») сохранены на дашборде.
- Вычищен артефакт рендера (лишние пиксели в углу кадра обдумывания).

### Мобильное приложение (Android)
- Приложение на **Capacitor** — оболочка над веб-редакцией: `web/android`, `applicationId
  ru.esstu.gradebook`, подписанный release-APK. Подготовлена публикация в **RuStore**
  (скриншоты витрины 1080×1920, 9:16).
- **Обновления «по воздуху» (Capgo, self-hosted):** сервер отдаёт манифест `/app/updates` и
  zip-бандл `/app/bundles/<версия>` (`server/app/routers/appupdate.py`). Новый интерфейс
  приезжает на телефоны **без переустановки APK** и без модерации магазина.

### Вектор: исправлена выдумка на сайте (анти-галлюцинация)
- **Баг:** на приветствие/справку сайт отвечал шаблоном с пропусками — «Средний балл по
  группам: [укажите средние баллы]». Причина: сервер гнал через LLM интенты, где цифр нет
  вовсе (`hello`/`help`), а есть лишь ПЕРЕЧЕНЬ названий метрик; модель послушно «озвучивала
  данные» и дописывала плейсхолдеры. Десктоп такой guard имел с самого начала
  (`vector/engine.py::ask`), при портировании на веб его забыли перенести.
- **Фикс:** восстановлен паритет с десктопом — `_NO_VOICE_INTENTS` (приветствие, справка,
  благодарность, факты о ВСГУТУ) отдаются как есть, LLM озвучивает **только ответы с
  реальными числами**. Промпт дополнен прямым запретом плейсхолдеров и заглушек.
- **Закрыто тестом** `test_static_intents_are_not_voiced_by_llm`: мок LLM проверяет, что
  статичные интенты идут мимо модели, а ответ с цифрами — через неё.

### Техдолг: план `docs/TECH-DEBT-PLAN.md` закрыт
- **Row-scope ПДн в синке (152-ФЗ).** Студент получает только своё (свою строку, свою группу,
  свои оценки), преподаватель — только свои группы/предметы и ростер своих студентов; чужие
  хеши паролей и секреты ИИ не покидают сервер. Админ по-прежнему получает всё.
- **kv-JSON → нормальные таблицы.** Группы и пользователи переехали из зашифрованных
  JSON-блобов в таблицы `groups`/`users`; слой-переводчик в синке удалён (прямой upsert, как у
  занятий). ПДн остались зашифрованными: служебные колонки открыты, payload — Fernet+DPAPI.
  Бонус: отчество студентов и кураторские группы теперь синхронизируются.
- **Дублирование Python↔JS закрыто контрактами.** Правила «завалена ли оценка», пересдач и
  выбора эмоции маскота проверяются ПАРНЫМИ тестами против общих golden-файлов
  (`docs/contracts/`) — молчаливое расхождение десктопа и сайта теперь невозможно.
- **Веб:** браузерные `alert/confirm/prompt` заменены на модалки и тосты (~30 мест).
- **Качество:** линтер `ruff` (+bugbear) и `mypy` в CI; починены реальные находки (дубль роутов,
  `zip` без `strict`, `raise` без `from`). Диагностические `print` (101 шт.) переведены на
  файловый логгер — в .exe без консоли диагностика больше не теряется.

### Десктоп
- **Журнал, ведомость и аттестация — как на сайте**, с учебными семестрами; итоговые оценки
  (`term_grades`) синхронизируются между ПК и сайтом. Экспорт ведомостей в Excel и Word.
- Журнал студента переделан из карточек-предметов в таблицу; добавлен переключатель
  «считать Н как 2».

### Синк: пограничная запись больше не теряется
- **Дельта-pull отсекал запись, чья метка совпала с меткой клиента.** Фильтр стоял строгий
  (`updated_at > since`), хотя правило синка — «лучше отдать повторно, чем потерять»
  (применение идемпотентно). Если push и pull попадали в один тик часов (на Windows они
  дискретны до ~16 мс), запись выпадала из дельты НАВСЕГДА — до своего следующего
  изменения: оценка могла не доехать до второго ПК. Теперь `>=`.
- Тест `test_delta_pull_does_not_lose_boundary_record` берёт метку клиента РАВНОЙ метке
  занятия и требует, чтобы оно пришло. Тесты дельты больше не зависят от гонки часов
  (перестали «моргать» в CI).

### Безопасность зависимостей веба
- **0 уязвимостей** вместо 8 (6 high + 2 moderate). Из зависимостей убран `@capacitor/assets`
  — разовый генератор иконок, который тянул уязвимый `node-tar` без доступного фикса; теперь
  запускается через `npx` по необходимости. Остальное закрыто `npm audit fix`.

### Паритет сайта с десктопом закрыт
- Цель «Desktop = Web» достигнута: сайт умеет то же, что десктоп. План `web/PARITY-PLAN.md`
  выполнен и удалён — он давно описывал уже неактуальные разрывы и только вводил в заблуждение.
  Расхождения по конкретной функции теперь заводятся обычной задачей, а не «разрывом паритета».

## 2.9 (ранее) — Голосовой ввод, локальный ИИ, аудит

### Голосовой ввод «Вектор слушает» (Speech-to-Text, Whisper)
- **Кнопка микрофона во всех окнах Вектора** (десктоп): нажал → говоришь → нажал (стоп) →
  распознавание. Полностью **локально** (OpenAI Whisper через faster-whisper) — аудио
  никуда не уходит (ПДн, 152-ФЗ), работает офлайн. Русский, модель `large-v3` (макс.
  точность). `vector/stt.py`, `vector/audio_capture.py`, `vector/voice_ui.py`.
- **GPU-ускорение** (CUDA) с авто-фолбэком на CPU; на Windows корректно подхватываются
  cuBLAS/cuDNN (в т.ч. транзитивная зависимость cudnn→cublas через PATH). Прогрев модели
  начинается в момент записи — команда распознаётся без ожидания загрузки.
- **Роли:** студент/админ — голосом задают ВОПРОСЫ (средний балл, долги, список группы) →
  обычный Q&A Вектора. Преподаватель — ещё и КОМАНДЫ записи («Гордееву пять», «Петров
  болеет»): распознаётся детерминированным парсером и **всегда подтверждается вручную**.
- **Безопасность оценки — без галлюцинаций:** разбор команды препода делает
  ДЕТЕРМИНИРОВАННЫЙ парсер (`vector/voice_command.py`), а не LLM. Нечёткое сопоставление
  фамилии с реальным ростером; при любой неоднозначности (две оценки, оценка+пропуск,
  оценка вне 2–5, однофамильцы) — переспрос/выбор, а не догадка. Вопрос со словом «пропуск»
  не станет случайной записью. 50 тестов (`tests/test_voice_command.py`).
- **Выбор микрофона** в Профиле (десктоп) и в настройках STT (админ). Тумблер «Включить
  голосовой ввод» — в админке, синхронизируется на все аккаунты, держится до выключения.
- **Веб-заготовка:** серверный `/web/vector/stt` — распознаёт на ХОСТЕ (когда на ПК ВСГУТУ
  поставят faster-whisper); без движка отвечает 503, кнопка на сайте не показывается.

### Локальный ИИ (Ollama) — выбор модели под видеокарту
- **Пикер моделей Ollama по объёму VRAM** в настройках Вектора (3B для 6 ГБ … 14B для 12 ГБ),
  статус движка, устройство. Проверено вживую: озвучка фактов через `qwen2.5:3b` (~0.8с),
  факты из SQL — модель только переформулирует (анти-галлюцинация).

### Аудит проекта: критичные фиксы
- **Синк: устранён риск потери офлайн-правок при реконсиляции.** `reconcile()` теперь
  ОТПРАВЛЯЕТ локальные изменения ДО очистки кэша (иначе офлайн-оценки препода на клиентском
  ПК могли пропасть до синхронизации). При неудачном push кэш не стирается.
- **Безопасность: закрыт обход серверного анти-брутфорса через X-Forwarded-For.** IP клиента
  берётся из доверенного `X-Real-IP` (ставит Caddy) / последнего хопа XFF, а не подделываемого
  первого. Caddyfile: `header_up X-Real-IP {remote_host}`.
- **Быстрое закрытие приложения:** синк на выходе сначала проверяет доступность сервера
  (health, 3с) и не вешает закрытие, если сервер недоступен.
- **Вектор (десктоп):** преподу — только его группы; ответ по названной фамилии после списка
  должников; голосовая правка сразу видна в открытом журнале; футер входа по центру карточки.

## 2.9 (ранее) — Вектор 1:1 на вебе, безопасность/152-ФЗ, PWA, passkeys, CI

### Безопасность и 152-ФЗ
- **Шифрование БД сервера при хранении — SQLCipher (AES-256).** Весь файл серверной БД
  зашифрован на диске (ПДн at rest): без ключа не прочитать. Ключ — 64 hex в `server/.env`
  (chmod 600). Прозрачно (схема id не меняется); без ключа/драйвера — обычный SQLite
  (dev/Windows, тесты не ломаются). Миграция plaintext→encrypted — `server/encrypt_db.py`.
  На боевом сервере включено и проверено.
- **ГОСТ-хеш пароля на C-скорости** — на боевом VPS поднят OpenSSL GOST-провайдер
  (`libengine-gost-openssl`), хеш считается на скорости C вместо pure-Python. Фикс детекции
  (`hashlib.new` вместо `algorithms_available` — на OpenSSL 3.0 ГОСТ-дайджест `md_gost12_512`
  доступен для new(), но не в наборе). Старые хеши совместимы. Подключено изолированно
  (OPENSSL_CONF в systemd), системный `openssl.cnf` не тронут; certified — позже через ViPNet.
- **Вход по passkey (WebAuthn)** — Face ID / отпечаток / ключ доступа без пароля
  (`/auth/webauthn/*`, `server/app/routers/webauthn_router.py`, модель `WebAuthnCredential`).
  Веб: кнопка на входе + управление ключами в профиле; Credential Management API для
  сохранения пароля (биометрический автозаполнитель).
- **Персистентный журнал аудита** (ФСТЭК №21) — append-only таблица `audit_events`
  (`server/app/audit.py`): входы/выходы, изменения оценок и ПДн, регистрации; переживает
  рестарт. Просмотр — `/web/admin/audit`. Аудит НЕ роняет бизнес-операцию.
- **HTTP security-заголовки** (Caddy): HSTS, X-Frame-Options, nosniff, CSP, Referrer-Policy.
- Телефон в заявках на регистрацию — шифруется ГОСТ (`server/app/gost.py`); анти-брутфорс
  на восстановление пароля + анти-энумерация.

### Вектор на сайте — 1:1 с десктопом
- **LLM-озвучка на сервере** (`server/app/vector_llm.py`): факты считает SQL, LLM
  (GigaChat/Ollama/оффлайн) только переформулирует. Оффлайн/ошибка → откат на факты.
  VPS в РФ → GigaChat работает.
- **Настройки ИИ в веб-админке** (`/web/admin/ai-config`, `AdminAiSettings.vue`): провайдер,
  ключ+scope GigaChat, модель Ollama, проверка связи. Хранятся в той же строке `config`,
  что и десктоп → **ключ синхронизируется в обе стороны**.
- **Боковой Вектор-док** — постоянная панель-чат справа на всех страницах (десктоп), общая
  переписка со вкладкой ИИ (Pinia-store); можно скрыть/вернуть. На мобиле — крупный маскот
  во вкладке. Быстрые команды 1:1 с десктопом (`vector/faq.py::QUICK_COMMANDS`).

### Устойчивость, PWA, деплой, CI
- **Синк устойчивее**: раздельные таймауты (connect 5с/read 30с), экспоненциальный бэкофф,
  индикатор онлайн/офлайн в шапке.
- **PWA** — сайт устанавливается как приложение (manifest + service worker, офлайн-оболочка,
  иконки). Фикс отравления кэша SW (маскот — network-first, HTML в кэш не кладём).
- **CI** (`.github/workflows/ci.yml`): compileall + серверные (56) + клиентские (65) тесты
  на каждый push. Статический тест «QScrollArea без setWidget».
- **Надёжный деплой веба** (`deploy/deploy-web.sh`): один tar.gz + атомарная подмена;
  установщик «одна флешка» (`deploy/install.sh` + `make-installer.sh`).

### Десктоп
- Раздел **«Запросы на регистрацию»** (1:1 с сайтом), контакты у студентов/преподавателей
  (логин/телефон/IP/последний вход), раздел **«Сервер и сайт»** переписан (статус по
  доступности, единый адрес, выбор SQLite/PostgreSQL). Версия 2.7 → 2.8/2.9. Фиксы:
  `sync_runner.flush`, стиль QTextEdit, гонки виджетов, пустая вкладка сервера.

## 2.8 — монорепо, Web Edition, запись из веба, фиксы синка

- Обновлены внутренние заметки (под монорепо и реальное состояние) и добавлен

### Web Edition (Vue 3 + Vite + Pinia + Tailwind, `web/`)
- Экран входа: живой canvas-фон (порт `AnimatedBackground` — соты + сеть-созвездие +
  частицы + пятна), крупный Вектор с плавным дыханием (GPU-слой), брендинг в углу, футер,

## 2.6.1 — постоянная связь с хостом, надёжная отправка темы

### Фоновый сервер хоста + постоянная serveo-ссылка
- **Проблема.** Сервер крутился ВНУТРИ программы (uvicorn в потоке), а serveo-ссылка без
  постоянного имени была случайной при каждом запуске. Поэтому при закрытии программы /
  перезапуске для смены аккаунта сервер и туннель умирали, а serveo выдавал новую ссылку —
  «нужно делать ссылку заново».
- **Решение — фоновый сервер.** Сервер и ssh-туннель теперь ОТДЕЛЬНЫЕ процессы (detached:
  на Windows `DETACHED_PROCESS|CREATE_NEW_PROCESS_GROUP|CREATE_NO_WINDOW`), которые
  ПРОДОЛЖАЮТ работать, когда программа закрыта и при смене аккаунта. PID пишутся в файлы
  (`server/server.pid`, `server/tunnel.pid`), логи — в `server.log`/`tunnel.log`. При старте
  программа ПОДХВАТЫВАЕТ уже запущенные процессы (по `/health` и живому PID), не плодя второй.
  Закрытие программы их больше НЕ гасит — останавливает только кнопка «Остановить»
  (`server_control.stop_processes`).
- **Постоянная ссылка.** `ensure_tunnel_name` гарантирует стабильное имя поддомена
  (`gradebook-<hex>`, хранится в `.env`), а адрес вычисляется детерминированно —
  `https://<name>.serveo.net` (`public_tunnel_url`). Ссылка не меняется между запусками и при
  смене аккаунта; обновлять её клиентам не нужно.
- **Запуск процесса сервера:** dev — `python server/run.py`; собранный `.exe` — тот же exe с
  флагом `--run-server` (внешнего python в сборке нет, поэтому сервером выступает наш же exe).
  ssh берётся системный (встроен в Windows 10/11). Новое: `server_control.start_server_process`/
  `start_tunnel_process`/`stop_processes`/`tunnel_alive`/`ensure_tunnel_name`/`public_tunnel_url`
  + PID-хелперы; `main.py` `--run-server`; на выходе программа больше не гасит туннель.
- Тесты — `tests/test_server_control.py` (имя/ссылка/PID-хелперы; процессы не поднимаются).
- ⚠️ Фоновый сервер живёт, пока его не остановят кнопкой «Остановить» (или `taskkill`).

### Персистентный вход + реконсиляция локальных данных (фикс «фантомных» записей)
- **Баг.** После обновления препод видел «фантомного» студента в пустой группе. Корень —
  слияние с сервером аддитивное (`sync_engine._merge_by_key`): локальная запись убирается
  только по серверному надгробию, поэтому запись, оставшаяся ТОЛЬКО локально (от прежнего
  аккаунта/сессии или после миграции), «протекала» в следующий аккаунт на этом ПК.
- **Реконсиляция «сервер = истина», только онлайн.** На входе/старте (КЛИЕНТ, онлайн):
  стираем синхронизируемый кэш и делаем ПОЛНЫЙ pull — локаль точно соответствует серверу,
  орфаны исчезают (`data_store.reset_synced_local_data` + `sync_engine.reconcile`). На выходе
  (КЛИЕНТ, онлайн): сперва push правок на сервер, затем сброс кэша — чистый старт для
  следующего пользователя без потери правок. **Офлайн — локаль НЕ трогаем** (offline-first,
  без пустого экрана). **ХОСТ (админ) от сброса освобождён** — он источник данных для сервера.
  Сбрасываем только синхронизируемое (students/teachers/groups/предметы/занятия/оценки + метку
  дельты); локальные настройки (`_local:` — адрес, device_id, токен, сессия, тема) сохраняются.
- **Персистентный вход.** После входа сессия запоминается (`app_settings.set_saved_session` —
  логин+роль, БЕЗ пароля); при следующем старте программа сама восстанавливает аккаунт по
  СОХРАНЁННОМУ JWT-токену (`main_window._maybe_restore_session` → реконсиляция → дашборд), не
  показывая экран входа. Токен протух (~12 ч) или явный «Выход» → снова экран входа. Синк
  работает по токену (`sync_runner.start(login, "", role)`); пароль не хранится.
- Новое: `DBManager.clear_synced_tables`, `data_store.reset_synced_local_data` /
  `lookup_session`, `sync_engine.force_full_pull` / `reconcile`,
  `app_settings.get/set/clear_saved_session`. Тесты — `tests/test_session_reset.py`.
- ⚠️ Осознанный размен: офлайн-правки, не успевшие уйти на сервер до выхода/закрытия, при
  следующем ОНЛАЙН-входе будут стёрты реконсиляцией (выбран режим «сервер = истина, онлайн»).

### Подтверждение подключения устройств (барьер device approval)
- **Зачем.** Раньше любой ПК, знающий адрес сервера и валидные логин/пароль из БД,
  синхронизировался без какого-либо одобрения. Теперь новый ПК сначала ЗАПРАШИВАЕТ
  доступ, а администратор на хосте решает — принять (выдать код) или отклонить.
- **Поток.** Окно подключения на новом ПК показывает его **IP** и телефон поддержки,
  при «Подключиться» шлёт `POST /connect/request` (сервер видит IP) → у админа во
  вкладке **«Запросы на подключение»** появляется строка (имя ПК + IP) с кнопками
  **Принять/Отклонить** → «Принять» генерит **6-значный код** (админ диктует его
  пользователю) → пользователь вводит код (`/connect/verify`) → «Подключение успешно»,
  дальше обычный вход логином/паролем. «Отклонить» убирает строку и показывает юзеру
  «Подключение отклонено».
- **Жёсткий барьер на сервере.** Одобренные устройства лежат в БД (таблица
  `approved_devices`, переживает перезапуск); ожидающие запросы и коды — в памяти
  (`server/app/connect.py`, как `events.py`/`throttle.py`). Сервер ОТКАЗЫВАЕТ (`403`)
  неодобренным устройствам на `/auth/login`, `/auth/bootstrap-admin`, `/sync/*`,
  `/me/*`, `/admin/*` (`deps.ensure_device_allowed`). Устройство опознаётся заголовком
  `X-Device-Id` (стабильный `app_settings.get_device_id`, хранится локально).
- **Хост не запирает сам себя.** `server_control` перед запуском сервера выставляет
  `GRADEBOOK_HOST_DEVICE_ID` = device_id хоста; сервер всегда пропускает его (на IP не
  полагаемся — через serveo все клиенты выглядят как loopback). Анти-брутфорс кода:
  TTL ~10 мин + лимит попыток; запросы лимитируются по IP.
- **Эндпоинты:** `/connect/request|status|verify` (без авторизации — калитка ДО входа),
  `/connect/requests|approve|reject` (только админ). Новый роутер `server/app/routers/
  connect.py`, тесты — `server/tests/test_connect.py`.

### Вход через сайт (кнопка — задел на будущее)
- Кнопка **«Войти через сайт»** на окне подключения и на экране входа открывает
  `app_settings.SITE_URL` (меняется в коде; пусто — кнопка скрыта). Сайт в перспективе
  будет на том же сервере, что и БД, и вход на нём не потребует подтверждения. Авто-вход
  обратно в приложение после входа на сайте — отдельная задача (сайта пока нет).

### Постоянная связь с ПК-хостом (автозапуск сервера)
- **Проблема.** Сервер на ПК-хосте жил только пока администратор держал свою сессию:
  стоило выйти из аккаунта или закрыть/открыть программу — сервер для всех «отваливался»,
  и админу приходилось снова входить и жать «Запустить сервер». Из-за этого хост-ПК
  фактически нельзя было выводить из аккаунта админа.
- **Решение — автозапуск сервера на хосте.** Удачный запуск из админки теперь:
  запоминает порт (`GRADEBOOK_SERVER_PORT` в `server/.env`), помечает ПК хостом и
  включает автозапуск (`app_settings.host_autostart`). При следующем старте программы
  `main_window._maybe_autostart_server` в фоне сам поднимает сервер по сохранённой
  конфигурации (`server_control.autostart` — без перезаписи `.env`, для serveo заодно
  туннель), ДО и НЕЗАВИСИМО от входа. Теперь админ спокойно выходит из аккаунта (сервер
  живёт в фоновом потоке-демоне до закрытия программы), а после перезапуска сервер
  встаёт сам. Ручная «Остановить» снимает автозапуск (явная остановка = «больше не
  поднимать сам»).
- **Свой адрес у хоста — всегда `http://127.0.0.1:<порт>`** (сервер локальный): хост
  не гоняет собственный трафик наружу через serveo и не зависит от туннеля. Публичный/
  ЛВС-адрес для ДРУГИХ ПК по-прежнему показывается в сообщении после запуска.

### Надёжная отправка персональной темы (`/me/prefs`)
- Раньше, если в момент «Сохранить» сервер был недоступен или ещё не было токена,
  отправка темы (`POST /me/prefs`) тихо терялась: тема оставалась только локально и не
  «роумилась» на другие ПК. Теперь не доехавшая тема складывается в отложенные
  (`app_settings.set_pending_prefs`, привязка к логину) и до-отправляется при следующей
  удачной синхронизации (`sync_runner._flush_pending_prefs`). `push_my_prefs` стал
  методом менеджера синка (знает логин и сам решает: отправить сейчас или отложить).

## 2.5.2 — хостинг/адрес сервера, усиление входа, мониторинг, ГОСТ-хеш

### Сервер и адрес (убран `api_config.json`)
- Адрес сервера хранится в самой программе (локальный ключ БД, не синхронизируется);
  старый `api_config.json` один раз мигрируется и удаляется.
- Админка → «Сервер»: ВЫБОР ТИПА сервера (Serveo·SQLite / ВСГУТУ·SQLite /
  ВСГУТУ·PostgreSQL) и ОДНА кнопка «Запустить сервер» (движок+сервер+туннель, адрес
  сохраняется сам). Стартовое окно ввода API для клиента (не трогает админа/ПК-хост —
  host-флаг, без замкнутого круга), кнопка «⚙ Сервер» на экране входа. serveo по IPv4 (`ssh -4`).

### Мониторинг для админа (только роль admin)
- Вкладка «Мониторинг»: кто сейчас онлайн + консоль событий/ошибок сервера.
- Сервер: `events.py` (presence + кольцевой буфер в памяти), `/admin/online` и
  `/admin/events` (дельта-опрос); события — входы, отклонённые чужие push-записи,
  старт сервера и непойманные ошибки (через глобальный обработчик → аккуратный 500).

### Усиление входа
- **Хеш пароля — двухэтапный ГИБРИД** `hybrid_sha512_gost512`: этап 1 PBKDF2-HMAC-SHA512
  (200k — основная стойкость) → этап 2 PBKDF2-Стрибог512 по Р 50.1.111-2016 (ГОСТ-прогон).
  ГОСТ-бэкенд авто: OpenSSL GOST-engine/**ViPNet CSP** на бою (C-скорость, юридически
  значимо) → gostcrypto на dev. Формат самоописываемый → старые `pbkdf2_sha256` (200k/600k)
  проверяются, апгрейд без сброса паролей. Совместимость dev↔бой закреплена KAT-вектором
  Р 50.1.111-2016. Хеш — не СКЗИ; сертифицированность даёт только СКЗИ на бою (см.
  `docs/STRIBOG_152FZ_PLAN.md`).
- Переиспользование JWT между запусками (локально, зашифровано) → нет PBKDF2-герда при
  перезапуске; jitter автологина (`GRADEBOOK_LOGIN_JITTER_SEC`).

### Нагрузочный прогон (5000 пользователей, 1 воркер uvicorn + SQLite, dev)
- **Дельта-pull: 87 req/s, p50 1.5 c, >99.7% успеха. Push: 74 req/s, 0 ошибок.** Синк здоров.
- LOGIN — CPU-bound (хеш), worst-case «герд» 5000 свежих входов: p50 ~7 c, 193 c суммарно.
  Микробенч (параллель ×8): **гибрид 32.4 хеш/с — БЫСТРЕЕ старого SHA256-600k (24.5/с)**;
  на бою с C-GOST-движком ~39.7/с (≈как SHA512). Т.е. гибрид не просадка, а ускорение
  (SHA512-200k легче SHA256-600k). Герд сглаживают токен+jitter; для боевых тысяч —
  несколько воркеров uvicorn + PostgreSQL (+ OpenSSL GOST-engine, см. `server/DEPLOY.md`).

## 2.5.1 — серверная безопасность, надёжность синхронизации, QA

Доводка до коммерческой готовности: закрыты блокеры безопасности сервера и сделана
синхронизация быстрой и не теряющей/не путающей данные. Добавлены автотесты.

### Безопасность сервера
- Анти-брутфорс на `/auth/login`: после серии неверных попыток — `429 + Retry-After`,
  ключ блокировки `(IP, логин)` (чтобы нельзя было запереть вход чужому), за обратным
  прокси берётся `X-Forwarded-For` (`server/app/throttle.py`).
- Построчная авторизация push: преподаватель пишет занятия/оценки ТОЛЬКО по своим
  предметам; чужой предмет отвергается.
- HTTPS-готовность клиента: TLS-проверка всегда включена; свой CA для ЛВС —
  `GRADEBOOK_CA_BUNDLE`; при `http://` к удалённому адресу — предупреждение.
- ssh-туннель `serveo` форсит IPv4 (`ssh -4`): при битом/выключенном IPv6 (типично
  для РФ) подключение к serveo.net больше не зависает. Боевой доступ из интернета —
  свой домен + Caddy (авто-HTTPS), см. `server/DEPLOY.md` (7.6); serveo — только
  тест/демо на выдуманных данных (ПДн через зарубежный сервис нельзя, 152-ФЗ).

### Хостинг сервера и адрес сервера (убран `api_config.json`)
- Файл-костыль `api_config.json` больше не создаётся. Адрес сервера хранится «в самой
  программе» — в локальном ключе её БД (не синхронизируется); старый файл при апгрейде
  один раз подхватывается и удаляется. Адрес задаётся через интерфейс, а не правкой
  json руками.
- В админке вкладка «Сервер» → одна кнопка **«Запустить сервер»**: по выбранному ТИПУ
  сервера ставит движок БД, поднимает сам сервер (API) и — для Serveo — открывает
  доступ из интернета, после чего публичный адрес САМ записывается в программу.
- Выбор типа сервера (3 варианта): «Serveo.net · SQLite3», «ВСГУТУ Сервер · SQLite3»,
  «ВСГУТУ Сервер · PostgreSQL».
- Стартовая проверка адреса: если адрес не задан, клиент при запуске получает окно
  «введите API сервера для синхронизации» (через Serveo адрес меняется каждый раз).
  Окно НЕ трогает администратора/ПК-хост (иначе замкнутый круг: адрес появляется
  только после запуска сервера) и всегда закрываемо («Позже» / «Работать офлайн»).
  Сменить адрес можно и со страницы входа (кнопка «⚙ Сервер») — без захода в админку.

### Безопасность входа (PBKDF2 600k, jitter, переиспользование токена)
- PBKDF2-HMAC-SHA256 поднят со 200 000 до **600 000 итераций** (рекомендация OWASP 2023),
  и на клиенте, и на сервере. Подъём обратносовместим: `verify_password` берёт число
  итераций из самого хеша — старые хеши (200k) проверяются по-прежнему, новые/изменённые
  пароли считаются с 600k. Соль — 128 бит из CSPRNG.
- Переиспользование JWT между запусками: валидный токен сохраняется локально
  (зашифрованным, привязан к логину) и при следующем старте берётся вместо входа по
  паролю — это убирает повторный PBKDF2 на сервере при каждом перезапуске (главный
  источник утреннего «герда» входов). Протух — сервер отдаёт 401, клиент тихо
  перелогинивается и сохраняет свежий токен.
- Jitter автологина: случайная задержка 0..N c перед входом по паролю размазывает
  одновременный пик входов многих ПК (offline-first — задержка фоновая, незаметна).
  N задаётся `GRADEBOOK_LOGIN_JITTER_SEC` (по умолчанию 8 c; 0 — выключить).

### Надёжность синхронизации
- Дельта-pull: клиент тянет только изменения позже метки `last_sync` (первый pull
  сессии — полный, для самоизлечения). Метку ставит сервер (до выборки). Полный pull
  каждый цикл убран — это снимало главный тормоз (на 1000 пользователей p50 ~29 c → ~2.5 c).
- Надгробия оценок и занятий: удаление распространяется на все ПК и не «воскресает».
  Исправлен баг: удалённое занятие возвращалось после перезагрузки журнала (удаление
  не доходило до БД). Удаление студента надгробит и его оценки.
- Устранён self-wake синхронизации: применение серверных данных больше не будит синк
  (раньше apply_remote → пробуждение → синк → apply_remote крутились без пауз).
- Пул соединений сервера поднят до 200 и включён WAL/`busy_timeout` (был потолок 60 —
  под нагрузкой вход «висел» до таймаута).

### Сохранность данных
- Оценки в журнале преподавателя пишутся на диск СРАЗУ (на каждое действие), а не
  только по кнопке «Сохранить» — смена группы/предмета и закрытие больше не теряют правки.
- Авто-бэкап локальной базы по расписанию (раз в 30 минут и при старте), а не только
  «на выходе» — защита от потери при аварийном завершении.

### Качество (автотесты — их в проекте не было)
- Серверный pytest (`server/tests/`): health, bootstrap, анти-брутфорс, push/pull,
  дельта, надгробия, row-scope.
- Клиентский pytest (`tests/`): надгробия, дельта-метка, отсутствие self-wake,
  персистентность по действию, авто-бэкап.
- Сквозной тест двух устройств через живой сервер (`tests/e2e_sync.py`): данные
  совпадают и не путаются, удаления распространяются.
- Нагрузочный тест (`server/tests/loadtest.py`): реальный uvicorn + asyncio,
  проверен до 5000 пользователей.

### Масштаб (известное ограничение)
- На ОДНОМ воркере uvicorn + SQLite дельта-синхронизация тянет тысячи пользователей
  (5000: pull p50 ~2.5 c, push ok, >99% успеха). Но одновременный «герд» из тысяч
  ВХОДОВ упирается в CPU (PBKDF2 600k — требование защиты ПДн, не ослабляем; герд
  смягчён переиспользованием токена и jitter, см. «Безопасность входа»). Для
  боевой нагрузки в тысячи — несколько воркеров uvicorn (`--workers N`) + PostgreSQL
  (общая БД; несколько процессов не делят SQLite). См. `server/DEPLOY.md` (7.3).

### Известная находка на будущее (не входит в 2.5.1)
- Оценки/студенты ключуются по ФИО, а не по стабильному логину: два студента с
  одинаковыми ФИО в одной группе схлопнутся, переименование сиротит оценки. Задача
  на отдельный заход — перевести ключ оценок на `login` (затрагивает схему и grading).

## Устойчивость синхронизации (clock skew, конфликты оценок)
- **Метки времени — в UTC** на клиенте и сервере единым форматом (`…+00:00`):
  раньше использовалось локальное время, и расхождение часов на ПК ломало
  сравнение «кто новее» в LWW. Затронуты `data_store`, `core`, `sync_engine` и
  серверные `routers/sync.py`, `routers/auth.py`.
- **Метку времени ставит СЕРВЕР** (а не клиент): на `/sync/push` сервер штампует
  `updated_at` временем приёма. Это убирает зависимость от часов на машинах
  преподавателей (clock skew) — правило становится «последняя дошедшая до сервера
  правка побеждает». Чтобы дельта-синк не гонял всё каждый цикл, сервер штампует и
  применяет только реально изменившиеся записи (push идемпотентен: повтор тех же
  данных = 0 изменений).
- **Детектор конфликтов оценок вернулся в API-синк.** В `sync_engine._merge_grades`
  расхождение значения оценки (серверное не старше локального) пишется в
  `sync_conflicts` и НЕ затирает работу преподавателя — он решает вручную
  (`conflict_dialog`). Совпадение значений и более новая локальная правка
  конфликта не создают.

## Сервер на ПК администратора (хостинг из админ-панели)
- Новый модуль `server_control.py`: из десктопа можно поднять сервер
  синхронизации прямо на этом ПК — записать `server/.env`, выбрать движок БД,
  проверить подключение и запустить/остановить `uvicorn` **внутри самой программы**
  (отдельным потоком — внешний Python не нужен; сервер живёт, пока открыта прога).
- Вкладка «Сервер» в админке: карточка «Этот ПК как сервер» — выбор **SQLite
  (по умолчанию)** или **PostgreSQL** (с реквизитами и проверкой подключения),
  кнопки запуска/остановки и индикатор состояния (по `/health`). Нужна только на
  одном ПК-хосте; клиентам по-прежнему достаточно указать адрес сервера.
- Безопасность: секрет JWT генерируется автоматически (не дефолтный), `server/.env`

## Мульти-ПК без мастер-ключа (простой UX для коммерции)
Учителя и студенты просто запускают программу и входят по своим логину/паролю —
никаких «паролей установки» и мастер-ключей. Реализация:
- В общую базу PostgreSQL значения kv_store пишутся ОТКРЫТЫМ текстом → читаются
  на любом ПК без ключа. Безопасность общей базы: учётная запись PostgreSQL
  (её пароль на диске под DPAPI), TLS-канал (sslmode), сервер в РФ, контроль
  доступа. Пароли пользователей всегда только хешами (PBKDF2).
- Локально в SQLite те же значения ШИФРУЮТСЯ ключом этого ПК (DPAPI, привязка к
  учётной записи Windows) — автоматически, без ввода. Защищает данные на
  украденном/чужом компьютере.
- Добавлен sslmode к подключению PostgreSQL (по умолчанию prefer; для боевого
  сервера — require) — шифрование ПДн при передаче.
- На экране входа — подсказка для студентов/преподавателей.
- Отменён ранее добавленный «общий ключ организации» (keyvault) с паролем
  установки — для коммерческого продукта это лишняя сложность для пользователей.

## ФИКС: синхронизация с PostgreSQL вообще не включалась

таблице install_keys». Но кода, который добавляет/активирует ключ, в проекте не
было: проверка всегда возвращала False, поэтому PostgreSQL не подключался никогда,

- Теперь синхронизация включается, как только админ прописал сервер и

- Удалён мёртвый код недоделанного лицензирования: `is_key_activated`,

## Аудит и защита от перебора (приказ ФСТЭК №21)

преподавателя. В журнале — кнопка «⚠ Конфликты (N)» и окно выбора верного значения
(conflict_dialog.py).

DBManager.backup() копирует базу в …/GradeBookAI/backups/ с меткой времени, хранит
последние 30. Срабатывает перед загрузкой из PG, при выходе из программы и по кнопке
«🗄 Бэкап». Есть restore() и list_backups().

## 4. SQLite только на локальном диске (core.py)
База теперь всегда в локальной user-папке (%LOCALAPPDATA% / ~/.local/share/GradeBookAI),
никогда на сетевой шаре. Добавлены детект сетевого пути с предупреждением и
PRAGMA WAL + busy_timeout против блокировок и порчи.

## 5. Валидация дат (ui_date.py)
Свободный ввод «дд.мм.гггг» заменён диалогом-календарём (QDateEdit). Кривую дату
(31.02, «завтра», пустую) ввести физически нельзя. Все вводы дат в журнале препода
переведены на него. parse_date/normalize_date проверяют реальный календарь.

## 6. Единая методика среднего балла (grading.py)
Формула вынесена в один модуль — его зовут и core.calculate_average, и Вектор
(расхождение теперь невозможно). Вес пропуска «Н», учитывать ли пропуск и включать ли
экзамены — настраивается (config), дефолты сохраняют прежнее поведение, методика

# Итерация 3 — PostgreSQL вместо GitHub, вход по логину/паролю, хеширование

## GitHub удалён полностью
Файл `github_storage.py` удалён. Вместо него — `data_store.py`: то же
key-value-хранилище (students/teachers/groups/config/journals), но на
**PostgreSQL + SQLite**, без обращений в интернет.
- Рабочее чтение/запись — локальный SQLite (мгновенно, не блокирует интерфейс).
- При настроенном PostgreSQL запись дублируется в PG асинхронно (PGSyncer),
  при старте данные подтягиваются из PG в SQLite. Все ПК колледжа — одна база.
- **Побочный эффект:** админ-панель больше не виснет на старте (раньше она
  синхронно лезла в GitHub). Проверено: создаётся за ~0.2 с.

## Хеширование паролей
Пароли НЕ хранятся в открытом виде. `security.py`: `hash_password` /
`verify_password` (PBKDF2-HMAC-SHA256, 600 000 итераций — OWASP 2023, случайная
128-битная соль; число итераций хранится в хеше, поэтому подъём со 200k обратносовместим).
`data_store` хеширует пароль прозрачно при записи (поле `password` → `password_hash`).

## Вход по логину и паролю
- Единая форма входа: **Логин + Пароль + «Войти»** (вместо вкладок Ученик/Учитель
  и ввода ФИО). Роль (студент/учитель/админ) определяется автоматически по логину.
- `data_store.authenticate(login, password)` — единая точка проверки.
- Убран скрытый вход админа «5 кликов» (давал доступ без пароля). Админ входит
  через обычную форму своими учётными данными.

# Итерация 4 — Брендинг ВСГУТУ и шифрование данных

## Надпись «Технологический колледж ВСГУТУ»
Добавлена в трёх местах: на экране входа (бирюзой под подзаголовком),
в шапке приложения (под «GRADEBOOK») и в заголовке окна.

## Шифрование данных на диске
Все значения в хранилище (kv_store: роутер студентов с ФИО, учётки
преподавателей, журналы, API-ключ) теперь **шифруются** при записи
(Fernet/AES, см. security.py: encrypt_value / decrypt_value).
- Ключ шифрования хранится в ОТДЕЛЬНОМ файле `data.key` (в APPDATA\GradeBookAI),
  НЕ в базе. Поэтому украденный файл базы без ключа нечитаем.
- Приложение расшифровывает прозрачно — остальной код не изменился.
- Старые незашифрованные записи читаются как есть и шифруются при следующей записи.

Проверено: в файле базы ФИО и API-ключ лежат как `enc:...` (нечитаемо),
приложение и вход работают.

⚠️ **Важно для нескольких ПК:** файл `data.key` должен быть ОДИНАКОВЫМ на всех
ПК колледжа (иначе ПК не расшифрует общие данные из PostgreSQL). Скопируйте его
на все машины вместе с программой.

## Честно о границах защиты (важно!)
Зашифрован реестр студентов/учителей, журналы и API-ключ (kv_store).
**НЕ зашифрованы пока** рабочие таблицы журнала (`students`, `grades`) в локальном
SQLite-кэше — там ФИО и оценки лежат открытым текстом, потому что по ним идут
связи (join) и их шифрование требует детерминированной схемы (отдельная задача).
Для боевого режима эти данные защищаются на уровне сервера PostgreSQL:
ограничение доступа к БД + шифрование диска сервера (см. дорожную карту, 152-ФЗ).
