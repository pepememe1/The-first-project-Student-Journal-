# GradeBookAI — Release 2.5 (список изменений с 2.4.2)

Кратко: пройден аудит безопасности и соответствия 152-ФЗ, и заложена клиент-
серверная архитектура «прога + сайт» с offline-first синхронизацией через API.
Подробности — в секциях ниже.

---

## 2.5.1 — серверная безопасность, надёжность синхронизации, QA

Доводка до коммерческой готовности: закрыты блокеры безопасности сервера и сделана
синхронизация быстрой и не теряющей/не путающей данные. Добавлены автотесты.

### Безопасность сервера
- Анти-брутфорс на `/auth/login`: после серии неверных попыток — `429 + Retry-After`,
  ключ блокировки `(IP, логин)` (чтобы нельзя было запереть вход чужому), за обратным
  прокси берётся `X-Forwarded-For` (`server/app/throttle.py`).
- Построчная авторизация push: преподаватель пишет занятия/оценки ТОЛЬКО по своим
  предметам; чужой предмет отвергается.
- HTTPS-готовность клиента: TLS-проверка всегда включена; свой CA для ЛВС —
  `GRADEBOOK_CA_BUNDLE`; при `http://` к удалённому адресу — предупреждение.
- ssh-туннель `serveo` форсит IPv4 (`ssh -4`): при битом/выключенном IPv6 (типично
  для РФ) подключение к serveo.net больше не зависает. Боевой доступ из интернета —
  свой домен + Caddy (авто-HTTPS), см. `server/DEPLOY.md` (7.6); serveo — только
  тест/демо на выдуманных данных (ПДн через зарубежный сервис нельзя, 152-ФЗ).

### Хостинг сервера и адрес сервера (убран `api_config.json`)
- Файл-костыль `api_config.json` больше не создаётся. Адрес сервера хранится «в самой
  программе» — в локальном ключе её БД (не синхронизируется); старый файл при апгрейде
  один раз подхватывается и удаляется. Адрес задаётся через интерфейс, а не правкой
  json руками.
- В админке вкладка «Сервер» → одна кнопка **«Запустить сервер»**: по выбранному ТИПУ
  сервера ставит движок БД, поднимает сам сервер (API) и — для Serveo — открывает
  доступ из интернета, после чего публичный адрес САМ записывается в программу.
- Выбор типа сервера (3 варианта): «Serveo.net · SQLite3», «ВСГУТУ Сервер · SQLite3»,
  «ВСГУТУ Сервер · PostgreSQL».
- Стартовая проверка адреса: если адрес не задан, клиент при запуске получает окно
  «введите API сервера для синхронизации» (через Serveo адрес меняется каждый раз).
  Окно НЕ трогает администратора/ПК-хост (иначе замкнутый круг: адрес появляется
  только после запуска сервера) и всегда закрываемо («Позже» / «Работать офлайн»).
  Сменить адрес можно и со страницы входа (кнопка «⚙ Сервер») — без захода в админку.

### Безопасность входа (PBKDF2 600k, jitter, переиспользование токена)
- PBKDF2-HMAC-SHA256 поднят со 200 000 до **600 000 итераций** (рекомендация OWASP 2023),
  и на клиенте, и на сервере. Подъём обратносовместим: `verify_password` берёт число
  итераций из самого хеша — старые хеши (200k) проверяются по-прежнему, новые/изменённые
  пароли считаются с 600k. Соль — 128 бит из CSPRNG.
- Переиспользование JWT между запусками: валидный токен сохраняется локально
  (зашифрованным, привязан к логину) и при следующем старте берётся вместо входа по
  паролю — это убирает повторный PBKDF2 на сервере при каждом перезапуске (главный
  источник утреннего «герда» входов). Протух — сервер отдаёт 401, клиент тихо
  перелогинивается и сохраняет свежий токен.
- Jitter автологина: случайная задержка 0..N c перед входом по паролю размазывает
  одновременный пик входов многих ПК (offline-first — задержка фоновая, незаметна).
  N задаётся `GRADEBOOK_LOGIN_JITTER_SEC` (по умолчанию 8 c; 0 — выключить).

### Надёжность синхронизации
- Дельта-pull: клиент тянет только изменения позже метки `last_sync` (первый pull
  сессии — полный, для самоизлечения). Метку ставит сервер (до выборки). Полный pull
  каждый цикл убран — это снимало главный тормоз (на 1000 пользователей p50 ~29 c → ~2.5 c).
- Надгробия оценок и занятий: удаление распространяется на все ПК и не «воскресает».
  Исправлен баг: удалённое занятие возвращалось после перезагрузки журнала (удаление
  не доходило до БД). Удаление студента надгробит и его оценки.
- Устранён self-wake синхронизации: применение серверных данных больше не будит синк
  (раньше apply_remote → пробуждение → синк → apply_remote крутились без пауз).
- Пул соединений сервера поднят до 200 и включён WAL/`busy_timeout` (был потолок 60 —
  под нагрузкой вход «висел» до таймаута).

### Сохранность данных
- Оценки в журнале преподавателя пишутся на диск СРАЗУ (на каждое действие), а не
  только по кнопке «Сохранить» — смена группы/предмета и закрытие больше не теряют правки.
- Авто-бэкап локальной базы по расписанию (раз в 30 минут и при старте), а не только
  «на выходе» — защита от потери при аварийном завершении.

### Качество (автотесты — их в проекте не было)
- Серверный pytest (`server/tests/`): health, bootstrap, анти-брутфорс, push/pull,
  дельта, надгробия, row-scope.
- Клиентский pytest (`tests/`): надгробия, дельта-метка, отсутствие self-wake,
  персистентность по действию, авто-бэкап.
- Сквозной тест двух устройств через живой сервер (`tests/e2e_sync.py`): данные
  совпадают и не путаются, удаления распространяются.
- Нагрузочный тест (`server/tests/loadtest.py`): реальный uvicorn + asyncio,
  проверен до 5000 пользователей.

### Масштаб (известное ограничение)
- На ОДНОМ воркере uvicorn + SQLite дельта-синхронизация тянет тысячи пользователей
  (5000: pull p50 ~2.5 c, push ok, >99% успеха). Но одновременный «герд» из тысяч
  ВХОДОВ упирается в CPU (PBKDF2 600k — требование защиты ПДн, не ослабляем; герд
  смягчён переиспользованием токена и jitter, см. «Безопасность входа»). Для
  боевой нагрузки в тысячи — несколько воркеров uvicorn (`--workers N`) + PostgreSQL
  (общая БД; несколько процессов не делят SQLite). См. `server/DEPLOY.md` (7.3).

### Известная находка на будущее (не входит в 2.5.1)
- Оценки/студенты ключуются по ФИО, а не по стабильному логину: два студента с
  одинаковыми ФИО в одной группе схлопнутся, переименование сиротит оценки. Задача
  на отдельный заход — перевести ключ оценок на `login` (затрагивает схему и grading).

## Безопасность и 152-ФЗ
- Убраны два бэкдора: захардкоженный мастер-пароль (и мёртвый `SecureStorage`) и
  дефолтный пароль администратора `vsgutu_admin_online` (теперь отвергается).
- Пароль администратора задаётся при первом запуске; добавлена смена пароля.
- `cryptography` обязательна (без слабого XOR-фолбэка); ключ шифрования данных
  защищён Windows DPAPI (не лежит открытым текстом, привязан к учётной записи ПК).
- Новый журнал аудита (входы, смена пароля, экспорт ПДн) и анти-брутфорс
  (блокировка логина после серии неверных попыток).
- Обмен с сервером — по HTTPS/TLS; сервер размещается на территории РФ (152-ФЗ,
  ст. 18 ч. 5).

## Архитектура «прога + сайт» (offline-first через API)
- Новый бэкенд `server/` (FastAPI + PostgreSQL/SQLite): авторизация JWT по ролям,
  эндпоинты `/auth/*` и `/sync/pull|push` (дельта, LWW, надгробия).
- Десктоп синхронизируется через API (а не напрямую в БД): `sync_client.py`,
  `sync_engine.py` (перевод данных в обе стороны), `sync_runner.py` (фоновый
  поток), `app_settings.py` (адрес сервера). Offline-first сохранён.
- Учителя/студенты просто входят своими логином/паролем — данные подтягиваются,
  без мастер-ключей и настройки каждого ПК. Прямой PostgreSQL с клиента отключён.
- На клиентах больше не нужен `psycopg2` (нужен только серверу).
- Гайд развёртывания (публичный HTTPS, сервер в РФ) — `server/DEPLOY.md`.

## Портативное хранилище (всё рядом с .exe)
- Новый модуль `app_paths.py` — единый источник правды о путях. Собранный .exe
  держит ВСЕ свои файлы (база, ключ, журналы, бэкапы, api_config.json,
  subjects.json) рядом с собой: папку можно копировать/переносить, это отдельная
  изолированная установка. Две копии в разных папках = два независимых «ПК»
  (честная эмуляция без общей базы и без гонок за один файл).
- Исправлен рассинхрон: ключ шифрования уезжал в `%APPDATA%` (Roaming), а база — в
  `%LOCALAPPDATA%` (Local). Теперь всё в одной папке; добавлена бесшовная миграция
  старого ключа, чтобы существующие данные остались читаемыми.
- Запуск из исходников (dev) по-прежнему пишет в профиль пользователя, чтобы не
  мусорить в репозитории.

## Чистка и фиксы

- Авто-обновление экрана администратора после фоновой синхронизации (лимит #2).
- Версия в заголовке окна — «Release 2.5».

## Финальная чистка наследия (PostgreSQL-клиент, OpenRouter, GitHub)
- Полностью удалён клиентский PostgreSQL: модуль `db_config.py`, класс `PGSyncer`
  и поток `_syncer`, флаг `use_pg`, методы `_pull_from_pg`/`_ensure_pg_tables` и все
  ветки прямой записи в PG в `core.py`/`data_store.py`. Синхронизация — только через

- Полностью убран OpenRouter: удалён `ai_module.py` (`AIWidget`/`AIRequestThread`),

- «Умный совет» на дашборде студента переведён с OpenRouter на Вектора: считается

- Доустранены GitHub-следы в коде (нейминг `get_gh_store`→`get_store`, `_GHWorker`→

- `.gitignore`: убраны неактуальные `pg_config.json` и `install_key.txt`.

## Устойчивость синхронизации (clock skew, конфликты оценок)
- **Метки времени — в UTC** на клиенте и сервере единым форматом (`…+00:00`):
  раньше использовалось локальное время, и расхождение часов на ПК ломало
  сравнение «кто новее» в LWW. Затронуты `data_store`, `core`, `sync_engine` и
  серверные `routers/sync.py`, `routers/auth.py`.
- **Метку времени ставит СЕРВЕР** (а не клиент): на `/sync/push` сервер штампует
  `updated_at` временем приёма. Это убирает зависимость от часов на машинах
  преподавателей (clock skew) — правило становится «последняя дошедшая до сервера
  правка побеждает». Чтобы дельта-синк не гонял всё каждый цикл, сервер штампует и
  применяет только реально изменившиеся записи (push идемпотентен: повтор тех же
  данных = 0 изменений).
- **Детектор конфликтов оценок вернулся в API-синк.** В `sync_engine._merge_grades`
  расхождение значения оценки (серверное не старше локального) пишется в
  `sync_conflicts` и НЕ затирает работу преподавателя — он решает вручную
  (`conflict_dialog`). Совпадение значений и более новая локальная правка
  конфликта не создают.

## Сервер на ПК администратора (хостинг из админ-панели)
- Новый модуль `server_control.py`: из десктопа можно поднять сервер
  синхронизации прямо на этом ПК — записать `server/.env`, выбрать движок БД,
  проверить подключение и запустить/остановить `uvicorn` **внутри самой программы**
  (отдельным потоком — внешний Python не нужен; сервер живёт, пока открыта прога).
- Вкладка «Сервер» в админке: карточка «Этот ПК как сервер» — выбор **SQLite
  (по умолчанию)** или **PostgreSQL** (с реквизитами и проверкой подключения),
  кнопки запуска/остановки и индикатор состояния (по `/health`). Нужна только на
  одном ПК-хосте; клиентам по-прежнему достаточно указать адрес сервера.
- Безопасность: секрет JWT генерируется автоматически (не дефолтный), `server/.env`
  кладётся рядом с сервером и вне Git; пароль PostgreSQL URL-кодируется.
- Tombstone GC (физическая чистка старых надгробий + `VACUUM`) — осознанно
  отложено: задизайнено на будущее, на текущем объёме не критично.

# GradeBookAI — Безопасность и соответствие 152-ФЗ (аудит и усиление защиты)

Пройден аудит репозитория на баги, мёртвый код и соответствие 152-ФЗ. Главное —
убраны два бэкдора, усилено хранение ключей и добавлены аудит и анти-брутфорс.

## Убраны бэкдоры (критично)
- Удалён захардкоженный мастер-пароль администратора (`_get_default_pw`) вместе с
  целиком мёртвым классом `SecureStorage` в security.py. Раньше любой с .exe мог
  расшифровать перенесённые ПДн — обфускация не защищала.
- Удалён дефолтный пароль `DEFAULT_ADMIN_PASSWORD` ("vsgutu_admin_online"), который
  молча принимался при первом входе. Теперь пароль администратора задаётся вручную
  при первом запуске на главном ПК (диалог в форме входа), а на остальных ПК он
  приходит из общей базы PostgreSQL — клиентам ничего настраивать не нужно.
- Добавлена смена пароля администратора в панели (раздел «База данных»).

## Шифрование и ключи
- `cryptography` теперь ОБЯЗАТЕЛЬНА. Слабый самописный XOR-фолбэк удалён —
  при отсутствии пакета приложение честно останавливается с понятным окном
  (раньше молча «шифровало» мусором).
- Ключ шифрования данных (`data.key`) и пароль PostgreSQL (`pg_config.json`)
  больше не лежат открытым текстом: защищены Windows DPAPI и привязаны к учётной
  записи Windows. Старые открытые ключи/пароли читаются и перешифровываются.

## Мульти-ПК без мастер-ключа (простой UX для коммерции)
Учителя и студенты просто запускают программу и входят по своим логину/паролю —
никаких «паролей установки» и мастер-ключей. Реализация:
- В общую базу PostgreSQL значения kv_store пишутся ОТКРЫТЫМ текстом → читаются
  на любом ПК без ключа. Безопасность общей базы: учётная запись PostgreSQL
  (её пароль на диске под DPAPI), TLS-канал (sslmode), сервер в РФ, контроль
  доступа. Пароли пользователей всегда только хешами (PBKDF2).
- Локально в SQLite те же значения ШИФРУЮТСЯ ключом этого ПК (DPAPI, привязка к
  учётной записи Windows) — автоматически, без ввода. Защищает данные на
  украденном/чужом компьютере.
- Добавлен sslmode к подключению PostgreSQL (по умолчанию prefer; для боевого
  сервера — require) — шифрование ПДн при передаче.
- На экране входа — подсказка для студентов/преподавателей.
- Отменён ранее добавленный «общий ключ организации» (keyvault) с паролем
  установки — для коммерческого продукта это лишняя сложность для пользователей.

## ФИКС: синхронизация с PostgreSQL вообще не включалась
Раньше `use_pg` требовал `is_key_activated()` — проверку «ключ ПК активирован в
таблице install_keys». Но кода, который добавляет/активирует ключ, в проекте не
было: проверка всегда возвращала False, поэтому PostgreSQL не подключался никогда,
и все ПК работали только локально (данные между ПК не синхронизировались).
- Теперь синхронизация включается, как только админ прописал сервер и
  пользователя БД (`is_pg_configured()`); доступ ограничен учётной записью PG.
- Удалён мёртвый код недоделанного лицензирования: `is_key_activated`,
  `get_key_hash`, таблица `install_keys`.

## Аудит и защита от перебора (приказ ФСТЭК №21)
- Новый `audit.py`: журнал событий безопасности (входы успех/неудача, создание и
  смена пароля администратора, экспорт ПДн) в `%LOCALAPPDATA%\GradeBookAI\audit.log`.
- Анти-брутфорс: после 5 неверных попыток логин блокируется на 5 минут; состояние
  на диске, поэтому перезапуск программы блокировку не сбрасывает.

## Локализация данных (152-ФЗ ст. 18 ч. 5)
- Боевая база с ПДн должна быть на территории РФ (сервер колледжа в ЛВС или
  российское облако). Предупреждения добавлены в db_config.py и requirements.txt.
  Зарубежный хостинг (Railway и т.п.) для боевых данных не подходит.

время неотличимо) расхождение пишется в sync_conflicts и НЕ затирает работу
преподавателя. В журнале — кнопка «⚠ Конфликты (N)» и окно выбора верного значения
(conflict_dialog.py).

## 3. Авто-бэкапы локальной базы (core.py, main.py)
DBManager.backup() копирует базу в …/GradeBookAI/backups/ с меткой времени, хранит
последние 30. Срабатывает перед загрузкой из PG, при выходе из программы и по кнопке
«🗄 Бэкап». Есть restore() и list_backups().

## 4. SQLite только на локальном диске (core.py)
База теперь всегда в локальной user-папке (%LOCALAPPDATA% / ~/.local/share/GradeBookAI),
никогда на сетевой шаре. Добавлены детект сетевого пути с предупреждением и
PRAGMA WAL + busy_timeout против блокировок и порчи.

## 5. Валидация дат (ui_date.py)
Свободный ввод «дд.мм.гггг» заменён диалогом-календарём (QDateEdit). Кривую дату

переведены на него. parse_date/normalize_date проверяют реальный календарь.

## 6. Единая методика среднего балла (grading.py)
Формула вынесена в один модуль — его зовут и core.calculate_average, и Вектор
(расхождение теперь невозможно). Вес пропуска «Н», учитывать ли пропуск и включать ли
экзамены — настраивается (config), дефолты сохраняют прежнее поведение, методика

# Итерация 3 — PostgreSQL вместо GitHub, вход по логину/паролю, хеширование

## GitHub удалён полностью

**PostgreSQL + SQLite**, без обращений в интернет.
- Рабочее чтение/запись — локальный SQLite (мгновенно, не блокирует интерфейс).
- При настроенном PostgreSQL запись дублируется в PG асинхронно (PGSyncer),
  при старте данные подтягиваются из PG в SQLite. Все ПК колледжа — одна база.

`data_store` хеширует пароль прозрачно при записи (поле `password` → `password_hash`).

- Убран скрытый вход админа «5 кликов» (давал доступ без пароля). Админ входит

преподавателей, журналы, API-ключ) теперь **шифруются** при записи
(Fernet/AES, см. security.py: encrypt_value / decrypt_value).
- Ключ шифрования хранится в ОТДЕЛЬНОМ файле `data.key` (в APPDATA\GradeBookAI),
  НЕ в базе. Поэтому украденный файл базы без ключа нечитаем.
- Приложение расшифровывает прозрачно — остальной код не изменился.
- Старые незашифрованные записи читаются как есть и шифруются при следующей записи.

Проверено: в файле базы ФИО и API-ключ лежат как `enc:...` (нечитаемо),
приложение и вход работают.

⚠️ **Важно для нескольких ПК:** файл `data.key` должен быть ОДИНАКОВЫМ на всех
ПК колледжа (иначе ПК не расшифрует общие данные из PostgreSQL). Скопируйте его
на все машины вместе с программой.

## Честно о границах защиты (важно!)
Зашифрован реестр студентов/учителей, журналы и API-ключ (kv_store).
**НЕ зашифрованы пока** рабочие таблицы журнала (`students`, `grades`) в локальном
SQLite-кэше — там ФИО и оценки лежат открытым текстом, потому что по ним идут
связи (join) и их шифрование требует детерминированной схемы (отдельная задача).
Для боевого режима эти данные защищаются на уровне сервера PostgreSQL:
ограничение доступа к БД + шифрование диска сервера (см. дорожную карту, 152-ФЗ).
